# Architecture

How the code is organized and why: the crate split, the engine thread and its clients, the parameter flow, the renderer's resources, the settings window, and the settings that are not shader parameters. The rendering itself (shaders, draw order, the celestial bodies, the clouds) is in [rendering.md](rendering.md), the tests in [testing.md](testing.md), and the per-OS behavior in [platforms.md](platforms.md). [retrospective-2026-08.md](reviews/2026-08-15-retrospective.md) section 7 is the reasoning behind the headless-first design; read it before changing the engine or the crate split.

## Headless first

The organizing principle is **headless first**. The engine runs to completion with no window at all; the settings window is one optional client. Hiding the window removes a client, it does not half-suspend the machinery. This is what removed the tray-mode memory leak class, made soak tests possible, and retired the teardown hacks.

## The engine (`sunlit_core::engine`)

One thread owns the wgpu device, the `Renderer`, the texture mailbox, and the schedule. Clients send `EngineCommand`s and receive `EngineEvent`s.

- **Commands**: `UpdateParams`, `SetPreviewSize`, `SetPreviewEnabled`, `RenderWallpaperNow`, `RenderToFile`, `ExportPixels`, `SetTextureResolution`, `SetDisplayPlan`, `DisplaysChanged`, `ReportMemory`, `ReportTiles`, `SetAutoRefresh`, `Poke`, `Shutdown`. `SetDisplayPlan` carries the display mode and the anchor screen, which are settings rather than shader parameters and so travel on their own command, exactly as `SetTextureResolution` does. `DisplaysChanged` is a hint and carries nothing: the watcher that sends it has no opinion about what moved.
- **Events**: `PreviewFrame { rgba, width, height }`, `TexturesReady`, `WallpaperSet(Result)`, `MonitorsChanged(Vec<Monitor>)`, `Status(String)`.
- **The loop never sleeps on wall time to decide what is due.** It blocks on the command channel with a 50 ms timeout and, on each wake, asks `clock.elapsed()` what is due: the texture drain (5 s), the sky state refresh (120 s), the cloud poll, the memory metrics sample (600 s), and the auto-refresh export. `Schedule::due` recomputes its deadline from `now` rather than accumulating, so a long stall produces one run and not a burst of catch-up runs.
- **Injected `Clock`.** `SystemClock` in production, `MockClock` in tests. `MockClock` advances UTC too, so simulated days really do rotate the Earth. This is what makes the soak test's two simulated days run in about a second and a half.
- **Injected `CloudSource`.** `HttpCloudSource` in production, fixtures in tests. A dedicated cloud worker thread does network I/O and JPEG decoding and never touches the GPU; it parks frames in the mailbox and pokes the engine, which uploads on its own schedule. A poll skipped because the worker is busy retries on the next tick. Which variant it fetches follows the texture resolution rather than the quality tier; see the Texture resolution section.
- **Injected `WallpaperSink`.** Three methods: `check_supported`, `monitors`, and `publish(&WallpaperJob)`. `SystemWallpaper` writes the PNGs and hands them to the desktop; `CountingSink` lets the soak test run for simulated days without touching one; `RecordingSink` in `tests/engine/` reports a fabricated monitor list and keeps what it was handed, which is what proves the engine asks for the right images in each mode on a machine with no second screen. `publish` answers `Result<String, String>`, and the success string is what the sink could not do: a desktop that cannot reach the mode does the nearest thing and says so, and `EngineEvent::WallpaperSet` carries that sentence to the status line.
- **A display-change hint settles before it is acted on.** `DisplaysChanged` sets a deadline two seconds out, and a hint arriving while one is pending pushes it out again, because a layout change is a burst on both platforms: RandR sends one event per CRTC and one per output, and Windows sends one `WM_DISPLAYCHANGE` per applied step, with a docking station bringing its screens up one at a time. When the deadline passes the engine asks the sink for the monitors once and compares against `known_monitors`, the last list it saw from a publish or from an earlier recheck. Equal is a debug line. Different, or no baseline yet, stores the list and emits `MonitorsChanged`; and where `published` is set it publishes again. The deadline is read off the injected clock and checked on the tick the loop already makes, so it costs no timer and no wakeup and a test advances a `MockClock` past it.
- **The preview follows window visibility.** The app sends `SetPreviewEnabled(false)` on every hide and `(true)` on every show, so a hidden window costs no readback. The engine keeps rendering regardless (the wallpaper export depends on it); only delivery stops. Re-showing pays back an "owed" frame from the existing texture, since the dirty check would otherwise suppress a re-render and leave the window blank.
- **Preview frames are pixel buffers**, not shared GPU textures. The engine reads its offscreen target back and hands over RGBA bytes; the app wraps them in `slint::Image::from_rgba8`. Slint therefore needs no wgpu feature and shares no device, which is why teardown is ordinary drop order.

## Parameters (`sunlit_core::params`)

`SceneParams` is the single description of what to draw: camera, texture selection, sample count, lighting, clouds, atmosphere, celestial controls, color correction, and the datetime input. There are exactly two translation points:

1. `ui_callbacks::read_params_from_window` / `apply_params_to_window` in the app.
2. `renderer::render_pass::write_uniforms` in core.

The Earth lens lives in `CameraParams::fov_deg` rather than beside `sky_fov` in `SceneParams`, because that is where `OrbitalCamera` already read it from and where `scene::sun_occlusion` already asks for it: wiring it through cost one assignment in `write_uniforms` and no digest entry, since camera floats compare exactly. The consequence is that it belongs to a preset too, and every entry of `PRESETS` carries `DEFAULT_CAMERA_FOV`, so a preset reproduces the framing its zoom was hand-tuned for instead of inheriting whatever lens was on. `CAMERA_FOV_MIN` and `CAMERA_FOV_MAX` (10 and 170 degrees) are the slider's ends and `AppConfig::sanitize` clamps to them, which is the one clamp there beside the texture resolution: `Mat4::perspective_rh` scales by `1 / tan(fov / 2)`, so 0 and 180 are not an ugly picture but no picture at all, and a config file is a text file.

## The renderer (`sunlit_core::renderer`)

`Renderer` owns every GPU object and renders offscreen into its own texture (`RENDER_ATTACHMENT | TEXTURE_BINDING | COPY_SRC`). It knows nothing about windows. Key methods: `render(&SceneParams, &SkyState) -> RenderOutcome`, `resize`, `drain_texture_updates`, `export_image_capped`, `read_preview_pixels`, `textures_ready`, `cubes_waiting`.

Submodules: `gpu_setup` (construction, pipelines, render targets), `render_pass` (uniform encoding, pass encoding, `Overlays::select`, `Stars::select`, `Sun::select`, `Moon::select`, `read_texture_rgba8`), `textures` (slots, mailbox draining, mipmapped upload, the bind group layout's `Bindings`), `surface` (the cube surface set, its formats per adapter, the surface sampler, and the upload of a pack's whole faces into a cube), `tiles` (the tile array, the page table, their rewrite and its check, and the per-cell cap the rewrite honors; public, like `uniforms`, so the render pipeline's tests drive it), `residency` (the wanted set and the cap, computed on the CPU from the cameras; public for the same reason), `texture_routing` (which mode draws the globe from which slot or surface group), `frame` (`FrameState` dirty check), `uniforms` (the 560-byte `#[repr(C)]` struct).

The texture slots are the grid at 0, then one slot per file-backed path in the order the paths arrive (the Moon 1, the Milky Way 2), then the cloud overlay last, 3, because it comes from the fetcher rather than from a file. `SlotLayout` is the one place that says so: it derives the cloud slot and the mailbox's slot count from the number of paths. The Moon and the Milky Way are `Rgba8Unorm`; the cloud overlay is `R8Unorm`, because `fs_cloud` reads the red channel alone: the fetcher keeps that channel straight out of the decoder (`Channels::Red` on the `DecodedImage` it posts), so neither the decoded frame nor the texture ever holds the three channels nothing reads, and `create_mipmapped_texture` builds either kind's mip chain with the same box filter. The four combo box modes are `TextureMode`s and not slots: the grid draws from slot 0 and the other three from the cube surface.

The cube surface is one unit beside the slots rather than three more of them. `SurfaceSet` in `renderer::surface` holds the day floors the engine keeps, every month's on a GPU, the night floor and the water mask, each a cube with its full mip chain, and three bind groups built from what is resident: the day floor of the month in force alone, the night floor alone, and the two with the mask for blend mode. The engine makes each resident from its pack on its own thread (`install_surface`), the mask, the night and the month in force's floor as their packs land and the other floors it keeps one a tick while it is idle (Months, below), not through a decode thread and the mailbox, and the globe is drawn from nothing else: there are no day or night slots, and without the cube (an incomplete face set, or no cache directory for the packs) it is the procedural grid. The grid in slot 0 is a cube too, 512 px a face, so the globe reads everything it draws through the warped direction (`rendering.md`, The globe's surface).

Above the floors, `SurfaceSet` holds `renderer::tiles::SurfaceTiles`: one tile array for the day's and the night's tiles and the page table that says what refines the floor at each cell (`rendering.md`, The tiles above the floor). A day or night pack handed to `install_surface` also gives the page table what its index says without a read, which tiles are constant ocean and the color they stand for; the day half names the tiles of the month in force alone, which `Renderer::set_surface_month` hands the table with the floor it draws (Months, below). The entry points the tile loader calls are on the renderer and synchronous on the engine thread. `Renderer::upload_tiles` takes `TileUpload`s, each a `TileId` (the pack and the `TileKey`), its `TileTexels` and optionally the layer to put it in; a tile goes into that layer, taking it from the tile that held it, else into the layer it already has, else into the lowest free one, and texels that are not a layer's size or that no layer can take are returned with the reason while the rest go in. The texels are the BC7 blocks as `Pack::read` returned them, or, for an array in RGBA8, those blocks decoded by `tiles::decode_tile`, which is what the loader's workers hand over so that the engine thread never decodes; blocks handed to an array in RGBA8 are decoded at upload. `Renderer::evict_tiles` frees the layers a list of tiles holds, `Renderer::purge_tiles` frees every layer and the array itself and puts the bind groups back on the array's stand-in, and `Renderer::set_tile_cap` hands the page table the finest level each cell may draw, the cap of the wanted set `renderer::residency` computes (`rendering.md`, The wanted set); until it is called the cap is the finest level everywhere. All four rewrite the page table whole and stage its upload behind the tile writes, so what a frame samples and the mapping it samples through reach the GPU in the same submit, and all four mark the frame dirty, the cap only when it changes the table. `Renderer::tile_layers` says which tile each layer holds and how many are free, which is what the loader evicts by. The array is created with the first upload at `TILE_LAYER_BUDGET` layers, 900, on a GPU and `CPU_TILE_LAYER_BUDGET`, 640, on a CPU adapter, or the device's `max_texture_array_layers` where that is lower, which `wgpu_init` requests at the adapter's own limit; `EngineConfig::tile_layers` sets another number, which the tests use to make the loader evict and the golden engine sets to none.

## The app (`sunlit-app`)

- `main.rs`: the console attach and a `main` over `sunlit_earth::run`, and nothing else. The program is in the library, where the tests can reach it: `cli.rs` is the clap types, `logging.rs` the subscriber, `startup.rs` the texture paths and the `EngineConfig` every mode shares, `headless.rs` the `render` and `displays` subcommands, and `app.rs` the entry point and the windowed run. `run_app` is an ordered list of steps over `start_engine`, `install_tray_and_geometry`, `start_startup_refresh_timer`, `register_close_handler` and `tear_down`, each of which documents what it cannot be moved ahead of. `run_render` is fully headless: no window, no Slint backend, no event loop; it starts the engine with the preview disabled, waits for `TexturesReady`, calls `render_to_file`, which the engine answers once the tiles of that size are resident or `TILE_WAIT` has run out, and returns an `ExitCode`. `run_app` takes the IPC socket name first, then creates the window, starts the engine, wires the UI, and runs the event loop. The socket comes first so a name the platform refuses, or one another instance holds, is known before the adapter and the textures rather than six seconds after; nothing is served on it until there is a window and an engine to answer for. CLI flags: `--mode <tray|window>`, `--tray-start <visible|hidden>`, `--ipc-socket <name>`, `--quality <low|medium|high>`, `--texture-resolution <8192|4096|2048>`, `--software-rendering`, `--textures-dir`, `--log-level`, plus the `render` subcommand. `startup::resolve_textures` names the two file-backed textures in slot order, the Moon and the Milky Way, and resolves the cube faces beside them. It asks how large each file is rather than whether it exists: `textures/**` is Git LFS, a checkout without the objects holds pointer files under the same names, and naming one costs a decode failure and an error line where the same run with no file at all is quiet and draws the same picture. The threshold is the 64 KiB the xtask's guest staging and the engine tests already use. `assets::cube_layout` names the 84 cube-map faces beside them (`day/2004MM/`, `night/` and `mask/`, six faces each in cube layer order), and `CubeTextures::resolve` gives each face a path, with an LFS pointer or an empty file resolving to an empty slot the way the Moon's and the Milky Way's files do. Startup logs how many resolved. The engine draws the globe from the cube when every face is there and from the grid otherwise; the tile cache section below has the wiring.
- `engine_client.rs`: `EngineLink` (send commands, push window state as `SceneParams`) and `event_forwarder` (engine events to the window). Preview frames cross the thread boundary through a latest-value mailbox with a single pending wake-up: the newest frame replaces the parked one and only one `invoke_from_event_loop` closure is ever in flight.
- `ui_callbacks.rs`: callback registration grouped into mouse, change, and action callbacks; every one of them ends in `link.push_params(&window)`. Also the config bridge (`apply_config_to_window`, `read_config_from_window`) and `set_combobox_indices`.
- `ipc.rs`: opt-in control channel over `interprocess` local sockets. `bind` takes the name and `IpcListener::serve` spawns the thread that answers it, in two steps for the reason above. Either failing is a warning and a run without the control channel. Commands: `quit`, `show-window`, `hide-window`, `export-test`, `query-memory`, `memory-report`, `set-wallpaper`. Fire-and-forget, with `SIGNAL:` lines on stdout as the reply channel. `export-test`, `query-memory` and `memory-report` are answered on the listener thread, so they work while the event loop is idle. `query-memory`'s single `SIGNAL:memory rss_bytes=... peak_rss_bytes=... private_bytes=... decoded_frames=... decoded_bytes=... downloads=... download_bytes=...` line is a parsing contract the e2e suite depends on, written and read by the one `MemorySignal` type, so a field changes on both sides in the same commit; `memory-report` is a separate command for that reason, and brackets its many lines with `SIGNAL:memory_report_begin` and `SIGNAL:memory_report_end` rather than promising a line format.
- `tray.rs`: the baked 32x32 icon bytes, the tray callback wiring, and single-instance enforcement. Both the tray icon and the single-instance mutex answer with an `Option`: a session with no tray host runs windowed, and a mutex the OS refuses leaves the app assuming it is alone. Neither is a reason not to draw a globe. The tray icon itself is a `SystemTrayIcon` component in `ui/tray.slint`, so Slint owns the platform integration.
- `session_end.rs`: Windows only. An invisible top-level window on its own thread that answers `WM_QUERYENDSESSION` and quits the event loop on `WM_ENDSESSION`, so a reboot does not have to wait for Windows to kill the process. winit handles neither message, so without this nothing in the app ever learned the session was ending. The decision is a pure function (`classify`), unit-tested everywhere; the Win32 window is tested by sending it both messages.
- `mouse_math.rs`: pure functions for mouse interaction (globe drag with tilt correction, frame drag, orient drag, tilt drag, zoom scroll). No Slint dependency; unit-tested with `proptest` invariants. The globe drag alone keeps two gains and blends between them by how fast the cursor is moving, because the painted surface and the sky lens do not scale together: `coarse_drag_gain` is the distance-proportional 0.3 degrees per pixel per eight Earth radii the drag has always had, `fine_drag_gain` is half the angle a pixel spans at the center of the sky lens, so a slow hand moves the Sun's image half a pixel per mouse pixel at every zoom, and `drag_gain` is a smoothstep between them in the logarithm of the speed from `FINE_DRAG_SPEED` to `COARSE_DRAG_SPEED`. The fine gain is capped at the coarse one, which is the only thing that could invert them, at the nearest zoom and the widest sky, and the sweeping end of the blend returns the coarse gain itself rather than the interpolation evaluated at 1, so a sweep turns the globe by exactly what it always did at every zoom rather than at most of them. `DragSpeed` is the estimator, an exponential moving average over the delta each `moved` callback brings and the time since the previous one, with the interval capped so a pause reads as a slow start; `ui_callbacks::register_globe_drag` holds it, and clears it on the left press, which is the one line `ui/main.slint` gained (`mouse-drag-globe-begin`): a press begins a gesture, and without the clear a deliberate drag started a few tens of milliseconds after a sweep inherits the sweep's speed and takes its first steps at the coarse gain. What it costs is path independence: a drag out and back at different speeds does not land where it started, which is the trade every pointer acceleration makes and the one the user chose over a modifier key. The two gains cross only at the nearest zoom against the widest sky, where the coarse gain is 0.056 degrees per pixel and the fine one 0.060, which is the single framing the `fine.min(coarse)` cap exists for: at 140 degrees of sky it is never active and the rate is one number from end to end, and at 180 it is active at the nearest zooms and nowhere else. The sweeping end of the blend returns the coarse gain itself rather than the interpolation evaluated at 1 because `fine + (coarse - fine)` rounds away from `coarse` at 62 of the 1001 zooms the slider reaches.

## UI (`ui/`)

`MainWindow`: resizable split layout, controls panel in a `ScrollView`. Top-level controls are "Set as Wallpaper", "Load Defaults" and "Reset", the auto-refresh checkbox, a 3x3 grid of camera presets, and the Displays group where the session has more than one screen. Below is a collapsible "Advanced" section with `GroupBox`es for Rendering, Camera Position, Camera Orientation, Framing, Date / Time, Clouds, Celestial, Atmosphere, Lighting and Color Correction. About is not in that section: it is a footer pinned under the scroll area, so it is one click away from a closed panel. The adapter name sits at the foot of the Rendering group, elided to one line with the whole of it on hover, because a word-wrapped `Text` inside the `if` reports the height of a single line whatever it wraps to and the scroll area sized from that cannot reach the rest. Camera properties are `in-out` with `<=>` slider bindings. A `TouchArea` over the image handles drag and scroll.

Every row in that section is one of three components rather than a hand-written layout: `SettingRow` (label, slider, value), `SettingCheck` and `SettingCombo`. Each carries a `hint`, the one-sentence hover text, and each has a `Tooltip` covering the whole row. That is why their roots are `Rectangle`s with the layout inside: the compiler lowers a `Tooltip` to a full-size sibling area, and inside a layout that area would claim a cell of its own. A row nested under a `SettingHeading` sets `indent`, which shifts the label right and takes the same width off it, so the sliders of a group stay in one column however deep the nesting is. Each instance keeps the element id the row's slider used to carry (`longitude-slider`, `rayleigh-intensity-slider`), since those are what `tests/slint_ui.rs` looks the advanced section up by.

The sidebar's width is derived, not chosen: it is the drag's stored width held between `panel.min-width`, which is what the content reports it needs, and whatever leaves the image `min-image-width`. That only works while nothing inside reports an unbounded minimum, which is the rule the `Setting*` components exist to keep. A `Text` fed from Rust reports its full unwrapped width as a minimum and needs `wrap: word-wrap` (`overflow: elide` does nothing for this: `layout_info` reads `wrap` and nothing else); a `CheckBox` or a `Button` reports the width of its own label and is pinned to zero; the fluent `ComboBox` asks for a flat 160px and `SettingCombo` overrides it. `tests/slint_ui.rs` asserts the resulting floor through the `panel-min-width` property, and it only means anything once the `if`-gated subtrees have been walked. The panel reserves the scrollbar's 14px in its right padding, since the fluent `ScrollView` draws the bar over the flickable rather than beside it, and the horizontal bar is `as-needed` so anything that does escape the floor is at least reachable. The panel's layout says `width: 100%` and not `parent.visible-width`, because only the literal spelling is recognized as filling the parent; anything else picks up a centering binding against a flickable viewport that grows to the content.

The tooltip's content is the custom-content form and not `Tooltip { text: ... }`, because the built-in content does not wrap and a sentence is wider than any screen. `Hint` is that content: the compiler still wraps it in the built-in `ToolTipImpl`, which is where the background and the border come from, and which sizes the popup from its children's preferred width. A `Text` reports the width it would take unwrapped however narrow the element around it is, so `Hint` declares `min-width`, `max-width` and `preferred-width` rather than a `width`, which the language refuses to have alongside them; the height then follows from the wrap at that width. Measured in the Linux guest under KDE, one boot per revision.

Celestial is subdivided: Sky (the sky lens and the Milky Way), Sun, Moon, Stars. The subsections are what let the labels drop the noun they repeated (`Star brightness` is `Brightness` under Stars), which is what makes one label column wide enough for every group.

`AboutWindow` is an ordinary exported window component: a fixed header over a `TabWidget` of three tabs. `about::AboutController` creates it on first use, supplies the package version and the three documents, registers the link opener, then reuses the handle. The settings control and tray callback clone the same controller.

The documents are `include_str!`s rather than files read at runtime: `assets/ATTRIBUTION.md` and `assets/third-party.md` for the two markdown tabs, and the repository's own `LICENSE` for the third. `git archive` of `HEAD` carries all three, so `cargo xtask dist` builds them in unchanged, and rustc records them in the dep-info, so editing one rebuilds the crate. Slint's `StyledText` renders a subset of CommonMark and cannot lay a document out: it rejects a heading, has no font size to give one, stacks paragraphs with no gap and no spacing property, and glues a list bullet to its paragraph as literal text, so a wrapped line gets no hanging indent. The two markdown tabs answer that differently, because their documents differ. `about::parse_blocks` cuts the attributions into blocks, a heading with its level, a list item with its nesting, or a paragraph, and the tab renders one element per row of an `AboutBlock` model, with only a block's own inline markdown reaching `StyledText::from_markdown`: a heading is a plain `Text`, since that is what carries a weight and a size, and a bullet is a `Text` drawn into the margin its item's padding leaves, because a `StyledText` laid out beside one in a `HorizontalLayout` reports the height of a single line whatever it wraps to. Under Slint 1.18 every block also states the width of its column as its `preferred-width`, and so does its `StyledText`: 1.18 measures the height of an element made by a `for` or an `if` at that element's own preferred width, which for wrapped text is one unwrapped line, so both markdown tabs ended their scroll area before their document ended (#66, slint-ui/slint#13655). Slint fixed it after 1.18.1, and the workaround comes out with the upgrade to 1.19. The third-party list is hundreds of uniform one-line entries with nothing to indent, so it stays one `StyledText` and `about::flatten_markdown` is what gets its leading heading through a parser that rejects headings: a heading becomes a bold line, a rule is dropped, nothing else is touched. The licence tab is a plain `Text` with `wrap: no-wrap` in a `ScrollView`, because that file is hard-wrapped at 76 columns with indentation that carries meaning and every markdown path through Slint reflows it. Links from all three tabs and from the header go through one `open-url` callback and out to the platform's own handler, with no `unsafe` and with only `http` and `https` reaching a shell.

`TrayIcon` inherits `SystemTrayIcon`: menu (Open, Refresh Now, checkable Auto-refresh, About, Exit) and `clicked()` to toggle the window. Only properties *declared* on the derived component are exposed to Rust, so the inherited `icon` is bound to a declared `tray-image` property. A `SystemTrayIcon`-rooted component implements `StrongHandle` but not `ComponentHandle`, so there is no `as_weak()`; the handle is kept in an `Rc`.

## Quality tiers

`QualityTier` (low, medium, high) is persisted in the config and overridable per run with `--quality` (the override is not written back). It has no widget in the settings window, which is why `read_config_from_window` is a read-modify-write against the stored config rather than a fresh `AppConfig::default()`: any persisted setting the UI does not manage has to survive a save untouched. It caps the MSAA sample count (1, 4, unlimited) and the preview width (1280, 1920, unlimited, aspect preserved). Default: low in debug builds, high in release; `EngineConfig::headless` pins low so tests do not depend on the build profile.

The tier does not select the cloud image variant; the texture resolution does. The tier says how much work a frame is allowed to be, and the cloud overlay is texture memory, which is what the other setting is for.

## Texture resolution

The Moon's texture is 1024 wide, which is at or below every cap the setting offers, so it is loaded at its own width whatever the setting says. The Milky Way panorama's 4096 is the one width between two caps: the two upper settings load it as it is and the lowest halves it in memory on each load, which is what `the_panorama_follows_the_texture_resolution_cap` measures. The Earth is not loaded at a width at all: it is drawn from the floors and the tile levels of the cube surface, and `AppConfig::texture_resolution`, from the three in `config::TEXTURE_RESOLUTIONS` (8192, 4096, 2048), caps how fine a level of them may become resident. 8192 allows both tiled levels, 4096 the coarser alone and 2048 the 512 px floors alone, and the Rendering group offers the three as a combo box. It also selects the cloud image variant, which is the third thing that scales with it; the three offered widths map one to one onto the three variants the upstream service publishes. The default is 4096, so an install whose config predates the setting moves to 4096 and anyone who wants the full width picks it once. `--texture-resolution <8192|4096|2048>` overrides it for one run; clap validates the three values, and a config file holding anything else is repaired to the default by `AppConfig::sanitize` on load, which is where the check belongs since a config file is a text file.

The halving of the Milky Way is the same box filter that builds the mip chain, so its 2048 texture is the 4096 texture's first mip level exactly.

Nothing is cached on disk for a downscale: the halving cache of earlier versions (`texture_cache/<stem>.<width>.png` under the cache directory) is retired (plan decision 8), and `texture_loader::remove_retired_downscales` deletes that directory when the engine is built, so no earlier version's downscales stay on disk. `texture_loader::load_capped` decodes the source and halves it in memory until it is within the cap, which for the Milky Way is one halving at 2048 and costs about 0.6 s of one background thread at jxl-oxide's 71 ns a pixel (research section 17, not measured here). The width is a cap, so a source narrower than the chosen width is loaded as it is.

Changing the setting at runtime is `EngineCommand::SetTextureResolution`, not a params push: it decides which pixels to load rather than what to draw. With the cube surface it purges the tile array and the page table as well and keeps the floors (The tile loader, below). The renderer clears the bind groups and views of the file-backed slots, calls `Texture::destroy` on the textures they held, and only then lets the reload allocate, in the same nil-before-recreate order as `gpu_setup::replace_render_textures`. `TextureSlot` keeps its `wgpu::Texture` so there is something to destroy, and `last_resolved` and `last_state` are cleared so the next frame is drawn afresh. `textures::lowering_the_resolution_releases_the_tile_array` in `tests/engine/` measures the point of it on the real cube: at 2048 the memory report's `tile_array` row goes, its computed total falls by the array's bytes, and wgpu's own texture counter falls by at least half the array (92.9 to 29.6 MiB measured on WARP). It does not assert on private bytes, which it only prints: a probe of five cycles that made 455 RGBA8 layers (45 MiB) resident at 8192 and purged them at 2048 left WARP's private bytes between 638.8 and 647.8 MiB, because the allocator reuses a destroyed texture's pages for the next one instead of handing them back, so the process footprint cannot tell a release from a reuse. The case skips with a printed reason where the cube faces are still Git LFS pointers.

The cloud overlay follows the same command but by a different route, because it comes from the network rather than from disk. `SetTextureResolution` deliberately does not purge the cloud slot: the switch must not depend on the network, and a cloudless globe while a download runs is a worse picture than one at the previous variant. What it does instead is point the fetcher at the new variant and ask for a poll now, and the existing update path replaces texture, view, and bind group together when that poll lands, which the soak test already proves frees the old one. Offline, the old variant stays for as long as the outage lasts, which is intended and logged. The worker reads its target before every poll, inside the retry loop rather than outside it, so a switch made during an outage changes what the next attempt asks for rather than queueing behind an attempt that may be minutes from finishing. The disk cache is keyed by variant (`clouds_cache_<w>x<h>.jpg` and its meta sidecar), so a switch can never be answered with the previous variant's bytes and a switch back finds what it left behind; an entry a run at another resolution wrote is dead weight the current one never reads, which is also what makes the change safe to roll back. The switch posts that entry as it adopts it, which is the step that makes a switch back visible at all: the poll it asks for sends the entry's own `ETag` to the entry's own URL, and inside the upstream refresh window that is a 304, which posts nothing. Nothing in production calls `post_cached` after startup, so without the switch doing it the overlay would sit at the previous variant until upstream published again. A variant with nothing on disk posts nothing, which is the same clause that keeps the old clouds up while a download runs.

`SUNLIT_EARTH_CLOUD_URL` still wins over all of it, and `SUNLIT_EARTH_NO_CLOUDS` is untouched. What the override serves has no variant, so it caches under `clouds_cache_override` rather than under a name claiming a size nobody checked; otherwise a run against a stub would leave that image in `clouds_cache_4096x2048.jpg` and the next ordinary run would put it on screen. With the override in force every resolution resolves to the same URL, and `set_resolution` compares URLs rather than variants, so a switch then moves nothing and keeps the `ETag` it has. `CloudUpdater::new` points the source at the URL its cache entry is named after, so the name and the bytes behind it cannot disagree whatever the caller built the source with.

The purge reaches only the Moon and the Milky Way, so the globe stays on the cube while they reload. Before the cubes exist the grid is drawn, which is fine for a preview and not fine for a desktop, so `publish_wallpaper` holds one request back while `Renderer::textures_pending` says a cube the current mode needs is on its way, and makes it at the end of the tick that cube arrives on. That covers every caller that publishes, since they all reach that one function: the button, the tray's "Refresh Now", the IPC `set-wallpaper`, and the auto-refresh schedule. What comes before the wait is the sink's own `check_supported`, so a platform with no wallpaper setter refuses at once rather than after seconds of waiting for textures that were never going to change the answer. `textures_pending` is deliberately not the negation of `textures_ready`: a cube whose pack failed is terminal, and without a cube surface nothing is ever pending, and waiting on either would be waiting for something that is never going to arrive.

A decode of the old width can still be running when the width changes, so every load carries the `texture_generation` it was spawned in, and two places use it. `process_decoded_textures` discards a post from a superseded generation and touches nothing else: `loading` names the decode that is on its way to a slot, a discarded post is never that decode (the generation moves only in `set_texture_resolution`, which purges every file-backed slot in the same call and clears the flag there), and clearing it again would claim a live load had stopped, which puts a second decode of the same source in flight beside the first. `TextureMailbox::post` refuses to let a stale arrival overwrite a parked message from a newer generation, which is the half that matters: the consumer discards a stale post on sight, so overwriting a fresh one there would destroy the only copy of the texture anyone wants and leave the slot empty for the rest of the session. The cloud fetcher posts no generation at all, and an unstamped message is neither held back nor held onto. Its slot is never purged, so there is nothing for a stamp to protect: a fetch of the old variant that lands after a switch is a cloud layer at the previous width for one poll, which is exactly what the switch deliberately leaves on screen while the new one downloads, and the next poll replaces it. The grid stays procedural at every width. `EngineConfig::mailbox` exists so a test can post that arrival directly, the same way the clock and the cloud source are injected, because the ordering needs a decode still running when the resolution changes and no amount of waiting makes that reliable; its slot count is asserted against the engine's own before the device is opened, since a seam that disagrees either drops posts or hands the consumer an index it does not have. Each of the three properties has a test that fails when the line carrying it is reverted: the mailbox guard, the discard, and the purge's own clear, which is what lets a reload start while the superseded decode is still running.

The setting has a widget, which makes the CLI override awkward in a way `--quality` is not: the window has to show what the engine actually loaded, but a one-run flag must not reach the config file. `EngineLink` therefore carries a flag, set at startup when the argument was given, that makes a save keep the stored width instead of reading the combo box; the combo box's own callback, Reset, and Load Defaults each clear it. That rests on a Slint property set from Rust not counting as a selection, which `test_setting_a_combo_index_is_not_a_selection` pins.

## The tile cache (`sunlit_core::assets::tiles`)

The cube faces are turned into packs of BC7 tiles once, on the user's machine (plan `plans/2026-09-29-seasonal-textures-plan.md`, Step 2), and the globe draws from the floors and the mask in them, from the constant-ocean flags of their index, and from the tiles the loader below reads out of them. `ensure_pack` builds one pack synchronously on the calling thread and the current rayon pool: a month of day (the 1024 and 2048 levels cut into 128 px tiles with an 8 px gutter and one mip, and the month's 512 px floor cube with its full chain), the night the same, or the mask as a BC4 cube of 1024 px. Packs live under `tile_cache/` in the directory the cloud cache uses, `day-2004MM.pack`, `night.pack` and `mask.pack`. A tile's gutter past a face edge is cut from the neighboring face at the same point on the sphere through `geometry::cube`, the mapping the bake uses, so sampling stays continuous across the edge. A tile whose footprint on the 2048 mask is all open water, and for the night whose texels also lie within 4 of the night's ocean color, is flagged constant ocean and stores nothing; the pack's header records the color it stands for. The index is sorted by level, face, row and column, with the offset, length, CRC-32 and SHA-256 of each blob, and the header carries the cache key: the stamps of the faces the pack was made from, the `dds` version, the preset, the geometry and the format version. `ensure_pack` rebuilds a pack whose key differs from the one the current sources give, writes it under a temporary name and renames it into place, and sweeps what an interrupted build left, as the halving cache does; a reader that holds the old pack open keeps reading it. `Pack::read` is a positional read checked against the blob's CRC, and takes `&self`, so one open pack serves any number of loader threads. `decode_bc7` is the decode a CPU adapter's upload goes through. The tests build packs from the texture pipeline's committed fixture bake, which `test_support::write_cube_fixture` lays out as a complete textures directory. Research section 21 has the sizes and timings on the shipped faces: 31.6 MiB a month, 416 MiB the year, 4.5 s a month on four threads.

A `Transcoder` runs `ensure_pack` over the fourteen packs in the background. The engine starts one when every cube face is there and a cache directory is set (`EngineConfig::takes_cube`), and the tests drive it headless as well. It owns one thread, `sunlit-transcoder`, and a rayon pool of its own, `sunlit-transcoder-N`, installed around each build so the JPEG XL decode and the encode stay inside it. The pool has `default_threads()` threads, the cores less two and at most four, and every one of them and the worker lower themselves to below-normal priority as they start (`thread_priority`, see `docs/platforms.md`). Research section 22 has a first run on the shipped faces (the month in force 4.5 s in, the year in 61 s on four threads) and how fast the worker gives way (within about 200 ms). A run has two passes:

- The check opens every pack and compares its key with the one the current faces would give, about 54 ms for all fourteen, and each current pack is ready at once. A second start over a whole cache therefore builds nothing and reports every pack ready in that time.
- The build takes the rest one at a time in rank order: the packs the first frame needs, which are the mask, the month in force and the night, then the other eleven months nearest the month in force, the next month before the previous one (for May: June, April, July, March and so on, November last). `set_month` changes the month in force at any time. The queue follows it, and the pack in progress is cancelled and put back in the queue only when it is a day pack and the new month's pack is still waiting; the mask, the night and a month that became the one in force always finish.

The pause gate, `set_paused`, holds everything after the first-frame packs: while it is closed nothing past them starts, and a build of one of them that is in progress is cancelled at the next point `ensure_pack` looks at its flag, which is between two face decodes or two batches of 64 tiles, and starts over when the gate opens. Cancelling rather than holding the build frees its decoded faces, over 100 MiB, instead of parking them for as long as the gate stays closed; the price is that pack's progress, so the gate is for spans of busy time and not for single frames. The month in force is a first-frame pack, so moving the date while the gate is closed still builds the month it lands on.

A pack that fails, from a face that does not decode, an I/O error or a panic in the decoder or the encoder, is recorded with its reason and the others go on; it is tried again on the next start and never in a loop. A textures directory without every cube face, which is what a checkout without the Git LFS objects has, builds nothing and says so as `Phase::Unavailable`. Dropping the handle raises the cancel flag and joins the thread; `stop` raises it without waiting. A cancelled or killed build never leaves a pack half in place, since the rename is the last step, and the next build of that pack sweeps the temporary file a killed one left.

What crosses from the worker to its holder:

- `status()`, the latest value behind a mutex, which a condition variable signals on every change: the `Phase` (`Checking`, `Building(kind)`, `Paused`, `Done`, `Stopped`, `Unavailable(reason)`), the packs that are ready in the order they became so, and the failures with their reasons. `wait_until` blocks on it for a caller with nothing else to do.
- `landed()`, a channel with one message per pack the moment it becomes ready, found current or built, which is what the engine will create a floor on. It is bounded at the fourteen packs: a pack is ready at most once per start, so the worker's send can never find it full, whenever the holder drains it.
- The `notify` callback of the `TranscoderConfig`, called on the worker thread after every change of the status and outside the lock, which is where the engine's wake-up goes.

The engine is the transcoder's holder, through `engine::surface::SurfaceFeed`. Its notify callback sends `EngineCommand::Poke` on the engine's own command channel, which is unbounded, so the callback never blocks on the engine thread that joins the worker when it drops the handle, and it has nothing in it that can panic. Every tick drains `landed()`, opens every pack that landed for the tile loader, and makes resident the cubes the frame draws, the mask, the night and the month in force's day floor; the other floors the engine keeps follow one a tick while it is idle (Months, below). A failure in the status, or `Phase::Unavailable`, marks its cube failed, which is terminal for this run. The month in force is derived from the scene's date wherever the sky state is, before a render and before an export (`scene::month`, plan departure 11). A new month goes to `set_month`, and its floor is drawn at once when it is resident, made resident at once when its pack has landed and waits its turn, and otherwise when the pack lands, with the floor drawn before drawn until then. The engine keeps the pause gate closed from its start and for `BUSY_AFTER_A_FRAME`, two seconds on the injected clock, after every frame and every export. The gate closes before the frame or export starts, so the transcoder yields during the work itself, and opens at the end of a tick in which nothing drew and the span has run out. Both come through `Engine::draw`, which closes it before it renders; the engine target's `an_export_closes_the_pause_gate_however_long_the_engine_was_idle` moves the clock past the span inside a publish, between the tick's reading and the export, and fails when the export does not close the gate itself. A drag or a slider holds the rest of the year back until it stops, and a lone frame of live time every two minutes closes the gate for two seconds. A publish judges the month in force before it judges whether the textures are pending, so a date that crossed into the next month since the last frame holds the wallpaper until that month's floor is resident.

Readiness follows the cubes and the tiles above them. `Renderer::textures_ready` is true once the cubes the mode needs are resident, which in blend mode is the floor of the month in force, the night floor and the mask, in the day and night modes that mode's floor, and for the grid nothing; `Renderer::textures_pending` is true while one of them is still to come from a pack that has not failed. The engine adds the tiles (below, readiness and the exports), `publish_wallpaper` holds a request back on the cubes, so no wallpaper is drawn from the grid while the first packs build, and the `render` subcommand waits for `TexturesReady` whenever the engine takes the cube. Without a cube the grid is the globe, and in the day, night and blend modes `textures_ready` stays false: nothing is coming, which `textures_pending` being false says, so nothing waits. A month change whose floor is not resident reopens the readiness latch, so `TexturesReady` is sent again when it lands.

`assets::cube_names` spells the 84 cube files once. The xtask, which shares no dependency with the core, compiles the same file into itself through a `#[path]` attribute, so what a bundle carries and what the core resolves cannot drift apart.

## The tile loader (`sunlit_core::engine::tile_loader`)

The loader makes resident the tiles the frame wants (plan decision 6). It exists beside the transcoder whenever the engine takes the cube, owned by `SurfaceFeed`, which opens every day and night pack for it the tick the pack lands. Every pack stays open, so the month ahead's tiles can be read before its hand-over and any month's the moment the date names it; the page table names the month in force's alone (Months, below).

- **The wanted set** is computed on the engine thread in `Engine::draw`, before every render and every export, when anything it is computed from changed since the last one: the outputs, each a camera with its framing applied (the preview's, then every export's that waits for its tiles, through `Framing::applied_to`, which `export_framed` renders with), the month in force and the month ahead (Months, below), the surfaces the mode draws (`residency::surfaces_for`, the sun's direction and the blend settings as `write_uniforms` hands them over), the finest level the resolution setting allows, the drag in progress, and whether a pack was opened or the array purged since. A pack opened in a tick that draws nothing, the month ahead's or another month's, has the set computed again without a frame. The finest level is the face's at the widest setting, one level coarser per halving, which on the shipped geometry is `residency::finest_level` and lets the tests' smaller geometries follow the setting too. The grid computes nothing. The page table is held to the preview's own cap before the frame is drawn, and whatever of the set is not resident, failed or already on its way is published.
- **The slot** the engine publishes to is latest-value: a list of tiles in the set's order, replaced whole by every publish, and a cursor. It sits behind a mutex with a condition variable, and holds the packs the workers read from, the array's epoch, and the tiles claimed and not yet taken back, which a publish leaves out so no tile is read twice at once. Cancellation is implicit: a tile that leaves the set is never claimed.
- **The workers**, `sunlit-tiles-N`, are `tiles::default_threads()` of them, the cores less two and at most four, each at below-normal priority (`thread_priority`). A worker claims the next tile under the mutex, parks on the condition variable when there is none, and reads the tile's blob with one positional `Pack::read`, checked against its CRC; where the tile array is RGBA8 it decodes the blocks there. A panic in a read fails that tile alone.
- **The results** come back through a channel bounded at two a worker, which blocks a worker whose result finds it full, so no worker reads ahead of the engine. Its consumer is the engine thread, which drains it on every tick, and the loop ticks at least every 50 ms whatever else happens; a worker whose result lands wakes the engine through its command channel, at most once until the engine drains, and a drain that leaves results behind wakes it again. A result is a tile's blob or its texels, 26 KB in BC7 or 104 KB in RGBA8, so the channel holds at most eight tiles in transit on four workers.
- **The drain** takes results until `UPLOAD_BUDGET`, 4 MiB, has been handed to the queue in the tick, and at least one, and uploads them before the tick's render, so the tiles and the table that names them reach the GPU in its submit. Every drain from the end of one tick to the end of the next shares that budget and the wait below, the tick's own and those an export or a publish makes before it draws, so a tick with an export waiting hands the queue no more than one without. The channel holds only a few tiles, so the drain takes what is queued and then, while a worker still holds a claimed tile or has one left to claim, waits for the next result until the budget is spent, and no longer than `DRAIN_WAIT`, 4 ms, after the tick's first drain began. Every result is uploaded before the drain returns. Research section 24 has the costs and the drain as measured: 162 BC7 tiles a drain on this machine's Radeon, a 4K day set of 506 in four drains and 15 ms, and 41 RGBA8 tiles a drain on WARP, 357 in nine drains and 95 ms, the uploads counted when handed to the queue, since WARP's own copy into an RGBA8 array is slow and runs when the next readback waits for it. A result is dropped when it was read from a pack that has since been opened again, before the array was last purged (the epoch), or for a tile no longer wanted; one that is dropped while its tile is still wanted is published again.
- **Eviction** happens only when a result needs a layer and none is free, and takes as many tiles as it needs from outside the set, the one wanted longest ago first, where a resident tile counts as wanted by every computation whose set held it. The floors are not in the array and are never evicted.
- **A set larger than the array** (plan departure 22) is taken in its order until the layers are spoken for, a failed tile taking none, and the rest is not loaded: those cells draw from the resident ancestor the page table finds under the cap, or from the floor. The log says so once when it starts and once when the array holds the whole set again, and the report counts what was left.
- **A tile that fails its read**, a CRC mismatch or an I/O error, is logged, recorded as failed for its pack, and not read again until that pack is opened again; the page table draws its cells from what is resident above it or the floor. It stays in the set, since the export readiness check counts it as satisfied.
- **The epoch** counts purges. `SetTextureResolution` purges the tile array and the page table, keeping the floors, and the next draw computes the set the new setting allows, so going down to 2048 frees the array entirely. The engine never recreates its device today; a recreation would purge the same way, so nothing resident or in flight outlives it.
- **Shutdown**: dropping the loader stops the workers, drops the channel's receiver so a worker blocked on it returns, and joins them.
- **The tile gate** (`TileGate`, `EngineConfig::tile_gate`) holds the workers' reads while it is shut, a worker keeping the tile it claimed, so the tile counts as on its way. The app never shuts it; the engine tests do, to keep the tiles a case wants on their way for as long as the case needs, which no amount of waiting on the workers makes reliable.

## Readiness, the exports and the drag

Plan decision 10 makes readiness the completeness of the wanted set, and the exports wait for it.

- **Readiness** is the engine's: `Engine::textures_ready` is the renderer's cubes and `TileLoader::complete`, which holds when the set in force was computed at the 1 px threshold, with no drag in progress, and every tile it takes in view is resident or failed. The margin never counts, nor do the tiles left for want of layers (plan departure 22). What a request waits on is asked of two predicates: `Renderer::textures_pending`, a cube still to come, and a count of the tiles an output wants in view that the set in force took and that are neither resident nor failed, `TileLoader::missing_for`, which a wallpaper asks of each of its renders (`shots_pending`) and an export of its own (`export_pending`). A failed tile counts as there, so neither can wait on it forever, which closes the roadmap's `textures_ready` defect for the tiled path. The latch behind `TexturesReady` is evaluated after every draw, the preview's and an export's alike, so the event goes out before a wallpaper drawn from what it announces, and it follows readiness both ways: new tiles wanted, a drag, a month or a resolution switch each reopen it, and `TexturesReady` goes out again when what the frame wants is there. A drain that only records failures still marks the frame dirty, so the draw that evaluates the latch follows it.
- **An export's outputs** join the wanted set at its front (`Output { export: true }`, which `Residency::wanted` ranks ahead of every other tile in view). A wallpaper's are the renders of its plan, one for each group of screens of one size or one for a spanned canvas, each the camera with that render's framing applied through `Framing::applied_to`, which is what `export_framed` renders with; a `RenderToFile` or `ExportPixels` request's is its size with the scene's own framing. The preview is always the first output.
- **The publish** holds a request back while a cube the mode needs is on its way, and then while a tile its own renders want in view is on its way, and makes it at the end of the tick those complete on; the preview's tiles and an export's do not hold it. It plans when it is asked for, whatever it then waits on, so its renders join the wanted set at its front at once and their tiles are read as soon as their pack is open. The wait for tiles is bounded by `TILE_WAIT`, 5 s on the injected clock counted from when the cubes were resident, and started over when the tiles it waits for could newly be read during the wait, which is when the month in force changes or its pack or the night's is opened (plan departures 30 and 31): after it the wallpaper goes out with what is resident in the missing tiles' place, their resident ancestors or the floor, the log says so, and the plan's renders stay in the set until their tiles are resident, when the wallpaper is made again. The wait for the cubes has no bound (plan departure 24). A request that finds its tiles resident plans again, with a fresh monitor list, and checks again, so a layout or a framing that moved while it waited is waited for too, within the same bound. `Shutdown` publishes a request asked for in its batch, or one still waiting for its tiles, with what is resident, since there is no tick left to wait in; one still waiting for a cube is dropped, since the globe would be the grid.
- **The exports a caller waits on**, `RenderToFile` and `ExportPixels`, are answered at once where the globe has no tiles or their own are resident, and otherwise wait in the engine, each for its own output's tiles alone and for `TILE_WAIT` from when it was asked for at the most, and are answered on the tick their tiles complete or the wait runs out, with a log line then. They wait for tiles and not for cubes, which stay the caller's to wait for through `TexturesReady`; the `render` subcommand does both. `Shutdown` answers a waiting export with what is resident.
- **The cap each render takes** is its own output's (`Residency::cap`, plan departure 23): the loader writes the preview's with every set, and each export render swaps its own in for its frame alone and puts the preview's back (`Renderer::export_image_capped`), leaving the redraw flag as it was, since the preview was drawn with that table already. The cap over all the outputs together would have a render smaller than another with the same camera read the larger one's tiles past their coarser level, which is what a pending 4K export would do to a 1080p preview, and a 4K screen to a 1080p one beside it.
- **The drag** is found on the engine thread from the camera's longitude and latitude that the draws see, on the injected clock (`DragWatch`): a move is part of a drag when it comes within `DRAG_PAUSE`, 100 ms, of the end of the tick that drew the move before it, or of the first sight of the camera, and its rate is that move's over the time between the two draws that saw them. The pause runs from the end of the tick, its readback included, because a frame shows at most one move: on WARP a 1080p frame and its readback take about 200 ms, a drag's moves queue behind it, and a pause counted from the move itself saw none of them as a drag. While one is in progress the set is computed at `DRAG_THRESHOLD_PX` with the lead along `residency::Drag`, the cap stays at 1 px, and readiness is false; the tick that finds the camera unmoved `DRAG_PAUSE` after the tick that drew its last move ends it and marks the frame dirty, and that draw computes the set at 1 px. A zoom is not a drag. Research section 25 has the convergence after a drag stops, on the Radeon and on WARP (plan departure 25).

`EngineCommand::ReportTiles`, and `EngineHandle::tile_report` on the client side, answer with a `TileReport`: the array's layers, the tiles taken from the set in order and how many of them are in view, how many were left for want of layers, what is resident and what failed, the tiles the page table names, how many results the engine has taken, the epoch, and how many day floors were made resident. The engine tests are written against it (`tests/engine/tiles.rs`), and it is what the loading line and the export readiness check can read.

## Months

Plan decisions 4 and 7, and Step 5. `scene::month::month_in_force` names the month in force from the date the Sun is computed for, the custom date or the live clock: the month whose first day is nearest, so the cut falls at mid-month (plan departure 11). The engine derives it before every draw and every publish (`Engine::sync_month`), outside the digest like the sun direction, and a change marks the frame dirty wherever it is seen, so the next tick draws the new month and asks for its tiles; a publish that is owed and still waiting for its tiles returns without drawing, and without the mark nothing would ask for them until its wait ran out (plan departure 31).

- **The floors.** On a GPU every month's day floor stays resident once its pack has landed, 2 MiB each in BC7 (plan decision 4): the month in force's is made resident the tick its pack lands, the others one a tick while the engine is idle (plan departure 32), and a change of month draws the new month's floor in the frame that names it. A CPU adapter keeps only the month in force's and, near a hand-over, the month ahead's, 8 MiB each in RGBA8, and makes any other month's resident in the frame that names it, about 200 ms on WARP (plan departure 35; research section 26). `SurfaceFeed` holds every day pack that landed, its index and an open file and no pixels, to make a floor resident again. The floor drawn while the month in force's pack is still to be built is the one drawn before it (plan departure 14), and it is never let go of while it is drawn. `EngineConfig::every_floor` overrides the adapter's way.
- **The page table names the month in force's tiles and no other month's.** `SurfaceTiles` holds what each pack handed over says about its tiles and the month in force (`set_month`), and its day half names that month's day pack once it has been handed over and the floor until then (plan departure 33). A tile's month is its `TileId`'s pack, `PackKind::Day(month)`, so the debug check of the rewrite, which compares the pack of every tile a cell names with its half's, fails on a tile of another month too. The old month's tiles leave the wanted set and are evicted as layers are needed.
- **The month ahead.** Within `PREFETCH_WINDOW`, a day, of a hand-over, the month across it is read ahead (`scene::month::month_ahead`): the next month ahead of the live clock, which only moves forward, and either side of the custom date, which a slider moves both ways. Its day tiles in view of every output join the wanted set after everything else, margin included, marked as margin, so they hold neither readiness nor a publish, are the first the array gives up, and are not counted among the tiles left for want of layers (plan departure 34). A crossing then finds the month it enters resident in view and waits for nothing. A day is far more than the live clock needs, since the engine draws at least every two minutes while the date is live and a view's tiles take a frame on a GPU and about a second on WARP to be read (research sections 24 and 25); for the custom date it is one step of the day slider, and a step along the hour slider is less.
- **The transcoder** builds the month in force first and ranks the rest of the year round it again when the month changes (`Transcoder::set_month`, The tile cache above).

The engine cases in `tests/engine/months.rs` hold this: every floor resident and the date drawing its own at once, a CPU adapter keeping two and making no floor resident that it lets go of, a busy engine making only the month in force's resident, an idle floor drawing no frame and leaving no staging buffer, the month ahead's pack landing without a frame still asking for its tiles, a sweep of the custom date across all twelve hand-overs and back with the resolution setting switched down and up in each direction, and the live clock crossing into the month ahead with every read shut. `TileReport::named` is what they check the table with.

## The loading line

`EngineEvent::Status` carries the line the settings window shows over the bottom right of the preview (`loading-text` in `main.slint`, set by `engine_client.rs`), and nothing else shows it: the tray has no tooltip and IPC no status command. `engine::loading` makes it (plan Step 6) from three things the engine asks after every draw and at the end of every tick, since the transcoder prepares the rest of the year while nothing is drawn, and it is sent only when it changed:

- **The pack the transcoder is building**, from its `status()` until it settles: a month as "Preparing March, 4 of 12", where the count is one more than the day packs ready or failed before it, so a first run counts from 1 to 12 whatever order the months come in, and the night and the mask as "Preparing Night" and "Preparing Oceans". This comes first whatever the frame waits for, since the frame waits for the pack being built. A pack held back at the closed pause gate is not being built, so a drag or a slider blanks the line until the engine is idle again.
- **A cube the mode needs on its way**, `Renderer::cubes_waiting`, the day floor of the month in force (and in blend mode the mask) and the night floor: "Loading Day...", "Loading Night..." or "Loading Day and Night...", the words the flat path used for its decode.
- **Tiles in view on their way**, the set in force's tiles in view that are neither resident nor failed, split by the surface they belong to, in the same words, but only once some have been on their way for `TILES_NAMED_AFTER`, half a second on the injected clock, without a tick in between that found them all there (plan departure 37). A GPU reads a view's tiles in a tick or two (research section 24), so a line named on every move of the camera would flicker; a software adapter, a cold file cache or a resolution switch takes long enough to say so.

`tests/engine/loading.rs` holds the sequence a first run sends, the packs named one by one with the months counted, through `BuildGate`, which holds the transcoder at the start of each build until the case lets it through (`EngineConfig::build_gate`; the app never holds it), and a warm start that names no pack and names the tiles exactly `TILES_NAMED_AFTER` after they went missing, with the moment counted again for the next tiles. `tests/slint_ui.rs` holds the window to showing the line while it is not empty.

## Sample counts

An MSAA sample count the adapter does not support is not a warning inside wgpu, it is a validation error that kills whichever thread builds the render target. Two layers guard it, and they are not redundant:

1. **The combo box** is built by `renderer::build_aa_options(adapter_supported, tier_cap)`, so the UI only ever offers counts that are both supported and within the tier.
2. **The engine resolves every requested count** through `renderer::resolve_sample_count` in `Engine::new` and again on every `UpdateParams`, and logs a `warn!` when it has to fall back. This is the single source of truth, and it is the one that matters: a config file, a hand-edited value, or a combo box index saved on a machine with a different GPU all arrive as a bare number in `SceneParams` and never go through the combo box.

The rule is "the highest supported count at most the requested one, otherwise the lowest on offer". `tests/engine/` starts an engine at the High tier (which does not cap) with `sample_count = 64` and asserts a frame still arrives.

## Wallpaper export

A publish is a plan over the monitors the session has rather than one image at the primary's size. `display::monitors()` is re-queried every time, `display::layout` turns that list and the mode into the exports to make and the crops to cut, and the engine renders each export with temporary GPU textures carrying `COPY_SRC`, reads them back through a staging buffer with 256-byte row alignment, encodes PNG, saves under `SunlitEarth` in the local data directory, and hands the finished `WallpaperJob` to the sink. PNG rather than TIFF because Windows preserves PNG wallpapers losslessly; TIFF wallpapers are JPEG-transcoded at 85% quality and band visibly in smooth gradients.

Three modes, in `DisplayMode`. `OneScreen` paints the anchor and leaves the rest as they are where the desktop can address them individually. `EveryScreen` is the default: the same view on every screen, rendered once per distinct size and shared, so two identical monitors cost one render and two files. `AcrossScreens` renders one canvas over the bounding box of the whole virtual desktop and cuts it, with the anchor keeping the framing it would have had alone; the geometry is in [rendering.md](rendering.md). On a session with one monitor all three are the same thing, which is why no migration was needed.

The job carries its images behind an `Arc` and each screen's slot is an `Option`: two screens of one size share one buffer and one encode, and a screen the mode does not paint carries no picture at all rather than a copy of somebody else's. A span is carried as the whole canvas plus its bounds rather than as pre-cut pieces, because a desktop that spans wants it whole and cutting it first would be wasted work; `WallpaperJob::image_for` does the cut for the sinks that need one.

A publish happens on demand (the button, the tray, IPC), on the auto-refresh schedule, and when the layout changed under a wallpaper this process made. That last rule is one sentence: the desk holds a picture made for a layout that is gone, so make one for the layout that is here. Its two edges are deliberate. `published` is set only where a sink answered `Ok`, so somebody who opened the settings window to look and never asked for a wallpaper does not get one because they moved a screen, and a sink that refuses is never asked unprompted, so a layout change cannot put an error in the status line out of nowhere. `display::watch` is what delivers the hint; [platforms.md](platforms.md) has the per-OS half.

Every publish writes into a directory of its own, `gen-<millis>-<pid>-<counter>` under the wallpaper directory, and `wallpaper/mod.rs` owns that choice: the names are `gen-<id>/<index>.png` per screen and `gen-<id>/canvas.png` for a span, so what a desktop is handed is always a path it has to load rather than one it can recognize and ignore, and no path a desktop still holds is ever rewritten or deleted under it. `docs/platforms.md` has the reasoning, which is entirely a Linux one; Windows shares the behavior because neither setter cares. A publish keeps the generation before it and sweeps everything older, so a layout that lost a monitor does not leave that screen's picture behind at full resolution forever, and `sweep_legacy_files` deletes what the two-slot scheme this replaced left in the directory.

## Memory reporting

Two things measure memory, and they answer different questions. `memory.rs` is the process-wide one: three counters per platform, a CSV the watchdog appends to, and a soft budget that emits a `warn!` when private bytes cross it. `memory_report.rs` is the where-is-it one: `MemoryReport` in six short sections, assembled on the engine thread because that is where the device is, reachable from a test through `EngineHandle::memory_report`, from a running app through the `memory-report` IPC command, and once per launch as a `debug!` dump the first time the textures are ready. Each counts what is alive at that moment, the staging buffers of writes not yet retired included: wgpu destroys a submission's staging buffers at the first submit or poll that finds it finished, and an engine that draws no preview may make neither until the next export. `EngineHandle::settled_memory_report` submits what is staged and waits for the GPU first, so its counters hold only what something keeps; the soak reads that one, and the check that an idle floor's upload was submitted reads the other.

The six sections are the process counters, the decoded pixel buffers and the downloaded cloud images alive in the process, wgpu's internal counters (`Device::get_internal_counters`), the backend allocator's live allocations (`Device::generate_allocator_report`), and the renderer's own table of what it believes it owns. The last two next to each other are the point: the day the columns disagree is the day there is a leak. Discipline keeps it readable rather than complete: the allocation section aggregates by GPU label, lists the ten largest groups of at least 1 MiB, and rolls everything else into one line; the expected table lists every texture over the same floor and totals all of them. Only the section names are a contract, and nothing parses the report, unlike `query-memory`'s single line.

The decoded pixel buffers are counted where they are made. `DecodedImage::pixels` is a `texture_loader::Pixels`, a wrapper around the buffer that adds one frame and its bytes to a process-wide count when it is made and takes them off when it drops; `texture_loader::decoded_pixels` reads the count, with the number of frames made since the process started beside it. The wrapper is on the buffer rather than `Drop` on the image because `create_mipmapped_texture` takes the image apart: it keeps the frame's `Pixels` and puts each mip level in place of the one before (`Pixels::replace`), so a frame counts as one from its decode until its last level has been uploaded and the buffer drops at the end of that function. Every image is decoded to be uploaded, so between loads the count is zero, and a frame that stays alive is a decoded pixel buffer parked in a queue, a cache or a long-lived struct. The count is in the memory report, in `query-memory`'s line as `decoded_frames` and `decoded_bytes`, and is what the soak test and the e2e hidden-window case assert on. It covers the image's own buffer and nothing else: the three-channel buffer a color cloud JPEG is decoded into lives and dies inside `decode_cloud_jpeg`, and the tile packs' pixels never become a `DecodedImage`.

The downloaded cloud images are counted the same way. `CloudImage::bytes` is a `cloud_source::Download`, which adds one buffer and its bytes to a second process-wide count when a source makes it and takes them off when it drops, and the cached image `CloudUpdater::post_cached` reads back off the disk is wrapped in one as well; `cloud_source::downloads` reads the count, with the number made since the process started. The wrapper is on the buffer rather than `Drop` on `CloudImage` because `poll_once` moves the freshness fields out of the image. A download lives through the poll that fetched it: it is decoded, written to the cache, and dropped when the poll returns, a moment after its frame is posted, so between updates the count is zero. It is in the memory report (`cloud downloads:`), in `query-memory`'s line as `downloads` and `download_bytes`, and the soak test and the e2e hidden-window case assert on it beside the frames. Both counts cost a few atomic operations per decoded image, per mip level and per download, a few times an hour against decodes of milliseconds, and neither counts anything per frame or per preview buffer.

Both wgpu queries degrade rather than vanish. `generate_allocator_report` is implemented for D3D12 and Vulkan and returns `None` elsewhere, so on Metal the section says so and names the adapter; the counters need the `counters` cargo feature, which is on workspace-wide, and a backend that does not maintain one reports zero: in wgpu 28 D3D12 and Vulkan keep the texture and buffer bytes and Metal keeps neither; D3D12 and Metal keep both object counts and Vulkan keeps the buffer count but counts a texture down when it is destroyed and never up when it is made, so its texture count goes below zero; and no backend keeps the allocation count (Vulkan reads it from a counter nothing adds to), so it is zero everywhere. The adapter slug is printed because it is what says whether the GPU bytes overlap the process's private bytes: on WARP and lavapipe they do, and on Windows on this machine's Radeon they do as well, both through Vulkan and through D3D12: every block the allocator takes counts in private bytes from the moment it is taken, written or not, while the working set does not move (research section 28). On a GPU whose driver charges its blocks to the process, as this Radeon's does on Windows (the only GPU driver measured), the allocator section's reserved figure is the one to read against private bytes, and the working set is what tells the GPU's share from the process's own.

The budget is a function of the texture resolution rather than one constant (`memory::private_bytes_budget`): a cold start, plus headroom, plus the textures that width keeps resident (the cube surface and its tile array where the setting allows tiles, the cloud overlay and the Milky Way), plus the Moon's 6 MiB, which is a constant because its file is narrower than the narrowest cap and is therefore loaded at the same width whatever the setting is. The cold-start half does not shrink with the setting. It is 1 GiB, measured on the cube surface: the release app's peak private bytes were 772 MiB on a GPU and 1140 MiB on WARP, which `memory.rs` records as `MEASURED_COLD_START_PEAK`, and the cold start is that peak less the textures the budget counts at 8192, rounded up. With the headroom the budget is 1583 MiB at 2048, 1687 at 4096 and 1719 at 8192, the cloud overlay counted at one byte a texel (research sections 27 and 28). Tests pin both directions: the budget clears a cold-cache first run at every resolution, and stays under twice one, so it is neither a warning nobody reads nor a warning nobody gets. Every resolution is held to the one peak that was actually measured (1140 MiB, at 8192) rather than to a smaller figure derived from the budget's own decomposition, which would move with it and assert nothing. That makes 2048 the binding case, since it gets the smallest resident allowance and has the same cold start to pay for. Every device asks wgpu for `MemoryUsage` rather than the default hint, because the allocator's reserve is committed process memory wherever it was measured: with the CPU adapter's two floors resident it holds 578 MiB instead of 634 on WARP, and with all twelve 642 instead of 891 (plan departure 38, research section 27), and on the Radeon, at 8192 with the preview at 8x MSAA, the default reserved 768 MiB in five blocks for 397 in use (research section 28). The hint changes the allocator's block size, 8 to 64 MiB where the default takes 128 to 256, and only the D3D12 and Vulkan backends read it. Smaller blocks leave less spare room for transient allocations, which matters twice: the preview is read back through a staging buffer the renderer keeps (`Renderer::read_preview_pixels`), which lives from the first read until a resize, a failed read or `SetPreviewEnabled(false)` drops it and is made again at the next read, so a hidden window holds none, since a fresh one each frame would take a block of its own and cost a GPU 0.5 to 0.9 ms a frame; and an export still makes its targets and its readback afresh and frees them before it returns, so with little spare room in the blocks a 3440 x 1440 export at 8x took 34 to 64 ms where the default's slack let it take 46 (research section 28).

## Resource-flow rules (from the retrospective, section 8.2)

- Every queue crossing a thread boundary is bounded, latest-value, or unbounded with the reasoning written down at the declaration site. There are five crossings today:
  1. **Decoded textures** (`assets::mailbox`, core): latest-value, one slot per texture. This is the Phase 0 fix.
  2. **Preview frames** (`engine_client`, app): latest-value, one slot, with a single pending wake-up so the UI thread cannot accumulate frame buffers either.
  3. **Engine commands** (`engine::start`, both directions): unbounded, deliberately. The consumer is unconditional and runs at most 50 ms apart, the producers are human-rate, and the payloads carry no pixels (`command_payload_is_small` pins that). A bounded channel would either block the UI thread against a mid-export engine or drop an `UpdateParams` that might be the last one. The premises behind that are a comment at the channel itself; keep both honest if any of them change.
  4. **Tile packs** (`assets::tiles::Transcoder`, core): the status is latest-value behind a mutex, and the landed packs go through a channel bounded at the number of packs, which a start sends to at most once per pack, so the worker never blocks on it. Its consumer is whoever holds the handle, and the worker does not depend on when that is.
  5. **Tiles** (`engine::tile_loader`, core): the tiles to read are a latest-value slot behind a mutex, replaced whole by every publish, and the tiles read go back through a channel bounded at two a worker, which blocks a worker when the engine falls behind. The engine thread is the consumer and drains it on every tick, at least every 50 ms. What is in it is in transit, at most a few tiles' blobs or texels, and is uploaded or dropped on the tick it is taken.
- Decoded pixel buffers are never parked in queues, caches, or long-lived structs.
- Every background producer names its consumer and the condition under which the consumer runs. If that condition is not "always", the design is wrong.

## Key constraints

- `rust-toolchain.toml` pins the channel (`1.94.0`, profile minimal, rustfmt and clippy).
  rustup honors it in this checkout whatever the host's default is, which is intended:
  a release build has to be able to say which compiler made it, and the builder images
  install the channel `guest::toolchain::pinned` reads out of that file. A developer whose
  default is newer sees `rustc -V` differ inside and outside the checkout.
- `.cargo/config.toml` links the C runtime statically on `x86_64-pc-windows-msvc`
  (`-C target-feature=+crt-static`). Every Windows build of this tree agrees, the e2e
  binaries and a local `cargo build --release` included, and the `cc` crate follows it
  with `/MT` for the Astronomy Engine's C. A clean Windows 10 then needs no Visual C++
  redistributable, which is what `dist --target windows` proves on the artifact.
- `unsafe_code = "deny"` in `[workspace.lints.rust]`. It is `deny` and not `forbid` because Slint macros need unsafe internally. `scene/sun.rs`, `scene/sky.rs`, `wallpaper/windows.rs`, `wallpaper/windows/shell.rs`, `config/window_geometry.rs`, `memory/windows.rs`, `memory/macos.rs`, `display/macos.rs`, `display/watch.rs`, `wallpaper/macos.rs`, `about.rs`, `session_end.rs` and `main.rs` have scoped `#[allow(unsafe_code)]` on individual FFI call sites with `// SAFETY:` comments. New FFI, on any platform, follows that pattern; the macOS `task_info` call in `memory.rs` is the most recent example.
- Slint is pinned to `~1.18` with no wgpu feature. The app does not share a device with Slint, so the wgpu version is independent of the Slint version.
- Render texture size is quantized to 64px boundaries to reduce GPU texture churn during resize, and then capped by the quality tier.
- Zoom is normalized (0.0 to 1.0) with exponential mapping: `distance = 1.5 * (80.0 / 1.5)^t`. Use `zoom_to_distance` / `distance_to_zoom` in `scene/camera.rs`.
- The grid is a procedural cube read through the surface sampler: trilinear, anisotropy 8 on a GPU and 1 on a CPU adapter. The Moon, Milky Way and clouds use a 16x sampler.
- WGSL `vec3<f32>` has 16-byte alignment, so `#[repr(C)]` structs need an explicit `_pad: f32` after every `[f32; 3]` field. `uniforms.rs` has a compile-time size assertion. It also declares the block once, as a list of Rust type and WGSL type, and its unit tests read `sphere.wgsl` and compare the two field lists name for name and offset for offset.
- LF line endings globally.
- `[profile.dev.package."*"]` builds dependencies at `opt-level = 2` with no debug info even in debug builds, which is what makes the GPU and math crates usable in a debug run.
