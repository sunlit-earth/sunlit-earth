# Research: Live Clouds (2026-03-20)

## Problem Statement

Sunlit Earth currently loads a static cloud PNG from disk at startup. The goal is to upgrade this to a live-updating cloud texture fetched from [matteason/live-cloud-maps](https://github.com/matteason/live-cloud-maps), with HTTP conditional requests to avoid redundant downloads, persistent disk caching, and new UI controls for cloud floor and cloud gamma so the user can tune contrast on the fly without re-downloading.

## Requirements

1. **8K cloud texture** from `https://clouds.matteason.co.uk/images/8192x4096/clouds.jpg` (JPEG, ~5 MB).
2. **Regular update checks** against the server, using HTTP conditional requests (`If-None-Match` with ETags) to avoid re-downloading unchanged images.
3. **Persistent disk cache** of the source JPEG so the app can display last-known clouds immediately on startup, then check for updates in the background.
4. **Post-processing on the fly** (floor and gamma adjustments) applied at decode time, never cached as a separate processed file.
5. **Two new UI sliders**: cloud floor and cloud gamma, in addition to the existing cloud opacity slider.
6. **No async runtime** — the app has no tokio dependency and should not gain one.

## Findings

### Cloud Data Source

The matteason service delivers pre-composited equirectangular cloud maps as static files served from GitHub Pages, fronted by Cloudflare. Four resolution tiers are available (8K, 4K, 2K, 1K). The 8K image at `8192x4096/clouds.jpg` is approximately 5 MB (JPEG quality 80, size varies with cloud coverage in the 4-6 MB range).

The images are generated by a GitHub Actions workflow on a `*/30 * * * *` cron (every 30 minutes), though GitHub Actions queueing delays push the effective update cadence to roughly 60-90 minutes. The README's claim of "eight times per day" is a conservative lower bound. The pipeline fetches EUMETSAT WMS satellite tiles, composites them with gamma correction and blending, fills polar gaps by mirroring adjacent data, and emits four resolution tiers.

There is no lightweight metadata endpoint (no JSON manifest, no timestamp file). The only way to check for updates is a conditional GET or HEAD request against the image URL itself.

### HTTP Conditional Request Support

Both `If-Modified-Since` and `If-None-Match` headers are fully supported by the server and correctly return `304 Not Modified` with no body when the image has not changed. Key response headers observed on 2026-03-20:

- `ETag: "69bd649b-4f332f"` (nginx-style, changes with each regeneration)
- `Last-Modified: Fri, 20 Mar 2026 15:15:39 GMT`
- `Cache-Control: max-age=7200` (2-hour CDN TTL)
- `Accept-Ranges: bytes` (range requests supported if needed)
- `access-control-allow-origin: *` (CORS enabled)

`If-None-Match` (ETag-based) is the preferred conditional request mechanism per HTTP/1.1 spec. When both headers are sent, the server prioritises `If-None-Match`. A 304 response preserves all caching headers, so the client can update stored values without re-downloading.

### Polling Strategy

Recommended polling interval: **60 minutes** using conditional GET.

Rationale:

- The CDN `max-age` is 2 hours, so polling more often than that does not reduce server load (Cloudflare serves cached responses).
- Actual image updates arrive roughly every 60-90 minutes.
- At 60-minute intervals, a typical 8-hour session costs ~8 conditional requests (~1 KB each for 304 responses) plus 5-8 full 5 MB downloads when updates are available.
- On first launch (no cached image), an unconditional download is appropriate.
- On subsequent launches with a cached image, the app loads the cache immediately and performs a conditional GET in the background.

### Rust HTTP Client

**`ureq` 3.x** is the correct dependency choice:

- Blocking (synchronous) I/O — no async runtime needed.
- Forbids `unsafe` internally.
- Minimal dependency tree: TLS via `rustls` by default, no tokio, no hyper.
- `Agent` is `Clone` (internal `Arc`), safe to share across threads.

Add to `Cargo.toml`:

```toml
ureq = { version = "3", default-features = false, features = ["rustls"] }
```

Note on 304 handling: ureq 3.x treats non-2xx responses as errors (`Err(ureq::Error::StatusCode(304))`). This is by design — 2xx is `Ok`, everything else is `Err`. The exact error variant should be verified against ureq 3.x source before implementation, as the error enum may differ from ureq 2.x.

`reqwest` was rejected because even its "blocking" API spawns a tokio thread internally, adding unnecessary runtime overhead.

### Background Thread Architecture

The existing codebase already uses `std::thread::spawn` with `mpsc` channels for async texture loading. The live cloud fetcher fits naturally into this pattern:

```text
Background fetch thread          mpsc channel          Slint UI thread
(std::thread::spawn)        ───────────────────>     (main thread)
- ureq blocking GET                                  - Slint Timer polls try_recv()
- decode JPEG (image crate)                          - uploads new texture to GPU
- send Result<CloudUpdate>
```

The background thread maintains a persistent `ureq::Agent` (connection pooling) and cached ETag across loop iterations. It sleeps 60 minutes between polls. The UI thread checks for new images via `try_recv()` in a timer callback, which returns immediately if nothing is available.

An alternative to timer-based polling is `slint::invoke_from_event_loop()`, which lets the background thread push a closure onto the Slint event loop when a new image arrives. This avoids timer overhead but requires the closure to be `'static + Send`.

### Persistent Disk Cache

Cache layout in `%LOCALAPPDATA%\SunlitEarth\`:

```text
clouds_cache.jpg           <- last successfully downloaded cloud JPEG
clouds_cache_meta.toml     <- ETag and Last-Modified strings
```

Startup sequence:

1. Load `clouds_cache.jpg` and `clouds_cache_meta.toml` if they exist.
2. Upload the cached JPEG as the initial cloud texture immediately (fast startup with last-known clouds).
3. Spawn the background fetch thread, which immediately performs a conditional GET using the stored ETag.
4. If 304: no update needed (cached image is current). If 200: write new image and metadata to disk, push new texture to the UI thread.

The `dirs` crate (already in `Cargo.toml`) provides the correct local data directory via `dirs::data_local_dir()`.

The ETag and Last-Modified values should be stored in a separate `clouds_cache_meta.toml` file rather than in the main `config.toml`, because they are cache metadata (not user settings) and have different invalidation semantics.

### Post-Processing (Floor and Gamma)

The existing Python fetch script (`scripts/fetch_matteason_clouds.py`) demonstrates the post-processing pipeline that significantly improves cloud contrast:

1. **Floor** (black point): Subtracts a threshold to remove surface haze. The script defaults to `floor = 50/255 ≈ 0.196`. Pixels below the floor become fully transparent.
2. **Gamma** (midtone adjustment): Raises values to a power of `1/gamma`. The script defaults to `gamma = 0.3` (i.e., exponent = 3.33, which darkens midtones considerably).

The post-processing formula per pixel:

```text
result = clamp((value - floor) / (1.0 - floor), 0.0, 1.0) ^ (1.0 / gamma)
```

This can be applied in two places:

**Option A: CPU-side at decode time.** Apply floor and gamma to the decoded pixel buffer before uploading to the GPU. This means re-decoding and re-uploading whenever the user adjusts the sliders, but avoids adding shader complexity. Latency concern: decoding an 8K JPEG takes measurable time.

**Option B: GPU-side in the fragment shader.** Upload the raw (unprocessed) cloud texture and apply floor and gamma in `fs_cloud`. This allows instant slider feedback without re-uploading. Two new uniform fields are needed: `cloud_floor` and `cloud_gamma`. This is the recommended approach because:

- Slider adjustments are instant (no texture re-upload).
- The raw source image is cached once; processing parameters are just uniforms.
- The existing shader already has the cloud density value available as a float.
- The uniform buffer has 8 bytes of padding (`_pad3`, `_pad4`) that can be repurposed.

The shader change to `fs_cloud` would be:

```wgsl
let raw = textureSample(sphere_texture, sphere_sampler, in.uv).r;
let floored = saturate((raw - uniforms.cloud_floor) / (1.0 - uniforms.cloud_floor));
let cloud_density = pow(floored, 1.0 / uniforms.cloud_gamma);
```

### Current Codebase Integration Points

**Texture loading:** The cloud texture is already loaded asynchronously via the `TextureSlot` system (slot 3, `CLOUDS_SLOT`). The slot is loaded unconditionally in the background regardless of the selected Earth texture. The live fetcher replaces the file-based load with an HTTP download, but the GPU upload path (`process_decoded_textures` -> `create_mipmapped_texture` -> `maybe_create_cloud_bind_group`) remains unchanged.

**Texture re-upload on update:** When a new cloud image arrives from the server, the existing `cloud_texture_view` and `cloud_bind_group` must be replaced. The current system creates these once; supporting replacement requires either:

- Resending through the existing `mpsc` channel (slot 3), which `process_decoded_textures()` already handles by overwriting the slot.
- Or adding a dedicated cloud update channel.

The first approach (reuse the existing channel) is simpler if `process_decoded_textures()` correctly handles receiving a new texture for an already-loaded slot.

**Uniform buffer:** The `Uniforms` struct is currently 144 bytes with two padding fields (`_pad3` at offset 136, `_pad4` at offset 140). These can be repurposed as `cloud_floor` and `cloud_gamma`, maintaining the same struct size and alignment. The WGSL uniform struct would gain two corresponding fields at the same offsets.

**Dirty-checking:** `FrameState` already tracks `cloud_opacity`. Two new quantized fields (`cloud_floor` and `cloud_gamma`) must be added to trigger re-renders when those sliders change.

**Config persistence:** `AppConfig` already has `cloud_opacity`. Two new fields (`cloud_floor` and `cloud_gamma`) with appropriate defaults must be added. The existing serde/TOML round-trip and debounced save mechanism require no structural changes.

**UI:** The Slint controls panel has a "Clouds" `GroupBox` containing the opacity slider. Two new sliders (Floor and Gamma) should be added to this group. The existing pattern of bidirectional `<=>` bindings with `sliders-changed()` callbacks applies.

**Image decoding:** The `image` crate (already in `Cargo.toml`) can decode JPEG via `image::load_from_memory()`. The existing `texture_loader.rs` handles PNG and JXL; JPEG support is a natural extension. The equirectangular coordinate transforms (horizontal flip, 1/4-width left shift) that `texture_loader.rs` applies to all textures must also be applied to the cloud JPEG.

### Cloud Rendering Architecture

The cloud layer uses a second sphere overlay approach:

- Separate `cloud_pipeline` with its own vertex/fragment shader entry points (`vs_cloud`, `fs_cloud`).
- Cloud sphere scaled outward by `cloud_sphere_radius = 1.0015` (0.15% larger than Earth) to prevent Z-fighting.
- Cloud texture sampled as greyscale (red channel = density).
- Shader applies day/night lighting via `smoothstep` brightness based on sun direction and terminator width.
- Final output: `vec4(brightness, brightness, brightness, cloud_density * cloud_opacity)` — white clouds with alpha blending.
- Both Earth and cloud sphere draw in the same render pass (Earth first, then clouds if opacity > 0 and bind group exists).

## Technical Constraints

1. **`unsafe_code = "deny"`** in Cargo.toml. The HTTP client (`ureq`) forbids unsafe internally, so no scoped allows are needed.
2. **No async runtime.** The app uses Slint's event loop exclusively. Background work must use `std::thread::spawn` with blocking I/O.
3. **Uniform buffer alignment.** WGSL `vec3<f32>` requires 16-byte alignment. The current struct has explicit `_pad` fields. Repurposing `_pad3` and `_pad4` for cloud floor/gamma maintains alignment since they are scalar `f32` fields that don't precede a `vec3`.
4. **Compile-time size assertion.** `const _: () = assert!(std::mem::size_of::<Uniforms>() == 144);` — repurposing padding fields to `cloud_floor` and `cloud_gamma` does not change the struct size.
5. **Network resilience.** The app must function without network access. If the fetch fails or the server is unreachable, the app should fall back to the cached image (if any) or display no clouds silently.
6. **JPEG feature flag.** The `image` crate in `Cargo.toml` currently only enables the `png` feature. The `jpeg` feature must be added for cloud JPEG decoding.

## Open Questions

1. **ureq 3.x 304 error variant:** The exact error type for a 304 response in ureq 3.x needs verification against the current source. The API shape was confirmed from documentation but the error enum may differ from ureq 2.x.
2. **HEAD request support:** It is unverified whether a HEAD request to the Cloudflare CDN returns the same `ETag` and `Last-Modified` headers as a GET. A HEAD request would be even lighter than a conditional GET for freshness checks.
3. **Rate limiting:** There is no documented rate-limiting policy for the matteason service. GitHub Pages + Cloudflare are unlikely to rate-limit at 1 request per hour, but there is no guarantee.
4. **Texture re-upload path:** The current `process_decoded_textures()` function needs verification that it correctly handles receiving a new texture for slot 3 when one is already loaded. If it creates a new bind group and texture view, the old ones should be dropped cleanly.
5. **Default floor and gamma values:** The Python script uses `floor=50/255, gamma=0.3`. These should be validated visually in the shader before committing to defaults, as the GPU gamma path (applied to float values) may behave slightly differently than the Python NumPy path (applied to normalized uint8 values).
6. **JPEG decoding feature flag:** Need to confirm the exact `image` crate feature name for JPEG decode support (likely `"jpeg"` based on the crate docs).

## Recommendations

1. **Use `ureq` 3.x** as the HTTP client. Add `ureq = { version = "3", default-features = false, features = ["rustls"] }` to `Cargo.toml`. Add `"jpeg"` to the `image` crate's feature list.

2. **Apply floor and gamma in the shader** (Option B). Repurpose `_pad3` and `_pad4` as `cloud_floor: f32` and `cloud_gamma: f32` in both the Rust `Uniforms` struct and the WGSL uniform block. This gives instant slider feedback with no texture re-upload.

3. **Cache the raw JPEG to disk.** Store the unprocessed source image at `%LOCALAPPDATA%\SunlitEarth\clouds_cache.jpg` with a companion `clouds_cache_meta.toml` for ETag/Last-Modified. On startup, load the cached JPEG immediately, then check for updates in the background.

4. **Poll every 60 minutes** with `If-None-Match` conditional GET. On first launch (no cache), perform an unconditional download. On subsequent launches, load cache first, then conditional GET.

5. **Add cloud_floor and cloud_gamma to the full data path:** `AppConfig` (persistence) -> Slint properties (UI) -> `FrameState` (dirty-checking) -> `ShadingParams` (render pass) -> `Uniforms` (GPU). Use sensible defaults derived from the Python script: floor ~0.2 (50/255), gamma ~0.3.

6. **Reuse the existing texture channel** for cloud updates. When the background fetch thread has a new image, send it through the same `mpsc::Sender<DecodedTextureMessage>` with `slot_index = CLOUDS_SLOT`. Verify that `process_decoded_textures()` handles slot replacement correctly.

7. **Retire the Python fetch script** once the Rust implementation is complete. The script served as a proof-of-concept and reference for the post-processing parameters.
