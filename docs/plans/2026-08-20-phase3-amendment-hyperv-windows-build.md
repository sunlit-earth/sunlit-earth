# Plan Amendment: The Windows Image Builds Natively on Hyper-V

Amends `2026-08-19-phase3-vm-orchestration-plan.md`. Written 2026-08-20, after the events deviation 25 of that plan records: on a Windows host QEMU runs on WHPX, a WHPX guest with more than one vCPU does not survive the guest reset Windows Setup performs after copying its files, and each of the three workarounds is blocked by another constraint. The host decision that deviation left open is now made: on a Windows host, `cargo xtask vm build-image windows` installs Windows on Hyper-V, driven by the xtask directly.

Packer's `hyperv-iso` builder was considered for this and declined. Third-party keyboard boot orchestration is the mechanism that already failed once on this host and cost the most to diagnose (deviation 22); the plugin would add a `packer init` network dependency to a path that otherwise sheds one (deviation 20's failure class); and agreement between an HCL file and the Rust orchestrator is harder to test than agreement inside one crate, which is where the second validation round's defect class lived. What Packer still contributed on this target had already shrunk to CD creation (shelled out to oscdimg), the SSH wait, one provisioner, and a shutdown command, each of which the xtask already performs elsewhere. The research section's recorded fallback, moving image building into the xtask and reimplementing the boot orchestration Packer supplies, is what this amendment does, on the hypervisor where that orchestration is smallest.

## What changes, and what does not

The builder matrix now mirrors the runtime provider matrix:

| | Windows host | Linux host |
|---|---|---|
| Windows image | native Hyper-V (this amendment) | Packer + QEMU on KVM (unchanged) |
| Linux image | Packer + QEMU on WHPX (unchanged) | Packer + QEMU on KVM (unchanged) |

Decision 10's intent, one canonical install that both providers boot, stands. What flips on a Windows host is the conversion direction: the install produces a VHDX natively and `qemu-img convert` derives the qcow2 for the QEMU provider, instead of the reverse. On this host the primary runtime provider is Hyper-V, so the common path now boots the install in its native format, and the derived qcow2 serves only the `SUNLIT_EARTH_VM_PROVIDER=qemu` override cell.

The guest-side files are provider-agnostic and carry over unchanged. `Autounattend.xml` names no devices, and Hyper-V's synthetic SCSI disk and NIC have in-box Windows 11 drivers, which is exactly the property deviation 4 chose the QEMU devices for. `bootstrap.ps1`, `run-job.cmd`, `session-ready.cmd`, and `finalize.ps1` run inside the guest; `finalize.ps1`'s fallback-loader work (deviation 16) remains necessary on this path too, because the runtime VMs are created fresh with blank NVRAM. The runtime providers, the guest contract, the manifest with its expiry and currency model, and the Linux image are untouched. The Packer QEMU template stays what a Linux host uses to build the Windows image, unchanged in behavior.

## Key design decisions (continuing the plan's numbering)

15. **The xtask drives the install; no builder in the loop.** The build creates the VM, boots it, waits for SSH the way the guest contract already does, runs `finalize.ps1` over the existing SSH machinery, shuts the guest down with the same `shutdown /s /t 5 /f /d p:4:1` the template used, waits for the Off state, removes the VM keeping its disk, moves the VHDX into the image store, converts, and writes the manifest. The unattend CD is built by the xtask with oscdimg from the same files the HCL template's `cd_files` block names, plus the two generated entries (`authorized_keys` and the media marker); the file list lives in one Rust constant, and an agreement test reads the HCL and asserts both name the same files, the technique that caught the e1000/virtio divergence in the second validation round.

16. **The boot prompt is removed from the media rather than answered.** Windows installation media carries two UEFI boot images: `efi\microsoft\boot\efisys.bin`, which prints "Press any key to boot from CD or DVD", and `efisys_noprompt.bin`, which boots the installer immediately. The build repacks the downloaded ISO once with the noprompt image: mount with `Mount-DiskImage`, copy the tree out, dismount, then `oscdimg -m -o -u2 -udfver102 -bootdata:2#p0,e,b<tree>\boot\etfsboot.com#pEF,e,b<tree>\efi\microsoft\boot\efisys_noprompt.bin <tree> <out>`. A generation 2 VM boots the EFI entry; the BIOS entry is kept because it costs nothing. No prompt means no keypress, no keyboard injection, and none of deviation 22's machinery on this path. The repacked ISO is cached next to the original in the media directory and both are inventory: `vm status` lists them and `vm purge windows --iso` deletes them. The transient extraction tree lives in the build directory and is deleted on the way out.

    The mid-install reboots do not loop back into Setup because a generation 2 VM keeps its UEFI variable store: Setup's first phase writes a Windows Boot Manager entry and puts it first in the boot order, so every later boot goes to the disk. That persistence is exactly what the QEMU path lacked; deviation 16 exists because Packer's throwaway OVMF store discards what Setup writes. This is the one assumption in this amendment without a measurement behind it. It is observable minutes into the first live build (`Get-VMFirmware` on the build VM after the installer's first reboot), and the contingency if it proves wrong is to detach the install DVD once the output disk crosses the installer-writing threshold `build_watch` already defines, which Hyper-V permits on a running generation 2 VM.

    The Linux-host QEMU path keeps the prompting original ISO and the QMP keypress. How OVMF weighs QEMU's `-boot order=d` against NVRAM entries written mid-install is unmeasured firmware behavior, and this amendment does not touch a path it does not need to.

17. **The build VM is inventory from the moment it exists.** It carries the same per-target name the runtime guest uses (`sunlit-e2e-windows`), so `vm view`, `vm ssh`, `vm down`, and the one-VM-at-a-time rule all apply to a build without new plumbing, and a `RunState` with a new build start reason is written before `Start-VM` runs, so `vm status` shows a build in progress or a leftover from a crash and labels it as a build. The second validation round's rule, no failure may leave a guest running silently, applies to every path inside the build, not only after boot returns: every failure either destroys the build VM or prints exactly what is still running and how to reach it. Tearing down a build VM deletes the VM and its unfinished disk, since a half-built image is worth nothing, and never touches the image directory or the media.

18. **The watcher slims down to the signals Hyper-V has.** The heartbeat keeps `Trend` and swaps signal sources: `Get-VM` state instead of QMP status, the growing VHDX's file size instead of the qcow2's. The resume and give-up arms stay unwired on this path; they exist because WHPX guests wedge unrecoverably, which Hyper-V guests do not, and a build that goes nowhere is bounded by the install deadline (one constant, two hours to match the old `ssh_timeout`, calibrated by the first live run) plus a heartbeat that reports a machine that turned itself off. No keypress, no QMP, no screenshots in the first pass; the WMI thumbnail (`GetVirtualSystemThumbnailImage`) is recorded as the option if a live failure shows screens are worth having, and `vm view windows` reaches a running build VM meanwhile.

19. **The build stays unelevated and needs less than before.** Hyper-V Administrators membership (which `vm setup` grants) covers `New-VHD`, `New-VM`, `Start-VM`, and `Stop-VM`; `Mount-DiskImage` of an ISO and oscdimg need nothing. This path requires Hyper-V with the membership effective, oscdimg, qemu-img (it ships in the QEMU winget package setup already installs), and ssh with ssh-keygen. It does not require packer or qemu-system-x86_64, and it uses no network after the ISO download, so `packer init` and its firewall failure class (deviation 20) are gone from this target. `build-image`'s preflight asks only for what the chosen path uses; the doctor's tool list stays as it is, because the same host still builds the Linux image with Packer and QEMU.

20. **Secure Boot and the TPM are unchanged in this pass.** The unattend keeps the LabConfig bypasses and the runtime VMs keep Secure Boot off, because the QEMU override cell boots the same image without a vTPM, and changing the install's security posture in the same change as the installer would confound the first live run. A generation 2 build VM can supply a real vTPM (`Set-VMKeyProtector`, `Enable-VMTPM`) and Secure Boot with the Microsoft Windows template, which would let the undocumented bypass keys be dropped and retire the "bypass keys drift with ISO revisions" risk. Recorded as a follow-up with its own template-currency consequences, not done here.

## Cleanup

What the WHPX debugging left behind, and what happens to each piece. The rule: a workaround survives only if a reachable path still exercises it.

- **C1. `commands::build_image::qemu_cannot_install_windows` is removed**, with its call site and its test. Its trigger, the Windows target on a Windows host under WHPX, becomes unreachable once the dispatch routes that cell to Hyper-V. The measurements stay recorded in deviation 25 and in the condensed `vm-setup.md` note (C2); nothing in code keeps warning about a path that no longer exists.

- **C2. `docs/vm-setup.md` is rewritten where the WHPX story lives.** The callout "The Windows image cannot currently be built on a Windows host" is replaced by the builder matrix. The WHPX troubleshooting entries collapse into one, scoped to what can still hit the fault (booting the Windows guest through the QEMU provider override on a Windows host, where `-cpu max` remains load-bearing), and that entry gains the twenty-second recheck recipe: the exact throwaway-QEMU-plus-QMP `system_reset` commands, so a future QEMU release can be re-evaluated without an hour-long build and without taking this document's word for it.

- **C3. `CLAUDE.md`:** the bold "cannot be built on a Windows host" paragraph and the build-watch paragraph are rewritten for the new matrix; the command list and testing table stay accurate.

- **C4. `vm/windows/windows11.pkr.hcl`:** comments rescoped to the path that still uses it, a Linux host building the Windows image; the WHPX narrative trims to a pointer at deviation 25. No behavioral change: `-cpu max`, the QMP port, and the empty `boot_command` all stay, because the prompting ISO still needs the keypress under KVM and `-cpu max` is load-bearing wherever WHPX boots this guest.

- **C5. `vm/windows/scripts/finalize.ps1` has a latent path typo, found while preparing this amendment.** The fallback boot manager source reads `\EFI\Microsoft\Bootootmgfw.efi` where `\EFI\Microsoft\Boot\bootmgfw.efi` is meant. Latent rather than shipped, since no Windows image build has ever reached this script; if Setup leaves no fallback loader, the copy would look for a file that cannot exist and fail the build with "no boot manager on the EFI system partition". Fixed.

- **C6. What deliberately stays, each because a live path still needs it:** the QMP boot-key machinery and `build_watch`'s resume and give-up arms (the Linux-host QEMU build of the Windows image), `BUILD_QMP_PORT` and its template-agreement test (same path), `-cpu max` in the template and the runtime QEMU provider (any WHPX boot of this guest), and the OVMF firmware location (QEMU builds and the QEMU runtime provider). Anything only the dead WHPX install path used goes.

## Success criteria

1. On a Windows host, `cargo xtask vm build-image windows` produces the golden VHDX, the derived qcow2, and the manifest, entirely on Hyper-V: no Packer, no QEMU process, no network after the ISO download, no keypress, unattended start to finish, with a heartbeat line a minute.
2. Every failure after the build VM exists either removes it or names it. A leftover build VM shows in `vm status` and `vm down windows` removes it. No failure path touches an existing golden image or the cached media.
3. `cargo xtask vm smoke windows` and `cargo xtask e2e --target windows` pass against the built image, which makes the original plan's criterion 4 reachable on this host for the first time.
4. The Linux image build and the Linux-host build of the Windows image are unchanged: the existing command-line and template tests pass untouched.
5. The cleanup list is executed in full. No document still claims a Windows host cannot build the Windows image, and the WHPX knowledge with its recheck recipe is retained where C2 puts it.
6. New logic is tested in the crate's established style: every generated PowerShell script parses under PowerShell's own parser, the CD file list agrees with the HCL by a test that reads both, the oscdimg, VM-creation, and conversion command lines are pinned, and the build state file's lifecycle is covered including the crashed-build case.

## Implementation steps

- **Step A: media.** The noprompt repack in `store::windows_media` (mount, copy, dismount, oscdimg), cached and inventoried; `vm status` and `vm purge --iso` learn the second file; failures name the tool and the disk budget (the extraction is transient but peaks at roughly the ISO's size again).
- **Step B: the unattend CD.** An oscdimg-built ISO from the shared file list plus the generated `authorized_keys` and marker; the list is one Rust constant; the agreement test reads the HCL.
- **Step C: the build VM.** Creation script (generation 2, 4 vCPUs, 6 GB static memory, Default Switch, both DVDs attached, install DVD first in boot order, Secure Boot off, no checkpoints, no automatic start), `RunState` with a build reason written before `Start-VM`, teardown and status integration, and the no-silent-guest rule on every path.
- **Step D: orchestration.** Start, slim watcher, SSH wait against the install deadline, `finalize.ps1` over SSH, shutdown and wait for Off, remove the VM keeping the disk, move the VHDX into the store, convert to qcow2, write the manifest. The manifest's builder field records the mechanism, since `packer <version>` no longer applies on this path.
- **Step E: dispatch.** `build-image` picks the path from host and target; the preflight checks per path; C1 lands here.
- **Step F: cleanup and docs.** C2 to C5, `docs/roadmap.md`, and this amendment's Status / Results section.
- **Step G: gates and the live run.** `cargo test`, `cargo clippy --all-targets`, `cargo fmt --check`; then, if `vm doctor` says the host is ready, `vm build-image windows`, `vm smoke windows`, and `e2e --target windows`, recording times and pass counts in Status / Results. The first live run is calibration, not regression, per the plan's own rule.

## Risks and mitigations

- **The generation 2 boot-order assumption (decision 16).** Observable minutes into the first live build; the contingency is named there.
- **oscdimg repack subtleties** (UDF version, long names). The flags in decision 16 are the documented ones for Windows media; the first live run validates that the repacked ISO boots before anything downstream is trusted.
- **The install deadline is a guess until a live run calibrates it**, the same stance the plan took for boot timing in step 3.
- **The Hyper-V Administrators membership may not be in the running session's token** (it is logon-time, per the setup design). The doctor already reports this; the build must fail with that pointer rather than a raw access-denied.
- **Two ISOs double the media footprint** to roughly 13 GB; `vm status` shows it and `vm purge windows --iso` reclaims it.

## Rollback

Additive within the xtask: the QEMU build path stays intact behind the dispatch, so reverting is removing the new module and the dispatch arm. The guest files change only by comments and the C5 typo fix.

### Departures

Numbered on from the plan's own deviations, since they are deviations of the same work.

26. **A guest that answers on SSH is not a guest whose image is ready, and the amendment's step D would have raced it.** `bootstrap.ps1` starts sshd at its third step of nine, so `finalize.ps1` run at the first SSH answer can arrive before the two scheduled tasks it checks for exist, and would then report a missing task, which reads as a broken image rather than as an early question. The Packer path has the same race and never got far enough to find it. The build now waits for `sunlit-e2e-session-ready`, the last thing the bootstrap registers, with a test that reads `bootstrap.ps1` and asserts it is still the last one, since the probe means nothing otherwise. `schtasks` rather than the transcript, because the transcript's encoding is not something to depend on.

27. **The disk the install writes into lives in the run directory, not the build directory.** Decision 17 asks that tearing down a build VM delete the VM and its unfinished disk. Putting the disk where run state already lives makes that true with no new code: it is a run file, so `vm status` counts it, `vm down windows` deletes it, and the `Session::tear_down` path that clears a crashed run deletes it too. In the build directory it would have needed a fourth teardown rule, and a rule applied in one place and not everywhere is the second validation round's own lesson.

28. **The record is written before `New-VM`, not between `New-VM` and `Start-VM`.** Decision 17 asks for it before `Start-VM`. Earlier is strictly stronger and free, because everything in the record is known in advance: it closes the window in which a VM exists that nothing can find again, which is what a failed `write_state` after a successful `New-VM` would leave. A record naming a VM that was never created is the harmless direction, and `vm down` handles it.

29. **A build that is running is refused as something to clear away.** Every other guest the xtask boots holds nothing worth keeping, which is decision 14's whole lifecycle, and the boot path therefore clears whatever it finds recorded. An install partway through is the exception, so `vm::may_clear` refuses it and points at `vm down windows` for ending one deliberately. Without this a `vm up windows` in another terminal would silently discard an hour of install.

30. **A build VM that is not `Running` ends the build rather than only being reported.** Decision 18 leaves the resume and give-up arms unwired and bounds a build that goes nowhere by the install deadline plus a heartbeat. The heartbeat is there and says which state it saw, and the arms are still unwired. What is added is that the wait ends there: a Hyper-V guest stays `Running` through the reboots an install performs, so any other state means the install is over, and deviation 24's rule is that an answer already known is not waited out for two hours. The watcher gained a `Guest::Off` variant for this rather than reusing `Stopped`, so the resume arm's "starting it again" stays true of the only thing it describes, a wedged WHPX machine. One reading turned out to be too few to end a build on; departure 42 is why it is now two.

31. **The heartbeat prints the firmware's first boot entry, which decision 16 asks to be observable.** One extra line in the same `PowerShell` probe, printed only when it changes: `Drive DVD Drive` while the VM is as it was created, `File` once Windows Setup has written its own boot manager entry and put it first. That is the assumption decision 16 has no measurement for, made visible minutes into a build without the WMI thumbnail decision 18 files as the option for screens.

32. **C5 was not a path typo. It was a literal backspace byte.** `finalize.ps1` held `\EFI\Microsoft\Boot`, then 0x08, then `ootmgfw.efi`: a `\b` escape that something had interpreted, which a terminal renders by printing over the preceding character, which is why it reads as `Bootootmgfw.efi`. Fixed to `\EFI\Microsoft\Boot\bootmgfw.efi`. A parser cannot catch this, since inside a double-quoted string a backspace is a character like any other, so the `PowerShell` parse check passed the file for as long as it was broken. `no_guest_script_carries_a_control_character` is the check of the same kind as the failure, over every shipped guest script.

33. **The WHPX recheck recipe uses QEMU's human monitor rather than a QMP client.** C2 asks for the exact throwaway-QEMU-plus-QMP `system_reset` commands. `-monitor stdio` with `system_reset` and `info status` is the same two operations against the same monitor, and it needs no client at all, which is what makes it a twenty-second recheck for a person rather than a program. The note says so where it sits.

34. **Both ISOs are packed as UDF.** Not specified either way. `-u2 -udfver102` is what Windows installation media is, it has no name-length limits to fall foul of, and WinPE reads it, so the repack and the unattend CD use the same flags and differ only in the boot images.

35. **No `Hyper-V` query asks for a VM by name any more, and every one of them says whether it ran.** Found by the first live build, which installed Windows, finalized the image, shut the guest down, removed the VM, and then failed on the line that confirms the removal. `Get-VM -Name X` on a host with no such VM writes an error record, and `-ErrorAction SilentlyContinue` hides the record without undoing what it did to the exit code: `powershell.exe` still exits 1. So a VM that is gone read as "Hyper-V refused", which is the one distinction a teardown may not get wrong, and it was reachable in the existing code too: `vm down` on a target whose VM had already gone would have reported a problem and deleted nothing.

    Every query now lists the VMs and filters in the script, which is a question with an answer either way, and prints `QUERY=ok` to prove the listing itself worked. A host where the cmdlets fail throws before that line, so "there is no such VM" and "the cmdlets did not work" are told apart by what the script said rather than by an exit code that cannot carry it. This is the third time this crate has met that boundary: `powershell -EncodedCommand` collapsing a native command's exit code is deviation 19, and the rule it left, that what a script knows a script has to say, was applied there and not here.

    Carried to the four other places the same rule applies: the address query and the teardown guard in `provider::hyperv`, the build's probe, the `vmms` service lookup in the host probe (where a host without Hyper-V would have reported the whole probe as broken rather than the feature as absent), the group-membership check in `vm setup` (which would have reported a step that worked as one that failed), and the ISO dismount. The `Get-CimInstance` filters are left alone: a filter that matches nothing returns nothing without an error record.

36. **The golden image installs the Visual C++ runtime, so the build is not quite as network-free as criterion 1 says.** Found by the first `e2e --target windows`: every case answered with exit code `0xC0000135` and an empty log, which is `STATUS_DLL_NOT_FOUND` and prints nothing anywhere. A fresh Windows 11 build 26100 has `vcruntime140_clr0400.dll` and `msvcp140_clr0400.dll`, which belong to .NET, and neither of the plain names every Rust MSVC binary links dynamically. Installing `vc_redist.x64.exe` in the running guest by hand made the harness list all ten cases, which is what confirmed it before anything was changed.

    `bootstrap.ps1` now installs it at first logon and `finalize.ps1` checks for both DLLs, so a guest with no network fails the build instead of producing an image whose every test fails identically. Which of the two reports it depends on the path, and on the native one it is not the DLL check: sshd starts three steps before the download, so a guest that cannot reach the network answers on SSH and then never registers the last scheduled task, and the build fails in its bootstrap wait after twenty minutes, pointing at `bootstrap.log` inside the guest, which is where curl's own error is. The Packer path has no such wait and does fail in `finalize.ps1`. The comment in `bootstrap.ps1` says the DLL check is what catches it, which is true of the Packer path only; correcting a comment under `vm/windows/` marks the built image stale, so it is left for the next rebuild that has a reason of its own (see the validation round below). That is one network fetch from inside the guest, which criterion 1's "no network after the ISO download" did not allow for: the host still needs none, and the guest needs one, once, at image build time. It is also exactly what a user installing the product needs, so a guest that has it is a guest that looks like the machine under test. The alternative of carrying the redistributable on the unattend CD would keep the property, at the cost of a second cached download, a CD entry, and the HCL agreement that goes with it; it is recorded here rather than done.

    The product-side half of this finding is a roadmap item, not a test one: the app does not ship the runtime it needs either.

37. **A Hyper-V guest has no OpenGL, so the Windows job runs the app on Slint's software renderer.** The suite ran for the first time once departure 36 landed, and nine of its ten cases then failed on one line printed by the app itself: `Failed to initialize OpenGL driver: Could not locate glCreateShader symbol`, after which every windowed case timed out waiting for `SIGNAL:first_frame_rendered` having seen only `SIGNAL:ipc_listener_ready`. A Hyper-V guest's synthetic display adapter offers no OpenGL, and Windows ships no software implementation of it, so Slint's default winit renderer, which is femtovg over GL, has nothing to initialize. The plan's assumption that the guest's software adapter covers the rendering is true of wgpu and not of Slint: WARP is a Direct3D adapter and Slint asks for GL.

    The generated Windows job now sets `SLINT_BACKEND=winit-software` (`commands::e2e::WINDOWS_SLINT_BACKEND`), which is for Slint what WARP already is for wgpu in this guest: the CPU implementation, because there is no other. The two halves of the value are what Slint parses, and both matter: `winit` keeps the real event loop and the real window, which is what the windowed cases are about, and `software` names the renderer rather than letting it fall back to one. `renderer-software` is one of the `slint` crate's default features, so it is compiled in.

    In the job and not in the product, because it is a property of the machine the suite runs on rather than of the app, and not in the image either, because the environment is per run: this needed no rebuild. The Linux job gets nothing of the kind, and should not: Mesa is a software GL implementation and llvmpipe answers there, which is the same reason that guest has a wgpu story at all.

38. **The guest gets the texture assets, because one case tests the map rather than the renderer.** With the app starting, `test_render_and_exit` was the only case still failing, on a cause of its own: `Sahara: expected yellowish/sandy (R+G >> B), got [71, 144, 148]`. That case renders with `texture_index = 3`, the day and night blend, and samples six places on the globe by their colors. A guest with no `textures/` directory renders the procedural grid, which is a perfectly good picture of nothing in particular. Nothing had ever staged them and nothing had noticed, because `e2e --target linux` has not run either (the plan's step 5 verified its host half only), so this is a gap in the guest contract rather than in the native install.

    `guest::artifacts::stage` now copies the repository's `textures/` in beside the fixtures, and the job points `SUNLIT_EARTH_TEXTURES` at it, for both targets. The assets are JXL, so the whole directory is under 6 MiB, which is a rounding error next to the binaries already going in. Two guards, and both are about honesty rather than about space. The copy happens only when the day and night files are present and larger than a Git LFS pointer, because `textures/**` is LFS and a checkout without the objects leaves files that exist and cannot be decoded, and a failed decode leaves the slot in the state `Renderer::textures_ready` never reports ready, which is an open roadmap item and would hang a guest instead of failing a case. The job then omits the variable entirely, so a guest that has no textures renders the grid, which is exactly what `cargo e2e` does on a host in the same state. `the_staged_textures_are_the_ones_the_app_asks_for` reads `resolve_texture_paths` in the app and asserts both file names, since that function is the only thing connecting the two crates.

39. **`UserKnownHostsFile=NUL` wrote a file called `NUL`.** The first live run left a 755-byte file of that name in the repository root, and `cmd` cannot delete it without the `\\?\` prefix. `NUL` is the null device to Windows' own OpenSSH client and an ordinary file name to the MSYS2 build that Git for Windows ships, which is the `ssh` first on this host's PATH; `/dev/null` has the mirror problem. So the choice cannot be made from the host operating system at all, which is what `guest::ssh::null_device` was doing: it depends on which of two clients `ssh` resolves to, and nothing here knows that.

    The known-hosts file is now a real one beside the key pair the guests trust, at `<store>/ssh/known_hosts`. Both clients understand the path, and it is inside the store, so the option keeps the property it exists for, that the developer's own `~/.ssh/known_hosts` is never written to, and what accumulates is the xtask's own. `StrictHostKeyChecking=no` is what makes a fresh guest's host key workable without a prompt, and that has not changed. The value is double-quoted when the path contains a space, because `UserKnownHostsFile` takes a whitespace-separated list of files and `%LOCALAPPDATA%` carries the account name. `Provider::windows_host` went with it, since the null device was the only thing it decided.

40. **A build's teardown does not free an overlay.** `vm status` printed "frees the memory and the overlay" under every running guest, and under a build the file in question is the disk the install is writing, not a throwaway child of an image. The hint now says what ending a build actually costs, that the install starts over from the media, and that a golden image already in the store is untouched. Noticed during the first live build and fixed here, with the run case pinned alongside it so the two readings stay distinct.

41. **The failure that names what is still there begins before the VM exists, not after.** Decision 17's rule is that no failure may leave a guest running with nothing said, and the implementation drew that line after the create script: the call that ran it returned early, and only failures below it printed the "here is what is still there" text. The line was in the wrong place. `runner::powershell` prepends `$ErrorActionPreference = 'Stop'`, so the create script is one process that stops at its first error record, and every statement in it after `New-VM` leaves a registered VM behind: `Set-VM`, `Set-VMFirmware`, both `Add-VMDvdDrive` calls, and the script's own `throw` for installation media that would not attach. A failure there left an Off build VM and a message that named neither it nor a way to reach it.

    Creating the VM and installing into it are now one boundary, and the failure asks the hypervisor which of three things happened rather than assuming: registered, and the text is the one it always was; not registered, and it says the VM was not created and points only at the record; or no answer, and it says that, because "the cmdlets did not work" is not "there is nothing running". The same distinction departure 35 is about, applied to the one question that had been answered by assumption. The wording of a script failure went with it: "Hyper-V refused" is wrong for a `throw` of ours, and the message now carries what the script said rather than a guess at which half of it spoke.

42. **An install ends on two readings that the guest is not `Running`, not one.** Departure 30 made a non-`Running` guest end the build rather than only be reported, on the reasoning that a `Hyper-V` guest stays `Running` through the reboots an install performs. True of an install under way, and not of one that has just been asked to start: `Start-VM` returns before the guest is `Running` and `Get-VM` reports `Starting` in between, so the first reading of a healthy build could end it. Two readings a poll apart is the same shape as `build_watch`'s stopped-twice rule and for the same reason, that one sample of a state a machine passes through is not a verdict. The install deadline stays the real bound on a build that goes nowhere, and the heartbeat still says which state it saw. Unconfirmed as a live failure; the cost of being wrong about it is a whole install, and tolerating one transient costs ten seconds.

43. **The prompt-free media is tied to the download it was made from, and the download is fetched only when there is a repack to do.** The cached copy was reused on size alone, which is a check that it is an ISO rather than a check that it is *this* ISO: a re-downloaded original at the next Windows revision would have left the previous revision's repack in place, and the install would have installed that. A repack now writes a record beside the copy, `windows11-enterprise-eval-noprompt.source.json`, holding the original's size and CRC-32, and a build checks it. Reading 6.6 GB to do so is a few seconds against a quarter of an hour, and the checksum is only read when the sizes already agree, since a size that disagrees has answered the question.

    The order of the two questions changed with it, which is the other half of the same finding. `ensure_iso` used to run first, so deleting the original triggered a 6.6 GB download to remake a file that was already on disk and is what actually boots. Now the copy is asked about first and the download is fetched only for a repack. A copy whose original is gone is used as it stands, with a line saying nothing checked it; `vm purge windows --iso` takes both files and the record together, which is how a fresh download is asked for.

44. **A build clears the known-hosts file, because a rebuild is what changes a guest's host key.** Departure 39 said nothing reads that file. `ssh` does. `StrictHostKeyChecking=no` accepts a key it has never seen without asking and says nothing about accepting a key it has seen change, so a changed key prints the remote-host-identification-changed warning on every connection while public-key authentication carries on working. A guest's host keys are generated during the image build and live on the golden disk, so every overlay of one image answers with the same key and the entries are right for that image's life; a rebuild is the event that invalidates them. `build_image::forget_host_keys` deletes the file at the end of a build on both paths, which is noise nobody would otherwise ever get around to.

45. **A media purge ends a build first.** Deviation 23 of the plan says a scope that touches a guest's own files stops the guest and media does not, because no booted guest still holds the ISO. A build VM does: both DVDs are attached for the whole install. So `vm purge windows --iso` during a build was deleting a file Windows had open, which Windows refuses and the plan reports, leaving a purge that has to be run twice for a reason nothing explained. `Scope::needs_the_vm_stopped` now takes the recorded start reason, and media plus a build stops the guest. It is the only case where what the guest is changes the answer, which is why the reason is passed in rather than the scope being widened.

Decision 20 is unchanged as specified: the unattend keeps its LabConfig bypasses, the build VM has no vTPM, and Secure Boot stays off.

### The validation round

The work above was reviewed on 2026-08-20, after the live runs, by a round whose job was to attack it. It read the working tree rather than this document, and found two major defects and twelve minor ones. Every major and every minor is fixed except two comment edits under `vm/windows/`, which are declined below with the reason. The findings that changed documented behavior are departures 41 to 45; the rest are here. It also raised two questions it could not settle by reading: whether `Get-VM` reports a transient state in the moment after `Start-VM` returns, and whether `Get-Volume` writes an error record in the window before a mounted image has a drive letter. Both are now handled without the answer, the first by departure 42 and the second by dismounting whenever the mount script ran at all.

**The two majors** are departure 41, a failure boundary drawn one statement too late, and the repack's cleanup:

- *The repack's failure paths did not clean up what step A claims they do.* Two of them. The extraction tree, which is the size of the media, was deleted on the oscdimg-failed branch and on success but not on the two early returns above them, so media that could not be mounted, or that carried no `efisys_noprompt.bin`, left 6.6 GiB behind while this document said otherwise. The steps that can fail now sit behind one function and the tree is deleted after it whatever it returned, which is one place rather than three. And the dismount ran only when the mount script had succeeded: with `Stop` in front of it that script ends at its first error record, and an error anywhere after `Mount-DiskImage` leaves the image attached and holding a drive letter, with the retry loop that waits for that letter on the far side of the mount. The dismount is now asked for whenever the mount script ran at all, which `dismount_script` was already written to tolerate. Whether `Get-Volume` really errors in the window before the letter arrives is still unmeasured, and the fix does not depend on the answer. A staged ISO from a failed pack goes too, rather than being left for the next run to find.
