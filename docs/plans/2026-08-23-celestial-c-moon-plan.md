# Plan: Celestial C, the Moon

Phase C of [2026-08-23-celestial-bodies-research.md](2026-08-23-celestial-bodies-research.md), section 6. Builds on phase A's `SkyState` ([2026-08-23-celestial-a-stars-plan.md](2026-08-23-celestial-a-stars-plan.md)) and on phase B's sky-lens placement in `scene::sun_occlusion` ([2026-08-23-celestial-b-sun-plan.md](2026-08-23-celestial-b-sun-plan.md)); both have landed.

## Summary

The Moon as a textured sphere at its true position, distance, and orientation, projected through phase A's stereographic sky lens: position from `Astronomy_GeoMoon`, phase falling out of lighting the sphere with the existing sun direction, orientation from `Astronomy_RotationAxis`, surface from the NASA CGI Moon Kit at 1024x512 through the existing async texture slot machinery. The far plane does not change. Three artistic controls: a brightness that doubles as the switch, a size factor that scales only the radius, and an earthshine floor. The Moon also joins the Sun's occlusion arithmetic, so the glare fades behind a Moon that covers the disk instead of burning on around it. Includes one load-bearing refactor: the texture slot layout stops punning the clouds slot against the blend-mode combobox index, because the Moon is the first new file-backed slot since that pun was written.

## Stakes Classification

Medium. The slot refactor touches the mapping every texture mode flows through, so a mistake shows as the wrong texture in a mode, a wedged "Loading..." state, or a mailbox index panic; all covered by existing engine tests plus new ones, none destructive. The rest is additive rendering plus one new LFS asset, and nothing outside the Moon's own draw changes at all now that the far plane stays where it is.

## Research

Recorded from code reconnaissance on 2026-08-23, references to the tree at that date.

The slot layout is the hazard. Slots are grid 0, day 1, night 2, clouds 3; `CLOUDS_SLOT = 3` shares its value with `BLEND_MODE_INDEX = 3`, which is a combobox index, and the code comment documents the pun (`renderer/mod.rs:39-53`); `slot_of` maps combobox index to slot by identity (`renderer/mod.rs:594-597`), which works only because the first three modes equal their slots and blend is special-cased before use (`renderer/mod.rs:397-406`, `texture_routing`). The engine computes `slot_count = texture_paths.len() + 2` (grid plus clouds, `engine/mod.rs:513`) and asserts the injected mailbox agrees (`engine/mod.rs:513-520`); production passes two paths (`resolve_texture_paths`, `sunlit-app/src/main.rs:228`), the default config passes `vec![None, None]` (`engine/mod.rs:175`). `SLOT_LABELS` names four slots for the memory report (`renderer/mod.rs:62-67`). `purge_file_backed_slots` purges slots 1 through `texture_paths.len()` on a resolution switch (`textures.rs:138`); `textures_ready`/`textures_pending` special-case blend mode and otherwise index by slot (`renderer/mod.rs:397-434`); clouds are deliberately excluded from readiness. The far plane is a literal 100.0 in `projection_matrix` (`camera.rs:238-240`); the worst-case eye-to-Moon distance is about 144 Earth radii (research document, section 6.1). The budget is `private_bytes_budget` = cold start + headroom + resident textures by resolution (`memory.rs:79-83`). Texture prep applies a horizontal flip and a quarter shift (`texture_loader::orient`, `assets/texture_loader.rs:61-65`), so a new equirectangular source goes through the same offline orientation as the Earth maps and reads back through the same loader. `Astronomy_GeoMoon` returns geocentric EQJ in AU, `Astronomy_RotationAxis` returns the pole's J2000 RA/Dec, a spin angle for the prime meridian, and the pole unit vector (`astronomy.h:1180-1185, 1323`, struct at `astronomy.h:1085-1093`); `Astronomy_Libration` provides distance and apparent diameter for tests. The CGI Moon Kit facts (LROC WAC natural color, equirectangular centered on the near side, Mean Earth frame, 2048x1024 at 3.2 MB in the 2019 set, public domain with an SVS credit) are in the research document. Uniform growth has room: `Uniforms` is 208 bytes with a size assertion (`uniforms.rs:42`).

Read again on 2026-08-26, after phase B. `Uniforms` is 400 bytes (`uniforms.rs:65`), holding the sky view, `world_from_eqj`, the viewport, the pan, the star and sun parameters, and the four sun scalars the CPU derives per frame. The sun work moved the slot layout's lines without touching it: `BLEND_MODE_INDEX` and `CLOUDS_SLOT` at `renderer/mod.rs:43-49`, `SLOT_LABELS` at `62-67`, `textures_ready`/`textures_pending` at `403-440`, `slot_of` at `652`, the engine's `slot_count` at `engine/mod.rs:514`. The draw order is stars and planets, the Sun's disk, the Earth, clouds, Rayleigh, the two nightglow shells, and the Sun's glare (`render_pass.rs:161-168`); `encode_and_submit` takes `Option<Stars>` and `Option<Sun>` selected by `Stars::select` and `Sun::select` (`render_pass.rs:344-394`), one per switch, and the comment on the disk draw already names a Moon as the next thing to cover it. The two sun pipelines come from one function with no vertex buffers, additive blend, no depth write and `CompareFunction::Always` (`gpu_setup.rs:331-388`). The disk is drawn in the sky group with those settings, so a Moon that has to cover it must draw after it and opaque: an additive disk drawn over a Moon would show through it. `scene::sun_occlusion` is where the sky lens is spelled out on the CPU: `sky_lens_edge_radius`, `sky_lens_disc` (the image of a cone about a view direction, as a circle in pixels), `globe_screen_circle`, `visibility` (a disk against two concentric circles by the circle-circle lens area) and `place_sun`, which floors the disk's radius at `SUN_MIN_DISK_RADIUS_PIXELS = 1.6` times `pixel_scale`. The shader mirrors the first two as `sky_lens_edge_radius` and `sun_disc`, carries the inverse as `sky_lens_direction`, and `the_shader_and_the_cpu_agree_on_the_two_shared_rules` in `tests/render_pipeline.rs` reads the two shared rules back off the GPU. `vs_star` still spells the forward projection inline (`sphere.wgsl:160-193`). The glare's fade is `sun_visible`, and it is computed against the globe alone.

## Key Design Decisions

1. **The slot pun ends before the Moon lands: file-backed slots stay contiguous, clouds move to the end, and mode-to-slot becomes an explicit map.** New layout: grid 0, day 1, night 2, moon 3, clouds last at `texture_paths.len() + 1`. `CLOUDS_SLOT` stops being a constant equal to 3 and is derived; `slot_of`'s identity mapping is replaced by a function that maps the four combobox modes to their slots and is unit-tested against every mode, and `BLEND_MODE_INDEX` remains purely a combobox concept that never indexes `texture_slots`. `SLOT_LABELS` and the default `texture_paths` grow together with the engine's slot-count assertion. This is a prelude commit sequence with all existing engine and texture tests green before any moon rendering exists, because it is the step with real regression surface.

2. **The Moon's placement, scale, and orientation are a model matrix, and the sky lens turns it into pixels.** *(Revised after phase A; see Revisions 1. Revised after phase B; see Revisions after phase B, 2 and 3.)* Position: `GeoMoon` in AU times 23,455 (Earth radii per AU) through `R_world_from_eqj`. Rotation: the IAU axis from `RotationAxis` (pole plus prime meridian spin) composed with `R_world_from_eqj`. Scale: 0.2724 times the `moon_size` parameter. Those three are a model matrix in the shared uniform buffer, as first planned. What changed is what happens next: `vs_moon` takes each mesh vertex to world space through that matrix, subtracts the eye position, and maps the resulting direction through the stereographic sky lens, exactly as `vs_star` maps a catalog direction. That projection is spelled inline in `vs_star` today, and the Moon is its second consumer, so it is factored into one WGSL function both call, the way phase B factored `output_pixel_scale` and `sky_lens_edge_radius` the moment the Sun became their second consumer. It is a model matrix followed by the sky lens, not a second MVP.

   The radius the model matrix carries is floored the way the Sun's disk is. `place_sun` draws the disk no smaller than `SUN_MIN_DISK_RADIUS_PIXELS` times the density ramp, because at the default sky field of view the true disk is under a pixel on a small preview. The Moon subtends the same half degree, so without the same floor the two bodies that are the same size in the sky would be different sizes on screen wherever the floor is active, which is every preview at the default: on a 1080p preview the Sun 3.2 pixels across and the Moon about 2, and a Moon crossing the Sun failing to cover a disk it covers in reality. So the CPU images the Moon's cone through `sky_lens_disc`, with half-angle `asin(0.2724 * moon_size / eye_to_moon_distance)`, and where that radius falls below the floor it inflates the model's scale by the ratio. That is the same operation `moon_size` performs and leaves direction, distance and parallax untouched. Inflating on the CPU side means the shader reads one matrix and there is no second spelling of the floor to pin across the language boundary; the constant is renamed to say it belongs to both bodies.

   Taking the direction from the eye rather than from the geocenter is what keeps the two things true scale placement was for. Parallax is exact at every camera distance, including the distances beyond the Moon's own orbit the zoom control reaches, and so is apparent size, which grows as the camera approaches the Moon and shrinks as it recedes. Neither needs a calculation of its own; both fall out of measuring the direction from where the camera is. Unit tests as first planned: distance within 55 to 64 Earth radii across a year sweep, one or two positions against JPL Horizons values, and the sub-Earth longitude of the oriented sphere within libration bounds of zero (the tidal-lock sanity check that catches a transposed rotation or a flipped spin sign).

3. **The far plane does not change.** *(Revised after phase A; see Revisions 1.)* The Moon reaches the screen as a direction, so nothing in the scene is farther away than the Earth and the literal 100 in `projection_matrix` is still correct. This decision existed to make a worst-case eye-to-Moon distance of 144 fit inside the frustum, and there is no frustum in the Moon's path any more. Dropping it takes the one step in this phase with repo-wide blast radius out of it: no reference image can move because of the Moon's projection. Whether one moves because the Moon is in it is criterion 5's check.

4. **The moon draws opaque and back-face culled, with the sky, after the stars and the Sun's disk and before the Earth, and it joins the Sun's visibility arithmetic so the glare fades behind it.** *(Revised after phase A; see Revisions 2. Revised after phase B; see Revisions after phase B, 1.)* Occlusion is the composite's rule rather than depth testing: everything celestial is drawn first and the opaque globe covers whatever falls inside its painted disc, which is how phase A hides a star behind the Earth and is the only rule that produces a coherent picture when the globe is drawn four and a half times larger than the sky lens's image of its own silhouette. A depth comparison between the two lenses would mean nothing, so the Moon does not make one; the pipeline writes no depth and its self-occlusion comes from back-face culling instead, which is exact on a convex sphere and needs nothing else. Clouds and the atmosphere shells then sit unambiguously in front of the Moon, which is correct for a Moon anywhere beyond the limb.

   Drawing after the disk is what makes a Moon crossing the Sun cover its body, and that half of the solar eclipse geometry is indeed free. The other half is not. Phase B fades every glare term by `sun_visible`, a fraction `scene::sun_occlusion::visibility` measures against the painted globe and nothing else, so with draw order alone a Moon in front of the Sun would hide the white disk and leave the bloom, the corona needles and the halo burning around a dark Moon, which is worse than no eclipse. So the Moon becomes a second occluder in that function: its screen circle comes from the same `sky_lens_disc` the Sun's does, at the floored radius decision 2 settles, and the visible fraction is the disk's area outside both circles. The Moon and the Sun are both in the sky lens, so unlike the globe comparison this one carries no mixed-lens caveat and agrees with an ephemeris. Where both occluders overlap the disk at once, an eclipse at the limb, the two hidden areas combine as the larger of the two rather than as their exact union, which errs toward more glare and is exact everywhere else; the transit fraction is untouched, since the atmosphere band belongs to the globe. The Moon occludes only while it is drawn: a Moon whose texture is absent or whose brightness is zero hides nothing, since a glare fading behind something invisible is the same incoherence in the other direction. What fading the glare buys is coherence. The solar corona a total eclipse reveals, and the shadow on the Earth, are section 6.5's deferred work and not this phase's.

   The fragment shader is unchanged in substance: sample the color texture, apply a hard terminator (narrow smoothstep on n dot l with the existing `sun_dir`), an earthshine floor, and a fixed brightness; no water, no fresnel, no night texture. The mesh is the existing UV sphere.

   What this gives up is the one configuration depth testing bought: a camera beyond the Moon's orbit, where the Moon is genuinely in front of the Earth and will be painted over anyway. The composite has no way to show that correctly, since the globe it would have to be in front of is drawn in a different lens from the sky the Moon is in. It is reachable (the camera goes to 80 Earth radii and the Moon sits between 56 and 64), so it is a stated limitation rather than an unreachable corner.

5. **The asset is the 2019 kit's 1024x512, prepared offline like the Earth maps.** *(Revised after phase A; see Revisions 3.)* Downloaded once by a maintainer, oriented (the same flip and quarter-shift convention `texture_loader::orient` expects, verified by the landmark check below), encoded to JXL with cjxl (the repo decodes JXL but does not encode it, so prep stays external, as it was for the Earth sources), committed to `textures/` under LFS with provenance and the SVS credit line recorded beside it and in the About window's attribution list. The size follows from what the sky lens can put on screen. The disk is 13 pixels across at the default field of view on a 4K render, and 260 at the far end of both controls together, the narrowest 60 degree sky at the eight times size decision 6 now offers. A visible hemisphere spans 180 degrees of longitude, so 260 pixels asks for 1.4 screen pixels per degree against the 2.8 texels per degree a 1024-wide map carries. 2048 was sized for a Moon that would have been 57 pixels at 1x under the Earth's own lens, and would now be four times the memory (11.2 MiB against 2.8 MiB of VRAM with mips) for resolution nothing on screen can ask for. One framing does out-ask it, and it is worth naming rather than rounding away: the camera at 80 Earth radii with the Moon on the same side is 24 radii from it, where the disk reaches 648 pixels and 1024 falls to about 0.8 texels per pixel. Three controls at their extremes at once, soft rather than broken; if a screenshot disagrees, 2048 is a one-file swap. At 1024 wide it sits at or below every resolution cap, so the halving cache never touches it. The Moon is an overlay like clouds: excluded from `textures_ready`/`textures_pending`, absent without the file, never delaying a wallpaper export; unlike clouds its slot is file-backed, so a resolution switch purges and reloads it, which at 1024 is cheap and correct.

6. **Three scene parameters, full digest treatment: `moon_brightness`, `moon_size` and `moon_earthshine`.** *(Revised after phase B; see Revisions after phase B, 4.)* Size 1.0 to 8.0, default 1.0 (realistic by default; the research document records the reasoning for scaling radius rather than distance). The range doubles because the sky lens made the honest Moon four and a half times smaller than the range was chosen against: 13 pixels on a 4K wallpaper and about 6 on a 1080p preview. It is worth saying in the same breath that `moon_size` is the dishonest way to get a bigger Moon and phase A already shipped the honest one, since narrowing the sky field of view magnifies the Moon and the stars around it together; the slider is there for the user who wants the Moon larger than its neighbors, not as the recommended route. Earthshine as a small floor, default subtly nonzero so a new moon does not vanish. `moon_brightness` is the fixed brightness decision 4's fragment shader applies, made a slider with a default of 1.0, and zero is the switch: `Moon::select` returns `None` at zero exactly as `Sun::select` does for `sun_glow` and `Stars::select` for `star_intensity`. Every other sky layer switches off that way, and every phase B engine case is one engine and one `UpdateParams`, an off frame compared against an on frame, which is the shape the Moon's engine cases take too; without a switch the only off frame would be an engine started without the texture path, a different engine rather than a different frame. All three in the Celestial group, config, digest rows, uniforms. A missing asset and the existing texture modes are unaffected by any of them.

7. **The budget grows by a constant.** `private_bytes_budget` gains the moon texture's resident footprint (about 2.8 MiB plus decode transients, per decision 5) as a resolution-independent term; the budget tests are re-measured and re-pinned per the phase 4.1 convention.

## Success Criteria

1. The slot refactor lands first and green: every texture mode renders what it did before, blend mode included, the mailbox assertion still fires on a mismatched seam, and the mode-to-slot map has exhaustive unit coverage.
2. Position and orientation are pinned: the year-sweep distance test, at least one Horizons cross-check, and the sub-Earth longitude test all pass on all three platforms.
3. Phase is right by construction and by measurement: the GPU invariant test's lit-pixel fraction tracks `Astronomy_Illumination`'s illuminated fraction within tolerance at three pinned datetimes (crescent, quarter, gibbous). The test narrows the sky field of view and raises `moon_size` so the disk is large enough for a pixel fraction to mean anything; at the defaults it is 13 pixels across and the measurement would be quantization noise.
4. A human check against a planetarium view confirms the visible face and crescent orientation once at a pinned datetime, at a framing chosen so the disk is big enough to judge; a moon-crescent golden at that framing then pins it forever. Its teeth are measured the way phase B measured its two: the reference framing is rendered with the Moon switched off and the comparison has to fail. A reference that passes without the feature is a picture, not a test.
5. Existing goldens are checked, not predicted to stand. Phase B's plan predicted that a default-on Sun would leave the set alone, and four references gained a Sun inside tolerance, which is the worst outcome: they went on passing while no longer showing what the renderer draws. The Moon is somewhere in the sky at the pinned datetime and a default-on Moon may land in a night-side frame, where at 140 degrees of sky it is two or three pixels and no tolerance will notice. So every reference is re-rendered with the Moon on and compared byte for byte against the committed one, on both local adapters, and any that differ at all are regenerated once with the cause recorded. The new golden is stable across three consecutive runs on the local adapters.
6. Without the LFS object the app runs exactly as today plus stars and the Sun: no moon, no error, no delayed export; the e2e staging carries the new texture along with the existing ones.
7. Budget tests re-pinned; `cargo test`, `cargo clippy --all-targets`, `cargo fmt --check` green on Windows and in WSL; CLAUDE.md and `docs/roadmap.md` updated.
8. The glare fades behind the Moon. Unit tests pin `visibility` with a Moon circle covering the Sun's disc (fraction zero), beside it (unchanged), and half over it (the lens area), and with the globe and the Moon both over the disk (the larger hidden area wins), all without a GPU. An engine case in the shape of `sun_off_and_on` shows `moon_brightness` at zero and a missing texture producing the same frame, and a Moon on the sky painting pixels that only got brighter or were covered.

## Risks and Mitigations

- The slot refactor is the concentrated regression risk, which is why it is Step 1, isolated, exhaustively unit-tested, and lands with no behavior change to hide behind.
- Texture orientation has four plausible wrong answers (flip, shift, spin sign, pole sign). The sub-Earth longitude test catches the rotation half analytically; the landmark check against a planetarium view catches the texture-prep half once, and the golden keeps it caught.
- The composite hides the Moon wherever it overlaps the painted globe, including places the Moon is not actually behind the Earth. That is phase A's rule applied consistently, and a Moon a few degrees off the limb will disappear earlier than an ephemeris says it should. It is the same trade the stars already make, at a size where it is more noticeable; if a screenshot makes it look wrong, the finding is about the mixed lens and not about this phase. The Sun already shows it: the user's review of phase B found that the composite does not read well while the disk is partly behind the globe or barely clearing it, and that is an open roadmap item to be revisited once phases C and D have landed. The Moon's crossing is the hard cut of an opaque draw under the painted globe, with no fade at all. This phase does not invent a limb treatment of its own: whatever the Sun's rework decides about the limb should apply to both bodies at once, and the Moon golden is framed clear of the limb so it does not have to be regenerated when that lands.
- The Moon's screen circle is used twice on the CPU, once to floor the model's scale and once to fade the glare, and the shader sees neither: it reads the inflated matrix and the fraction. That keeps both uses to one spelling on one side of the language boundary, which is the situation phase B's two shared rules did not have and had to pin with a GPU readback. What can still drift is the drawn Moon against the circle, which the phase test of criterion 3 covers indirectly, since a lit-pixel fraction measured on a disk the circle mis-sized would miss its tolerance.
- A camera beyond the Moon's orbit shows no Moon in front of the Earth, per decision 4. Reachable but rare, and stated rather than fixed.
- `RotationAxis` correctness for the Moon is trusted from the library's IAU model; even a few degrees of error is invisible on a disk of a dozen pixels, and the tests bound gross errors.
- A fixture moon texture is needed so engine tests do not depend on the LFS asset, following the existing skip-with-reason convention for tests that need real assets.

## Revisions after phase A

Phase A landed with a design that moved during implementation: celestial content is drawn through a stereographic sky lens with its own field of view (60 to 180 degrees, default 140) rather than through the Earth camera's 20 degree perspective lens. That is recorded in phase A's own Departures. This plan was written before that change and never updated for it, and read against the shipped tree on 2026-08-24 it was the phase most affected: the Moon was to be an ordinary depth-tested object in the Earth's lens, which is now the one place it cannot be.

1. **The Moon moves onto the sky lens, and the far plane change goes with it.** Under a 20 degree lens the Moon is inside the frame only when it sits within 10 degrees of the view axis, which is under one percent of the sky, so a Moon drawn there would almost never be visible; and when it was, it would be four and a half times larger than the sky lens puts the stars around it, and in the wrong place among them. Neither is acceptable for the phase whose whole point is that the Moon is up there. So `vs_moon` projects eye-relative vertex directions through the sky lens, which keeps parallax and apparent size exact for free and leaves nothing in the scene farther away than the Earth. The far plane stays at 100, and decision 3 is now a decision not to touch it.

2. **Occlusion is draw order, not depth.** A depth comparison between two different lenses means nothing, so the Moon draws with the sky, before the Earth, and the painted globe covers it exactly as it covers a star. Back-face culling replaces depth testing for the Moon's own front-to-back. The configuration this gives up is a camera beyond the Moon's orbit, where the Moon is really in front of the Earth; the composite cannot show that, and decision 4 says so rather than leaving it to be discovered.

3. **The asset halves twice.** 2048x1024 was sized against a 57-pixel disk under the Earth's lens. Through the sky lens the largest disk any ordinary framing produces is 260 pixels, which 1024x512 serves at two texels per screen pixel for a quarter of the memory. Only the camera-beyond-the-Moon framing at both controls' extremes out-asks it, and decision 5 records that rather than sizing the whole asset for it.

4. **The size slider's range doubles, to 1.0 through 8.0.** Same cause: the honest Moon is now 13 pixels on a 4K wallpaper. The default stays at 1.0, and decision 6 records that narrowing the sky field of view is the better way to get a bigger Moon, because it magnifies the sky with it.

Unchanged by any of this: decision 1's slot refactor, which is the step with the real regression surface and has nothing to do with projection; the astronomy (position, IAU orientation, libration); the phase falling out of the shared sun direction; the earthshine floor; and the overlay semantics that keep a missing asset from delaying anything.

## Revisions after phase B

Phase B landed on 2026-08-26 and this plan was read against it the same day. Four things follow, and the user's review of the Sun adds a note to the risks.

1. **The glare needs the Moon as an occluder, or the free eclipse is half an eclipse.** The Sun is two draws. Its disk is in the sky group, where the Moon covers it by order; its glare is a last draw faded by `sun_visible`, which `scene::sun_occlusion::visibility` measures against the painted globe and nothing else. A Moon crossing the Sun would therefore hide the white disk and leave the bloom, the needles and the halo burning around a dark Moon. Decision 4 puts the Moon into that function as a second circle from the same `sky_lens_disc`, exact against the Sun because both are in one lens, and only while the Moon is drawn.

2. **The Moon takes the Sun's pixel floor.** `place_sun` floors the disk at 1.6 pixels of radius at 1080p times the density ramp. The Moon subtends the same half degree and would otherwise be the smaller of two equal bodies wherever the floor is active, which is every preview at the default sky. Decision 2 inflates the model's scale on the CPU by the operation `moon_size` already performs, so the shader reads one matrix and no rule is spelled twice.

3. **The sky lens's forward projection gets one WGSL spelling.** `vs_star` spells it inline and `vs_moon` would have been the second copy. Phase B's departure 7 is the precedent: `output_pixel_scale` and `sky_lens_edge_radius` were factored the moment the Sun became their second consumer. Phase D's ray reconstruction is a consumer of the same chain's inverse, which `sky_lens_direction` already is, so after this phase both directions of the lens exist once each.

4. **A third parameter, `moon_brightness`, and zero is the switch.** Every sky layer switches off at zero through a `select` that returns `None`, and every phase B engine case is one engine, one `UpdateParams`, an off frame against an on frame. A Moon with no switch would have no off frame but an engine started without its texture. The research document's sections 6.2 and 9 both list a brightness control; this plan had dropped it and has it back.

Carried over from phase B without a decision to make: its goldens taught that a reference can pass while the picture it pins has lost a feature, so criterion 4 measures the new golden's teeth by rendering without the Moon, and criterion 5 stops predicting that the existing set will stand and checks it byte for byte instead. `Uniforms` is 400 bytes now rather than 208, with the same size assertion; the model matrix and three scalars this phase adds leave it far below any limit that matters.

Unchanged by any of this: the slot refactor, the astronomy, the asset and its size, the earthshine floor, the overlay semantics, and the far plane staying put.

## Departures

Recorded during implementation on 2026-08-26 and 2026-08-27, in the order the plan met reality.

1. **The parameter plumbing landed with the pipeline rather than in step 5.** `SceneParams` cannot gain a field without `AppConfig` gaining one, and `write_uniforms` cannot place the Moon without both, so `moon_brightness`, `moon_size` and `moon_earthshine` went through config, `SceneParams`, the digest, the digest table and the Slint bridge in their own commit before the shader work. Step 5 kept what it is actually for: the round-trip and default tests in `config.rs` and `slint_ui.rs`, the engine cases, the phase test and the budget. Phase B's departure 5 is the same departure for the same reason, which suggests the step order in these plans should stop separating the two.

2. **The asset is encoded by ImageMagick's libjxl rather than by cjxl, and it is a downscale of the 2k TIFF rather than the published 1k JPEG.** This machine has libjxl 0.11.1 through ImageMagick and no `cjxl` binary, and the plan named the tool rather than the format. What the two commands do, and what they measured, is in `textures/PROVENANCE.md`: `magick lroc_color_poles_2k.tif -filter Box -resize 1024x512!` is the average of each 2x2 block, which is the filter `downsample_2x` uses for the mip chain, so the asset is the 2k map's first mip level; `magick moon_1024.png -quality 99 lroc_color_poles_1k.jxl` decodes through the app's own `jxl-oxide` path to a mean channel difference of 0.41 of 255 with a worst pixel off by 5, at 285 KB. Quality 95 (0.95 and 9, 169 KB) and 90 (1.63 and 19, 108 KB) were measured too; 99 was taken because the file is small either way. The published 1024x512 product is a JPEG, and taking the 2k TIFF instead is what keeps JPEG artifacts out of the one asset a close framing can magnify.

3. **The moon golden compares a 96 pixel window rather than the whole frame, because a full frame cannot see the Moon at all.** The largest the disk can be in any coherent framing is 31 pixels across: the Moon subtends half a degree, `moon_size` stops at 8, the sky lens stops at 60 degrees, and the geometry allows nothing more (an eye far from the Earth on the Moon's own side puts the Moon behind the camera, and an eye beyond the Moon's orbit is the configuration decision 4 gives up). Measured on that framing at 512 by 256: switching the Moon off costs a mean channel difference of 0.2194 with 0.12 percent of pixels outliers, against the suite's 2.00 and 1.00 percent. So a full-frame reference would have passed with the feature deleted, which is exactly the failure phase B's goldens taught. On the 96 pixel window the same loss is a mean of 3.1196 with 1.7144 percent outliers, and it fails on both counts; `moon_size` at 1 instead of 8 is 3.1718 and 1.7470 percent, and `moon_brightness` at 3 instead of 1 is 2.5916 and 2.2461 percent. What the window leaves out is the globe, which the nine other references pin. The mechanism is `Window` in `tests/golden.rs`, and `every_golden_case_is_distinguishable` skips pairs whose sizes differ, since two references of different sizes cannot be confused.

4. **The golden engine got a generated moon fixture, and `check_golden` had to learn to wait for it.** Without a texture in the Moon's slot the Moon is not drawn, and criterion 5's byte-for-byte check over the existing set would have been vacuous: every case would have been compared with the feature switched off in all but name. So the shared engine's `texture_paths` names a fixture written into `CARGO_TARGET_TMPDIR` at startup, which also means every reference in the suite is now rendered with a Moon somewhere in the sky. That introduced a test-order hazard the suite has not had before: the fixture's decode takes a few tens of milliseconds, so the first case would render without the Moon and the rest with it. `check_golden` therefore polls the memory report until the renderer owns `moon_texture`, which is the only channel that answers the question, because `TexturesReady` deliberately excludes overlays. The wait is skipped when `moon_brightness` is zero, since nothing then spawns the load and the poll would run to its timeout.

5. **Criterion 5's check came back clean on both adapters, and the reason is worth writing down rather than being lucky.** Every one of the nine existing references was regenerated with the Moon on, on `warp` and on `lavapipe`, and every file came back byte identical; on `warp` the comparison was also measured before regenerating and read a mean of 0.0000 for all nine. The cause is not that the Moon is small: at the instant the whole suite pins (2026 day 172, hour 12, and hour 0 for `nightglow`) the Moon is outside the frame in all nine framings. At 512 by 256 its disc centre is at x = 627 for `default` and `rayleigh`, x = -29 for `nightglow`, x = 674 for `close_up`, x = -155 for the three star cases, x = -758 for `sun_over_the_night_side` and x = -847 for `sun_grazing_the_limb`. A framing or datetime change to any of those cases can therefore move its reference for a reason that has nothing to do with the case, which is worth knowing before the next one is edited.

6. **Two engine cases the plan did not ask for, both because a measurement showed the golden could not see the thing.** Dropping the earthshine floor entirely changes the golden's window by a mean of 0.6447 with no outliers at all, which is inside the tolerance, so `earthshine_lifts_the_unlit_face_only` pins it where a count of pixels needs no tolerance: the frames with and without it differ only inside the disk, and only upward. And the illuminated fraction of criterion 3 cannot see a terminator rotated in the plane of the screen, which is the one thing the human check of criterion 4 is looking at, so `the_lit_limb_faces_the_sun` measures the brightness centroid of the disk against the Sun's own screen position: 31.3 pixels from the centre and 2.6 degrees off the direction of the light.

7. **The phase measurement was wrong the first time, and the fault was in the measurement rather than in the Moon.** Counting lit pixels in a box around the disc read 0.5536 against the ephemeris's 0.4439 at the quarter phase, because at that framing the painted globe reaches inside the box and its grid is bright. Masking to a circle at 1.1 times the disc radius, which is the shape the disk actually is, gives 0.4461. The tenth of margin is deliberate: it is what lets a disk drawn larger than the circle the CPU placed show up as too much lit area instead of being cropped out of the measurement. The three instants then read 0.2089 against 0.2272, 0.4461 against 0.4439, and 0.8619 against 0.8450, so the worst disagreement is 0.018 against the 0.04 the case allows. The crescent's is the largest because the camera's own nine Earth radii of parallax move the phase by about 0.02 there, and the instants were chosen so that displacement is nearly across the Sun's direction rather than along it.

8. **Decisions the plan left open, recorded here because they are now conventions.** The mesh's local frame against a body-fixed one is `scene::moon::mesh_from_body`, the same permutation the Earth's own map goes through, which is what lets one texture orientation serve both bodies; `the_meshs_prime_meridian_faces_the_earth` and `the_meshs_north_pole_is_the_moons_north_pole` are what hold it. The earthshine default is 0.05, which on the reviewed renders leaves the unlit face a few levels above the sky rather than invisible or grey. The Moon's terminator width is 0.03 in units of n dot l, as narrow as it can be without aliasing, because the Moon has no atmosphere to scatter light past the shadow line. And `textures/*.md` is exempted from the LFS filter in `.gitattributes`, so the provenance note beside the assets is readable in the repository rather than behind a pointer.

9. **Criterion 2's Horizons cross-check is a solar eclipse instead.** The plan asked for "one or two positions against JPL Horizons values", which is what phase A did for Jupiter, and this run had no access to Horizons. What replaced it is a fact of the same kind and a stronger one about the Moon in particular: at 2024-04-08 18:17 UTC, greatest eclipse of the total solar eclipse over North America, the geocentric directions to the Moon and to the Sun are 0.347 degrees apart, which `the_moon_covers_the_sun_at_the_2024_total_eclipse` holds to under 0.6. A position wrong by a degree in any component does not reproduce that, and the date is checkable by anyone. Three more independent checks came with it, all against models inside the library that this code does not use: the distance against `Astronomy_Libration`'s kilometres, the sub-Earth point against its libration angles (worst disagreement 0.0276 degrees over four years of six-hourly samples), and the pole against the Moon's known 1.54 degree Cassini tilt to the ecliptic.

10. **A Moon at the antipode of the view axis is refused rather than drawn, and phase A's revision 2 named one of two configurations rather than the only one.** `Moon::select` gated on the brightness and the bind group, which are properties of the configuration, and nothing gated on the frame: `place_moon` leaves the disc empty where the body's cone reaches the lens's antipode, and the draw went in anyway. The camera that produces it is the eye on the line from the Earth to the Moon at any zoom short of the orbit, which is a globe drag away, and the picture is not a subtle one. Review round 1 found it by reading and reproduced it independently; measured here at the framing the Moon's own engine cases use, with the eye put exactly on that line, 110,303 of the frame's 131,072 pixels differ from the frame with the Moon switched off, opaque moon-textured triangles across five sixths of it. The gate now sits in `write_uniforms`, which is the one place that has the placement, and it hands back the narrowed selection rather than a second answer for the caller to combine: the function is `#[must_use]` and both callers name it, so a third caller that ignored the return would be a build failure under CI's `-D warnings` rather than the same bug again. `a_moon_at_the_view_antipode_draws_nothing` is that camera, derived from `SkyState`'s own moon position rather than hardcoded, and it asserts the empty disc before it renders anything, so a framing that stopped being the antipode fails instead of passing vacuously. `vs_moon` deliberately does not carry the offscreen guard `vs_star` has, and this is the reason: a sprite's four vertices share one direction, so one verdict moves all four, while a mesh judged per vertex keeps every triangle that straddles the verdict, which is the artifact rather than a defense against it. Every point of a sphere lies inside its own tangent cone, so the disc the CPU already measured is exactly the condition under which the projection has a finite answer for every vertex; the gate is sufficient and a second spelling of the antipode rule in WGSL would be neither. What the phase A revision said about a camera beyond the Moon's orbit stands, and it is now one of two framings the composite cannot show rather than the only one: that one is given up and painted over, this one is refused. CLAUDE.md says both. One unrelated line came with it, since the same function decides it: the pixel floor's `disc.radius > 1.0e-4` clause was a constant with no reasoning, and it is now `> 0.0`, which is the only radius the inflation ratio cannot be taken against; anything smaller than the old threshold now gets the floor it is entitled to, and an inflated radius that reaches the eye is refused by `disc_for` as it always was.

11. **The Moon's half of the glare's fade was wired but not measured, in both of the places it passes through.** Review round 1 found that `moon_disc` could be replaced with `None` at the uniform encoder and the whole suite would stay green on both adapters: the three `visibility` cases call that function directly, every `place_sun` case passed no Moon, and every Moon engine case had the Sun switched off. Two tests close it, one per crossing. `place_sun_measures_the_sun_against_the_moon_it_was_given` is the cheap half: the Sun thirty degrees off the view axis at eighty Earth radii, where the painted globe is a few degrees wide and nothing but the Moon can hide the disk, measured once with no Moon and once with a circle twice the disk's radius on its center; dropping `inputs.moon_disc` inside `place_sun` fails it. `a_moon_over_the_sun_fades_the_glare_around_it` is the end-to-end half, and it is the one the encoder's own line answers to. It renders the greatest eclipse of 2024-04-08 at 18:17 UTC, the instant departure 9 already leans on, with the view axis seven degrees off the Sun: that is the window where the Sun's image clears the painted globe, so there is a glare to fade, and where the camera's own parallax, nine Earth radii across a sixty-nine radius line of sight, still leaves the Sun inside the Moon's disc. Measured at 1024 by 256: the Moon's disc is 63.9 pixels across and the Sun's image is 14.3 pixels from its center, well inside it. The assertion is on pixels more than one and a half disc radii out, which the Moon's own mesh cannot reach because the disc is the image of the cone every vertex of it is inside, so nothing but `sun_visible` can have moved them: 195,391 of them dim and none brighten. Replace the encoder's `moon_disc` with `None` and the count is 0.

12. **The app asks how large a texture file is rather than whether it exists, which is what criterion 6 was actually claiming.** Review round 1 ran the criterion in a checkout whose `textures/**` are still LFS pointers and found one `error!` line per pointer: `resolve_texture_paths` filtered on `exists()`, a pointer exists, and the decode of a couple of hundred bytes of text fails. The Moon inherited that from the two Earth maps, which have had it since before this phase, and nothing else follows from it: no panic, no delayed export, the slot's path is cleared and the picture is the one that checkout was always going to draw. It was still the wrong question to ask, and the right one is three lines: `std::fs::metadata(p).is_ok_and(|meta| meta.len() >= TEXTURE_MIN_BYTES)`, with the threshold at the 64 KiB `xtask`'s guest staging and `tests/engine.rs`'s `real_textures` already use against the same three files, both for the same reason and both saying so. Fixed for all three rather than for the Moon, since a fix that left the Earth maps logging errors would be a rule with two spellings and one exception. `a_git_lfs_pointer_is_not_a_texture_path` is the first unit test in `main.rs`: a directory holding one file of exactly the threshold and one pointer, where the asset is named, the pointer is not, and the file that is not there is not either. It fails on the old `exists()` filter. What did not change is the log line, which still reports the three resolved paths and now reports `None` for a pointer: an incomplete checkout is a developer's state, the app has always been quiet about a missing texture, and this makes the two states quiet in the same way rather than adding a warning for one of them.

## Rollback Strategy

Feature branch. Step 1 is intentionally separable: if later steps revert, the slot refactor can stay, since it is a correctness improvement on its own. New config fields are serde-ignored by older binaries, and the LFS asset is inert data. There is no far plane constant to revert any more, which is one fewer global thing this phase can leave behind.
