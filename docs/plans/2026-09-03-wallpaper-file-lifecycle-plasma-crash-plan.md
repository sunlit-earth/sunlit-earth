# Plan: The wallpaper file lifecycle crashes plasmashell (2026-09-03)

## Summary

On a real two-screen KDE Plasma session, the unattended wallpaper refresh crashes plasmashell and the desktop falls back to its default blue wallpaper. The cause is in how a publish writes its PNGs, not in how it addresses the screens: a publish streams each image into its final path so a reader can catch a half-written file, and it reuses a fixed set of file names so a file the shell is watching is later deleted and recreated at the same path. Both are safe on the desktops the suite tests, which read the file once at set time, and neither is safe on Plasma, which keeps a file watch on the current wallpaper. The fix is to write every image atomically and to never hand the desktop a path that was ever used before, then sweep the old files once the switch has happened.

This is a defect in the merged multi-monitor feature (`2026-08-30-multi-monitor-plan.md`), reachable on any single-screen Plasma session too and made frequent by the auto-refresh. It is separate work from the display-change-events amendment; that amendment adds a third reason to publish, which is why this should land first or alongside it.

## What was observed

On the development host on 2026-09-03: KDE Plasma 6 on X11, two screens (a 3440x1440 primary and a 2880x1800 panel), a release build of `sunlit-earth` running in the background in `every-screen` mode at the High tier and 8192 textures, auto-refresh on at a two-minute interval. The user reported plasmashell crashing and the secondary screen turning blue. The user's journal, read afterward, carries the sequence in full:

- `15:53:07 plasmashell: StaticImageComponent.qml: QML Image: Error decoding: file:///home/.../SunlitEarth/wallpaper-...png`, one second before `15:53:08 sunlit-earth: SIGNAL:wallpaper_set`. Plasma decoded a file the publish had not finished writing.
- `15:54:12 plasmashell: ASSERT: "path == m_source.toLocalFile()" in wallpapers/image/plugin/utils/mediaproxy.cpp, line 207`, then `KCrash`. That assertion is in Plasma's `MediaProxy`, which puts a `KDirWatch` on the current wallpaper file so a changed image reloads. It fires when a watched path reports a change while it is no longer the proxy's current source, which is exactly what removing and recreating an older slot's file produces. This distro ships the plugin with assertions live, so a violated one takes the shell down.
- `15:54:19` and again after a second crash at `15:54:53`: plasmashell restarts and logs `The backend got an unknown wallpaper provider type. The wallpaper will now fall back to the default.` The default is Plasma's blue wallpaper, which is what the secondary screen showed.

The implementer's run on the display-change-events branch was ruled out: none of its commands touched this host's display, `xrandr`, `dbus-send`, or any desktop tool, and the branch has never run here. The 15:54 timing lined up with a VM booting and nothing else.

Two facts about Plasma were confirmed rather than assumed. The live containment file `plasma-org.kde.plasma.desktop-appletsrc` held, after the crash, both desktop containments on `org.kde.image` with `file://` URIs into the SunlitEarth directory, one image per screen, so the addressing half of the KDE row works on a real two-head session, which the roadmap listed as unobserved. And the crash is the file half, not the addressing half.

## Root cause

Two independent defects in `crates/sunlit-core/src/wallpaper.rs`, both in the file lifecycle, both invisible to the current tests because the test desktops read a wallpaper once when it is set and never watch it.

1. **A publish streams each image into its live destination path.** `Publication::write` calls `std::fs::File::create(&path)` on the final name and runs the PNG encoder straight into it. For the duration of the encode, a full-resolution 8K-derived PNG on a software-free path, the destination is a truncated file. A desktop that reads it in that window, which Plasma does the moment the setter points it there and also whenever its watch fires, decodes a partial image. This is the `Error decoding` line.

2. **A publish reuses two fixed name sets and rewrites one in place.** The output alternates between two slots, `wallpaper-1-*.png` and `wallpaper-2-*.png` (`SLOTS`, `slot_name`). `begin_publication` takes the slot the desktop is not showing, and its first act is `remove_file` on every file of that slot before `write` recreates them at the same paths. The alternation's own doc comment explains why two slots exist: a desktop keys the wallpaper on the path it was handed, so a new image must arrive on a path the desktop is not already showing. What the comment does not account for is a desktop that keeps a watch on a path after it has moved on from it. Plasma does. When a screen was left alone in a `OneScreen` publish, or simply while `KDirWatch` is between the change and the reload, a `MediaProxy` still watches a path that `begin_publication` then deletes and rewrites, and the reload asserts because that path is no longer the proxy's source.

The two combine: even the currently shown slot is unsafe to read mid-write, and the not-shown slot is unsafe to rewrite at all.

3. **The unit tests write to the real wallpaper directory.** `wallpaper.rs`'s `publishing_alternates_slots_and_empties_the_one_it_takes` calls `wallpaper_dir()`, which resolves to `dirs::data_local_dir()/SunlitEarth`, the live directory, and publishes a 4x4 red and a 2x2 blue image into it, sweeping what was there. On any developer's KDE machine a plain `cargo test` therefore overwrites the current wallpaper with a 2x2 image and, through the same file watch as defect 2, drops the desktop to its default. Observed on 2026-09-03: a validation-round `cargo test` clobbered the user's freshly set wallpaper about fifteen seconds after the app closed, with the app not running, and the desktop went blue. This is a worse blast radius than defect 2, because it hits anyone who runs the test suite on this desktop, not only someone running the app, and it is the one to fix first.

## Why it surfaced now, and where else it reaches

- The multi-monitor feature is the first per-screen KDE writer. Before it, `plasma-apply-wallpaperimage` set every containment from one file and the app wrote one image; the churn was lower and single-screen.
- It is not KDE-only in principle. Any desktop that watches the wallpaper file rather than reading it once is exposed. GNOME's shell and XFCE read the value and load the file at set time and do not keep a watch, which is why the suite has never seen this.
- The auto-refresh is what makes it unattended and repeated. It is off by default and was two minutes here, so every two minutes a full-resolution publish rewrote a watched file. At the High tier the encode is long enough to widen the partial-read window.
- The display-change-events amendment adds a publish on every layout change. That is more publishes through this same lifecycle, so the amendment raises the exposure and is a reason to fix this first.

## Proposed solution

Change the file lifecycle so that no reader ever sees a partial file and no path a desktop was handed is ever written again. The addressing, the mode logic, the sink contract, the per-desktop reach table and the KDE script do not change.

1. **Write every image atomically.** Encode into a temporary file in the same directory, then `std::fs::rename` it onto the destination. A rename within one directory replaces the destination as one operation on both platforms this ships to, so a reader sees either the whole old file or the whole new one and never a truncated one. The temporary name carries the process id and is swept on failure, which is the discipline `assets::texture_cache` already uses for the same reason. The Windows single-image path through `SystemParametersInfoW` copies the bytes itself and needs the atomicity less, but writing every image the same way keeps one code path.

2. **Never reuse a path.** Replace the two fixed slots with a per-publish generation: a directory or name segment that is unique to each publish, so every image a publish writes is at a path no earlier publish used. This satisfies the alternation's actual requirement, a path the desktop is not already showing, by construction and for every publish rather than every other one, and it means a file under a live watch is never modified in place. The `PUBLISHED` record, `published_wallpaper_files` and the read-back that carries the alternation across a restart move from "which of two slots is newer" to "which generation is newest", which the modification-time logic already expresses.

3. **Sweep after the switch, and keep one generation back.** Delete a generation's files only once a newer generation has been applied, and keep the immediately previous generation rather than deleting it, because a screen left alone in `OneScreen` mode still references it and Plasma still watches it. Deleting a file a watch is on is its own `KDirWatch` event; keeping the last two generations and sweeping older ones leaves at most one spare layout on disk, which is the same order of residue the two-slot scheme already tolerated. The sweep runs after the setter reports success, never before.

4. **No test writes to the real wallpaper directory.** `wallpaper_dir()` gains a test-only override so the publishing tests run against a temporary directory, the way `set_wallpaper_rejects_empty_file` already builds one under `std::env::temp_dir()`. The cleanest form is a per-test directory injected into the code under test rather than a process-wide env var, but at minimum every test that publishes points `wallpaper_dir()` somewhere disposable. A guard test asserts that a publish under test does not resolve to `dirs::data_local_dir()`, so a later test that forgets the isolation fails in CI rather than on a developer's desktop. Until the code carries the fix, running the suite with `XDG_DATA_HOME` set to a scratch directory isolates it on Linux, because `dirs::data_local_dir()` honors that variable; that is the interim guard the orchestration runs use and it is not a substitute for the code change.

The net change to the contract is small: `begin_publication` stops clearing a slot up front and starts a fresh generation; `write` writes through a temp file; `commit` records the generation and triggers the sweep of generations older than the previous one; `published_wallpaper_files` reports the newest generation's files; and the publishing tests no longer touch the real directory. Everything above `wallpaper.rs` is unchanged.

## What must not change

- A single-monitor session on a landscape screen still comes out byte-identical to today in every mode. The pixels do not move; only the path they are written to and the way they are written to it move. The identity tests in `tests/engine.rs` compare pixels, not paths, so they hold.
- The alternation guarantee the two-slot comment states, that a publish hands the desktop a path it is not already showing, holds more strongly, since every publish is a new path.
- The e2e alternation assertion, that two publishes in a row write different paths per screen, holds, since generations differ by construction.
- Windows behavior is unchanged in effect. The single-image path still hands the shell a path that changes between publishes.

## Testing

Most of this is decided in `wallpaper.rs`'s own unit tests, which run on every platform with no desktop:

- **Atomicity, observably.** The destination path never exists as a short file: after a `write`, the file at the destination is either absent or a complete, decodable PNG, never a partial one. A test that writes a known image and asserts the destination decodes to the right dimensions covers the encode-into-temp-then-rename path; a companion asserts no `*.tmp`-style leftover remains in the directory after a successful publish, and that a failed encode leaves neither a partial destination nor a stray temp.
- **No path is ever reused.** Two publishes in a row, then a third, write three disjoint sets of paths; no path from publish N appears in publish N+1. This is the assertion that would have caught the in-place rewrite.
- **The sweep keeps one generation back and no more.** After three publishes the directory holds the files of the last two generations and nothing older; a `OneScreen` publish that leaves a screen alone does not sweep the generation that screen still references; the legacy single-image names are still swept.
- **The read-back still carries the alternation across a restart.** `published_wallpaper_files` with an empty in-process record returns the newest generation, so a fresh process publishes a generation the desktop is not showing, exactly as the restart case needs today.
- **The existing slot tests** are rewritten to the generation model rather than deleted, so the property each pinned, the alternation and the sweep of what a layout dropped, is still pinned.

What only a real Plasma session proves is that the crash is gone, and it cannot be an assertion in this suite: the Hyper-V and QEMU guests run GNOME, XFCE, Cinnamon and KDE, but the crash needs Plasma's `MediaProxy` watch and a rapid re-publish, which the guest cases do not exercise. So the guest KDE case is extended to publish several times in a row with no pause and assert the shell is still answering `dbus-send` afterward, which is the cheap proxy for "it did not crash", and the definitive check stays the hand check on a two-screen Plasma machine: run the two-minute auto-refresh for several cycles and confirm the shell survives and both screens keep the rendered wallpaper. `docs/roadmap.md` already carries the KDE read-back as an open item; this adds the survival check beside it.

## Implementation steps

1. **The lifecycle.** `crates/sunlit-core/src/wallpaper.rs`: the temp-then-rename in `Publication::write`, the generation replacing `SLOTS`, the sweep in `commit`, and `published_wallpaper_files`/`newest_slot` moved to the generation model. The unit tests above. Verify: `cargo unit`, `cargo clippy --all-targets`.
0. **Stop the tests clobbering the real directory (do first).** The test-only `wallpaper_dir()` override and the guard test from defect 3, so the rest of this work, and every future `cargo test` on a KDE machine, cannot overwrite the live wallpaper. Small and independent of the lifecycle rewrite, so it lands before anything else. Verify: `cargo unit`, then confirm `~/.local/share/SunlitEarth` is untouched by a run.
2. **The e2e survival case.** `crates/sunlit-app/tests/e2e.rs`: extend the KDE two-screen case to re-publish several times and assert the shell still answers. Verify: `cargo xtask e2e --target linux --screens 2`, and `--target windows` for the single-image path.
3. **Docs.** `docs/rendering.md` or `docs/platforms.md` gets the file lifecycle and why it is atomic and generational; `docs/roadmap.md` records the crash fixed and keeps the KDE read-back open. The two-slot reasoning in the code comment is replaced, not merely appended to.

## Not in this

- **The KDE config read-back.** Asking Plasma through `evaluateScript`/`readConfig` what it actually holds is the assertion the roadmap already wants and is worth having, but it is a separate reliability improvement and does not fix the crash.
- **Throttling or coalescing publishes.** Lowering the default interval or skipping a publish when the scene has not moved would reduce the churn, but a correct lifecycle should not need it, and a slower refresh is a worse product, not a fix.
- **A KDirWatch-friendly signal to Plasma.** Telling Plasma to reload without a file watch is Plasma-specific and unnecessary once no watched file is ever rewritten.

## Open questions

1. Does keeping one generation back suffice for `OneScreen` mode, where a screen can reference an arbitrarily old generation because it is never repainted? If a person leaves one screen alone for many publishes, its file is generations old and would be swept. The safe answer is to never sweep a generation any current containment still references, which on KDE the read-back could confirm; the conservative interim is to keep the anchor's own last-painted generation for every screen the current mode does not paint. Decide against the read-back work.
2. Is `std::fs::rename` over an existing destination atomic on the Windows path in practice, including when the shell has the old file open? It replaces on both platforms, but a reader holding the old handle on Windows is worth confirming on the Hyper-V guest before relying on it there.
3. Should the whole publish move under one generation directory (`SunlitEarth/wallpaper/<gen>/screen-N.png`) rather than a generation segment in the name? A directory makes the sweep a single `remove_dir_all` and the read-back a single listing, at the cost of the flat layout tests and the e2e helper assume today.

## Departures

1. **The generation is a directory, not a name segment.** Open question 3 asked whether a publish should move under one directory (`SunlitEarth/gen-<id>/<suffix>.png`) rather than carry a generation segment in a flat name. It is a directory. The sweep is then one `remove_dir_all` per retired generation and the read-back is one directory listing, and each publish is fully isolated: nothing in a live generation shares a name with anything a later one writes. The cost the question named, that the flat-layout tests and the e2e helpers assume a flat directory, did not materialize: those helpers key on `file_name()` and the whole absolute path (`assert_the_files_match_the_layout`, `assert_the_desktop_holds_the_wallpaper`, `placement_of`), none of which cares whether the file sits in the wallpaper directory or a child of it. `desktop.rs` and its `Placement` are untouched. The generation id is `gen-<millis>-<pid>-<counter>`: the millisecond orders generations across a restart the way the slot scheme's modification times did, and the pid and counter make it unique so no path is ever reused.

2. **The sweep runs in `commit`, before the setter, not after it.** The plan's point 3 says "the sweep runs after the setter reports success, never before", while the net-change paragraph says `commit` triggers it; `commit` is called before the setter on both platforms. The reconciliation is that keeping the immediately previous generation makes the timing irrelevant to safety. Until the setter points the desktop at the generation just committed, the desktop is still showing the previous one, which the sweep keeps; everything the sweep removes is older than that and referenced by nothing the desktop currently holds. A setter that then fails leaves the desktop on the previous generation, still on disk. Sweeping in `commit` keeps one lifecycle choke point that both the Windows and Linux setters share, rather than spreading a post-setter sweep call across two platform paths. The before/after distinction only ever mattered for the current generation, which the sweep never removes.

3. **`wallpaper_dir()`'s test override is a `cfg(test)` scratch with a panic-guard, not an env var or an injected directory.** The plan wanted every publishing test off the real directory and a guard that makes a forgetful future test "fail in CI rather than on a developer's desktop". A process-wide env var and threading a directory parameter through `begin_publication`/`published_wallpaper_files` (which the sink and the e2e binary call) were both weighed. What landed: under `cfg(test)`, `wallpaper_dir()` returns a thread-local scratch directory and *panics* when none is set, so any unit test that publishes without a `tests::Scratch` fails loudly instead of writing to the live directory. The process-global publish record forces the publishing tests to serialize, which a `Scratch` does by holding a mutex for its lifetime; it also resets the record so each test starts as a fresh process would. The override is compiled only into `sunlit-core`'s own unit tests: the e2e binary links `sunlit-core` without `cfg(test)`, so it still resolves the real directory, which is what a throwaway guest wants.

4. **Generation recency breaks a modification-time tie by the publish counter.** The plan said the read-back moves from "which of two slots is newer" to "which generation is newest", "which the modification-time logic already expresses". Two publishes inside one filesystem clock tick can carry the same newest-file modification time, which would make the read-back and the sweep order nondeterministic. So the ordering key is `(newest-file mtime, generation counter)`: the counter is the trailing field of the directory name and is monotonic within a process, so it decides only ties an equal modification time would otherwise leave to `read_dir` order. This is what lets the rapid-republish tests be deterministic without sleeping.

5. **The atomicity failure test forces a failed *rename*, not a failed *encode*.** The plan's testing section asks that "a failed encode leaves neither a partial destination nor a stray temp". The `image` crate's PNG encoder panics on a malformed pixel buffer rather than returning an error, and a malformed buffer never reaches this code (the sink hands well-formed frames and `CountingSink` even asserts it), so that is not a representative failure. The test instead stands a directory where the finished PNG would go, so the encode into the temporary succeeds and the rename onto the destination fails; it then asserts the temporary was removed and the destination was not clobbered with a partial file, which is the same guarantee the plan wanted from the same cleanup path.

6. **Keeping the last two generations is the interim answer to open question 1.** A screen left alone across many publishes in `OneScreen` mode references a generation older than the one kept, and the sweep would eventually remove the file under its watch. The plan settled on keeping the immediately previous generation as the conservative interim and deferred the full answer (never sweep a generation any current containment references, confirmed through the KDE read-back) to the read-back work that is explicitly out of scope. This is implemented as written: the sweep keeps the current and previous generations, and `docs/roadmap.md` records the residual `OneScreen`-across-many-publishes edge beside the KDE read-back item.

7. **The legacy flat files are swept one cycle late, not on the first generation publish.** Departure 2 argued the sweep is safe at `commit` because the previous generation, which the desktop is still showing, is kept. That argument covers generation directories but not the flat `wallpaper-1-0.png`/`wallpaper-2-0.png` an older build wrote: on a desktop upgraded from that build, one of those is the live wallpaper, and Plasma may still be watching it in the window between this first generation publish's `commit` and its setter. Deleting it there is exactly the watched-file deletion this fix exists to prevent, and it hits the development host on its first publish after upgrade. So the legacy files are treated as the previous "generation" for one cycle: `commit` sweeps them only when a prior generation already exists (`previous.is_some()`), which is the second generation publish, by which point a generation has been set and the desktop is no longer on a legacy file. `the_first_publish_keeps_the_legacy_files_the_desktop_may_still_show` pins both halves.

8. **The panic-guard is pinned by a `#[should_panic]` test.** The `cfg(test)` guard in `wallpaper_dir()` that refuses to resolve to the real data directory had no test asserting it actually panics, so a refactor that silently reintroduced the `data_dir_wallpaper_path` fallback under test would have re-exposed the developer's desktop without failing anything. `resolving_the_wallpaper_directory_without_a_scratch_refuses` calls `wallpaper_dir()` with no scratch set and asserts the panic, so that regression fails loudly instead.
