# Platform support

Windows is the platform that ships. Linux builds, tests, renders headlessly, and since phase 5 sets a wallpaper and exits cleanly when its session ends. macOS has the same platform code as the other two since the macOS branch, and none of it has run on a Mac: nobody working on this project owns one, so every macOS claim below carries the evidence it rests on and nothing claims more.

Three tiers of evidence, and the macOS column names one per row:

- **compiled** — it builds and its unit tests pass on `macos-latest`. That is a real check of the pure functions and of every type and call, and it is no check at all of what the API does to a desktop.
- **runner** — it ran in the hosted runner's own session: the `render` smoke step of `ci.yml`, or the `build-and-e2e` mode of `macos-build.yml`. A runner's session is not a desktop somebody is looking at, so this is evidence that a call succeeds and not that a picture changed, except where a row says it was seen over VNC in an interactive session: that is the runner's own paravirtual screens, not a Mac's panel, and no Retina or mixed-scale question is answered there.
- **tester** — somebody ran it on a real Mac and reported back. This is the only tier that says a wallpaper appeared on a screen.

A row moves up only when the evidence exists. That is the retrospective's rule about not pretending: a setter that has never painted a real desktop is not "yes" here.

The macOS CI job is not green. As of 2026-09-07 one engine case fails there, `stars::zero_star_intensity_leaves_catalog_pixels_at_the_clear_color`, on a single pixel the paravirtual Metal device does not reproduce when the star draw enters the pass; `testing.md` has the measurement and the revision written for it, which no macOS run has seen. Every other target passes. Nothing in the table below rests on that case, but a reader should not take "compiled" to mean the job came back green.

The `render` row is the one at the middle tier, and what put it there is the smoke step of <https://github.com/sunlit-earth/sunlit-earth/actions/runs/34063631672>: the binary the suite built, run on a `macos-latest` runner with no textures and no clouds, wrote a 640x360 PNG whose IHDR the step reads back. It is the first image this project has produced on a Mac. The release bundles are verified the same way and by the same two renders, on the runner that built them, in <https://github.com/sunlit-earth/sunlit-earth/actions/runs/34063658604>.

The rows at the runner tier since 2026-09-23 rest on `macos-build.yml` in `build-and-e2e` mode: the whole suite on Intel with one screen in <https://github.com/sunlit-earth/sunlit-earth/actions/runs/35850483773>, and on Apple Silicon with one screen in <https://github.com/sunlit-earth/sunlit-earth/actions/runs/35849074116> and with two in <https://github.com/sunlit-earth/sunlit-earth/actions/runs/35859134554>, the second screen being the virtual one `testing.md` describes. The settings window, the status item and both display modes that span or repeat were then driven by hand over VNC in sessions of the same workflow. `test_render_and_exit` fails only on Apple Silicon, with an exit RSS of 1775 to 2075 MB against its 1000 MB bound; the cause is not known.

Per-OS implementations live in four places, each behind a `cfg` and each documented where it sits:

- `memory::snapshot`: `GetProcessMemoryInfo`, `/proc/self/{status,smaps_rollup}`, `task_info(TASK_VM_INFO)`. Same `MemorySnapshot`, same CSV, so every memory assertion in the suite is live on all three.
- `engine::wallpaper_sink::SystemWallpaper`: Win32 on Windows, a per-desktop command on Linux (see Setting a wallpaper on Linux below), `NSWorkspace` on macOS (see Setting a wallpaper on macOS below). The refusal a platform with no setter would get is still there, and nothing this tree builds for reaches it any more.
- `config::is_position_on_screen`: Win32 monitor enumeration on Windows, the `xrandr` outputs on Linux, and the CoreGraphics displays in points on macOS, which give the same shape of answer. Points on macOS and not pixels, because that is the space winit reports a window position in and this check compares a saved position against it. Where there is no display to ask, and on any platform with no query, a coordinate-range sanity check against X11's INT16 window-position range, which is the coarse portable half of the same question. A run with no display still loads a config, so refusing every saved position there would move a window on the next run that has one.
- `session_end::install`: the Win32 listener on Windows and a SIGTERM listener on both Unixes, each on its own thread, each quitting the event loop once however many times it is told. What SIGTERM buys on macOS is smaller than on Linux and is written down under Setting a wallpaper on macOS.

## One wallpaper per screen

A publish is a plan over every monitor the session has (see [architecture.md](architecture.md) for the shape of it and [rendering.md](rendering.md) for the geometry). What differs per platform is two thin functions: enumerate the monitors, and hand the desktop N files instead of one. That split is deliberate, because it is what makes a Linux guest with two heads evidence about the model rather than only about Linux.

**Enumerating.** `display::monitors()` keeps the three-valued answer the display query already had: `None` where there is no way to ask, an empty list where the query answered with nothing usable, and a list otherwise. On Linux it is `xrandr --query` through the same parser `outputs()` uses. On Windows it is the `EnumDisplayMonitors` walk that only ever kept the primary before, with `rcMonitor` as the rectangle, `szDevice` numbered into a label a person recognizes (`Display 2`), and the id taken from `IDesktopWallpaper::GetMonitorDevicePathAt` where the COM query answers, because that path is what `SetWallpaper` takes and it survives a reboot in a way `\\.\DISPLAY1` does not. The match from an `HMONITOR` to a device path is by comparing `GetMonitorRECT` against `rcMonitor`, which is the documented way and is exactly the kind of thing that works on one monitor and is ambiguous on two mirrored ones. Where the COM query fails the label stands in as the id and the sink refuses per-monitor work rather than addressing the wrong screen. On macOS it is CoreGraphics, and CoreGraphics rather than AppKit for one reason: `NSScreen` is main-thread-only and both callers of `monitors()` are off it, the engine thread and the `displays` subcommand. `CGGetActiveDisplayList` needs no `MainThreadMarker`, so the query is the same call from anywhere. `CGDisplayBounds` answers in points with a top-left origin in the global display space, and a monitor's own size is its current mode's pixel count, so the rectangle is the mode's pixels at an origin scaled by that display's own pixels-per-point. The id is the ColorSync UUID from `CGDisplayCreateUUIDFromDisplayID`, because a `CGDirectDisplayID` is reassigned across a reboot and even across a wake where external screens come back in a different order, and a serial number collides between two monitors of the same model; `display-<id>` is the fallback where the UUID cannot be had, and the anchor screen then does not survive a reboot. Identical twin monitors can still swap, and no id macOS offers fixes that.

**Being told it moved.** The monitor list is re-queried on every publish, and `display::watch` is what makes a publish happen when nothing asked for one. One thread per process blocks on the platform's own notification and calls a closure; it has no opinion about what a hint means, and the engine settles the burst and compares (see [architecture.md](architecture.md)). On Linux that is RandR through `x11rb`'s pure-Rust connection: `SCREEN_CHANGE | CRTC_CHANGE | OUTPUT_CHANGE` selected on the root, a 1x1 unmapped `InputOnly` window to be woken through, and `wait_for_event` blocking in `poll` on the socket. `OUTPUT_PROPERTY` is left out because it fires for EDID and backlight properties, which move no rectangle. RandR rather than the alternatives: D-Bus signals exist per desktop (KScreen, Mutter's `DisplayConfig`) and there is no common one, udev hotplug events see a connector change rather than a layout change made in a settings dialog and see nothing through XWayland, and polling `xrandr` is the busy loop this exists to avoid. On Windows it is `WM_DISPLAYCHANGE` on an invisible top-level window with its own message pump, which is the same shape `session_end` uses and for the same reason: a message-only window receives no broadcast messages, and this one is a broadcast to top-level windows. On macOS it is `CGDisplayRegisterReconfigurationCallback`, and it is the one watcher with no thread of its own: CoreGraphics delivers the callback on the run loop of the thread that registered it, the app registers on the main thread before the event loop runs, and that run loop is about to be pumped for the life of the process. `kCGDisplayBeginConfigurationFlag` is ignored, because it announces a change that has not happened and the layout still reads as it did. The consequence, and it is why it is written down: a process with no event loop gets no hints there, which is the `render` and `displays` subcommands, neither of which watches anything.

Under a Wayland session the connection is to XWayland, exactly as the query is, and XWayland implements RandR over the compositor's outputs. It is expected to fire for the same changes and is still unverified: the suite runs in Plasma and GNOME on Wayland now, but the layout change case skips there, because the change it makes is an `xrandr` command and cannot move a Wayland compositor's outputs. `docs/roadmap.md` carries the native query that would let it. A Wayland session with no XWayland has no `DISPLAY`, no watcher and no query, all for the same reason. A watcher that cannot start is not a failure: it is logged once and the app is exactly what it was before, with the layout re-queried on every publish.

**DPI.** `rcMonitor` is in virtual-screen coordinates, which are physical pixels only for a per-monitor DPI aware process, so being aware is a precondition for every rectangle above. winit declares `PER_MONITOR_AWARE_V2` behind a `Once` from `EventLoop::new`, and Slint reaches that constructor without overriding it, so a windowed run is aware by the time anything publishes. A run that creates no window is not, and `sunlit-earth displays` is exactly that run. So `wallpaper::ensure_dpi_awareness()` makes the declaration itself, once, from inside `enumerate_monitors` rather than from `main`: that is the one place no caller can skip, headless commands included. Calling it in a windowed run is harmless, and measured to be: with the app running and a window up, `SetProcessDpiAwarenessContext` reports the awareness already set, which is winit having got there first.

What that does *not* settle is behavior under mixed scaling. The development host runs at 100 percent (`AppliedDPI` 96), where an unaware process reads the same rectangles an aware one does, so nothing measured here separates the two. `sunlit-earth displays` on a two-screen Windows machine with different scale factors is the thirty-second check that would, and until somebody runs it the mixed-DPI half stays open; `docs/roadmap.md` carries it.

**Handing over.** Windows takes `IDesktopWallpaper` for anything with more than one monitor: `SetPosition(DWPOS_FILL)` and then `SetWallpaper(device_path, file)` per screen, or `SetPosition(DWPOS_SPAN)` with the canvas for one view across all of them. A single-monitor session keeps the `SystemParametersInfoW` path and the registry style write exactly as they were, so the one configuration that is regression-tested on every desktop and in the Hyper-V guest does not move. `GetWallpaper(monitor_id)` is the read-back, and it is the first time the Windows setter can be asserted the way the Linux one already is: by asking the shell what it holds rather than trusting an exit code.

Linux differs per desktop, so `desktop.rs` says how far each row reaches rather than letting the sink guess:

| Reach | Desktops | What a publish does |
|---|---|---|
| `PerMonitor` | XFCE, KDE Plasma, Deepin, the X11 root pixmap | One image per screen: into the backdrop property named after that monitor on XFCE, into that screen's containment on KDE, one `SetMonitorBackground` per `xrandr` name on Deepin, and drawn at the screen's rectangle in one root-sized image for the root pixmap, which also places a canvas where it spans |
| `Spanned` | GNOME, Cinnamon, MATE, Budgie, Unity | One image; `picture-options` is `spanned` for a view across the screens and `zoom` otherwise |
| `OneImage` | LXQt, LXDE, Trinity, sway, Hyprland, awww, wpaperd, the owned `swaybg`, the portal | One image for every screen: the anchor's own picture, even in the span mode |

The Wayland setters could address outputs by name, and the names they want are the compositor's, which `xrandr` through XWayland does not report (it says `XWAYLAND0`); per-monitor there waits on the native Wayland display query `docs/roadmap.md` carries.

A mode a desktop cannot reach is not a failure. The sink does the nearest thing and the publish says which, in the same voice as the existing refusals, and that sentence rides the success string back to the status line. `OneImage` is handed the anchor's picture rather than the canvas, because a canvas zoomed onto every screen separately is not the view it was cut to be.

KDE reaches every screen, and not through `plasma-apply-wallpaperimage`, which is Plasma's own tool for this and writes every containment: it can neither give two screens two pictures nor leave one alone, which is why one-screen mode used to paint all of them. The scripting API behind that tool does both. `dbus-send` calls `org.kde.PlasmaShell.evaluateScript` with a script where `desktops()` lists the containments, each carries the `screen` it sits on, and `screenGeometry` says where that screen is. Plasma has no span mode of its own, and does not need one here: a view across the screens is already cut into one image per screen before the row sees it, so the span is per-screen crops like any other per-monitor publish.

Two things about that script are worth knowing. It sorts the containments by where their screens sit rather than trusting the order `desktops()` returns, because Plasma numbers them by index and renumbers when the layout changes; `Placement::by_position` is sorted the same way, which is the whole reason that field exists. And a screen this publish left alone is a hole in that list rather than a missing entry, since dropping it would address every screen after it one place too early. `wallpaperPlugin` is written on every screen the publish paints, because a screen left on a colour or a slideshow would otherwise take the image into a plugin that does not read it.

## Setting a wallpaper on macOS

`NSWorkspace.setDesktopImageURL(_:for:options:)` is what every maintained tool on macOS 14, 15 and 26 uses, `macos-wallpaper` and `desktoppr` included, and it is what `wallpaper/macos.rs` calls. Not `osascript`, which needs a TCC Automation grant that a bare binary cannot hold and whose consent dialog often never appears; not the `wallpaper` crate, which wraps `osascript` and stopped in 2021.

The shape is two threads and one hop. The PNGs are written on the thread that asked, through the same `Publication::write_job` Windows and Linux use, so the file lifecycle is one lifecycle. The act of handing them over is AppKit's and `NSScreen` is main-thread-only, so that half goes to the main dispatch queue and the engine thread waits for its answer for at most ten seconds. `exec_async` and not `exec_sync`, because the app joins the engine thread from the main thread at shutdown and a synchronous hop there is a deadlock waiting for its moment; a main thread that never answers is a refusal the status line shows and names the ten seconds. On the main thread each `NSScreen` is matched to a `Monitor` by taking its `CGDirectDisplayID` out of `deviceDescription`'s `NSScreenNumber` and asking for the same ColorSync UUID the query used. A screen the plan did not name keeps what it had; a screen the plan named that AppKit has no `NSScreen` for is a note in the Windows setter's voice.

Every mode reaches the setter as one image per screen, because `image_for` has already cut a spanning canvas into per-screen pieces. macOS has no spanning setter and needs none for the same reason KDE does not: the span is per-screen crops like any other per-monitor publish. Fill is `NSImageScaleProportionallyUpOrDown` with clipping allowed, spelled out rather than left to the default.

Three things about it are known and unpainted. It paints the active Space of each screen and nothing else, and there is no API for the others, so a Space that was not active still holds the path it was handed the last time it was: that is why the generation sweep keeps twelve generations on macOS instead of two, an hour at the default refresh, as a provisional number until a tester says what a Space does when its file has gone. Re-setting the same path with new contents does not refresh the picture, which the generation directories sidestep by giving every publish a new path. And the read-back, `desktopImageURL(for:)`, is not trusted by anybody who uses it, with reports of a directory, the default wallpaper or another screen's image on all three current versions, so it is logged at debug level and never asserted.

Session end is where macOS is genuinely thinner. At logout `loginwindow` sends a quit Apple event, AppKit's default answer is to terminate at once, and winit implements nothing that could block it, so the app can never hold up a logout, which is the property the Windows work exists for. What is lost is the ordered teardown: `slint::run_event_loop()` never returns and nothing after it runs. Config is written when a setting changes rather than at exit, so what a logout can lose is one debounced interval save. The SIGTERM listener is `cfg(unix)` and therefore live on macOS, which covers `kill` from a terminal and a launchd agent being stopped; hooking winit's `exiting` needs Slint's `unstable-winit-030` and is on the roadmap.

One known result comes out of the pixel conversion, and it is a real limitation rather than a rounding worry. A monitor's origin is its point origin times *its own* scale, which is exact for one screen and for several at one scale and wrong the moment the scales differ: a 2x built-in screen 1512x982 points at the origin and a 1x external screen at (1512, 0) come out as pixel rectangles 0..3024 and 1512..3432, which overlap over 1512 pixels. `display::macos`'s own fixture is that layout and its test asserts exactly those numbers. What it costs is `AcrossScreens` on a Retina laptop with a 1x monitor beside it, where the external screen is cut from a region the laptop already covers; `OneScreen` and `EveryScreen` address each screen on its own and are unaffected. A fix means carrying two spaces rather than one, points for where the screens are and pixels for how big to render, which is the same question Windows has open for mixed DPI, so the two want fixing together.

The single-instance guard is the one place a macOS name is a path. `single-instance` is a named mutex on Windows and an abstract socket address on Linux, both names in namespaces of their own, but on macOS it is `flock` on a file at the literal name it was handed: a relative one is created in the working directory, and the working directory of an app launched from Finder is `/`, so the create fails, the guard is silently absent, and a second instance starts beside the first. `tray::instance_name` makes it an absolute path under the app data directory, where the config and the wallpapers already are.

`assets/macos/Info.plist` is the template `cargo xtask bundle --platform macos` copies into `Contents/Info.plist`, with `@VERSION@` replaced by the workspace version and everything else fixed, so the bundle's identity is a file somebody can read rather than strings in the xtask. `CFBundleIdentifier` is `earth.sunlit.SunlitEarth` and never changes once chosen: preferences and TCC grants key on it, so a new one is a new application as far as macOS is concerned. `LSUIElement` is deliberately absent, because winit sets the regular activation policy at startup whatever the file says; the app has a Dock icon while it runs and closing its window hides it to the status item, as on the other two platforms.

Shipping it is `Sunlit Earth.app`, ad-hoc signed with `codesign --force -s -` and zipped with Apple's own `ditto`, plus a plain tarball of the same binary beside it. Apple Silicon runs only signed code, ad-hoc included, and the linker seals a bare `cargo build` binary at link time; wrapping it in a bundle breaks that seal, which is why the assembled bundle is re-signed. Gatekeeper on 15.1 and later has no Control-click bypass for an ad-hoc signed download, so [usage.md](usage.md#installing-on-macos) quotes the System Settings route; the tarball exists because quarantine is an extended attribute that browsers and Archive Utility set and `tar` in Terminal does not, so `curl -L … | tar xz` and `./sunlit-earth` meets no dialog and prints its log to the terminal it was started from. Notarization needs the Apple Developer Program, and this project has no account; the release workflow leaves the hook and ships ad-hoc.

## Setting a wallpaper on Linux

Setting a wallpaper is a desktop-shell operation rather than a display-server one, so there is no call to make. `desktop::choose` decides, as a pure function over a `Session` trait that answers every question it asks (a variable, a program on `PATH`, a running process, a bus name, a socket, the X server's desktop windows, the Wayland globals, the portal); `desktop/probe.rs` answers live and lazily, and the tests answer from fabricated sessions on every platform. It returns the setter with the evidence it rests on, or a refusal that lists every row and rung it tried with the reason each declined. The plan and the research behind it are `docs/plans/2026-09-23-linux-wallpaper-fallback-*.md`.

The first stage is a table. `XDG_CURRENT_DESKTOP` selects a row, walked in the session's own order; where it is empty, `XDG_SESSION_DESKTOP` and then `DESKTOP_SESSION` are walked the same way. gsettings for the GNOME schema (both `picture-uri` and `picture-uri-dark`, because GNOME picks between them by colour scheme), for Cinnamon's own schema, and for MATE's, whose key takes a path rather than a URI; a plasmashell script over `dbus-send` for KDE; `xfconf-query` for XFCE; `pcmanfm-qt --set-wallpaper` for LXQt. Budgie and Unity have their own rows using the GNOME mechanism, so a refusal can name what it found. Five rows were added from their tools' documentation, and all but sway's have not run: `pcmanfm --set-wallpaper=<path> --wallpaper-mode=crop` for LXDE, `dcop kdesktop KBackgroundIface setWallpaper <path> 8` (scale and crop) for Trinity, which `TDE:KDE` now reaches before KDE because the walk follows the session's order, `SetMonitorBackground` per monitor over `dbus-send` for Deepin (`org.deepin.dde.Appearance1`, or `com.deepin.daemon.Appearance` where only that name is on the bus), `hyprctl hyprpaper wallpaper ", <path>, cover"` for Hyprland, gated on hyprpaper's socket, and `swaymsg output * bg <path> fill` for sway, which a session also reaches through `SWAYSOCK` alone. The sway row has run in the test guest (sway 1.10), read back through the `swaybg` sway starts for it.

A row applies when its setter is on `PATH`, and for GNOME and Cinnamon also when the process that draws the key runs (`gnome-shell` or `gnome-flashback`, `cinnamon`), because `gsettings set` succeeds silently with nobody drawing, which was harmless while a refusal was the alternative and is wrong now that a ladder is. A row that does not apply does not refuse: the walk goes on to the next token, which is what takes `Regolith-Wayland:GNOME:sway` with no GNOME shell to sway. MATE, Budgie and Unity have no gate, since no process name for them was verified.

A session no row claims goes down a ladder, first working rung wins. On Wayland: a running awww (or swww, its name before the rename) found by `$XDG_RUNTIME_DIR/<display>-awww-daemon.sock`, told `awww img <path> --transition-type none`; a running wpaperd, found by `$XDG_RUNTIME_DIR/wpaperd.sock`, told `wpaperctl set <path>`; then a `swaybg` of the app's own where the compositor advertises `zwlr_layer_shell_v1`. A running daemon comes first so the app does not put a second background surface under one the user already has. On X11: a desktop window (`_NET_WM_WINDOW_TYPE_DESKTOP` on `_NET_CLIENT_LIST`) picks its owner's row by `WM_CLASS` (pcmanfm, pcmanfm-qt, xfdesktop, nemo-desktop, caja, plasmashell) and keeps the root alone; with none, and no Mutter, Muffin, GNOME Shell or KWin named by `_NET_SUPPORTING_WM_CHECK`, the app paints the root pixmap itself. Last, on either, the XDG desktop portal. `SUNLIT_EARTH_WALLPAPER_SETTER` names a setter and skips all of it but that setter's own presence check; an unknown name is a refusal listing the valid ones.

The root pixmap follows feh and Esetroot over x11rb, with no program installed: every monitor's picture is composed into one image the size of the root in the server's own pixel layout, uploaded into a new pixmap (x11rb's `Image::put` splits the upload to fit the maximum request length), the previous setter's pixmap is freed with `KillClient` when `_XROOTPMAP_ID` and `ESETROOT_PMAP_ID` both name it, both atoms and the root's background are set, and the connection closes with `RetainPermanent`, so the server holds the pixmap until the next publish frees it. No PNG is written, because nothing reads one.

The owned `swaybg` is started for each publish in a process group of its own, as `swaybg -o * -i <path> -m fill`. If it exits within 500 ms that is the refusal, with its stderr. So is a "Failed to load" line in its log by then, because `swaybg` that cannot read the image does not exit: it runs on and draws nothing, which the guest showed as a black screen behind a passing read-back until the check was added; the failed one is ended before any earlier one, so the previous wallpaper stays. Otherwise a one-shot thread waits a second, so the two surfaces overlap rather than the compositor's grey showing between them, and ends every `swaybg` of this user whose command line names a file under the wallpaper directory except the newest. The last one outlives the app, as every desktop's wallpaper does, and the next start finds it by its command line rather than through a state file. A `swaybg` showing the user's own file is left running and named in the evidence; open question 2 of the plan asks whether it should be ended. In sway, forced with the variable, ours was the one on screen beside the `swaybg` sway starts for its own background colour, which is older, and exactly one of ours was left running with the globe on screen after the app exited.

The portal was rejected here once, as putting a dialog in front of every set. That is true only with `show-preview` true. With it false the portal asks once, stores the answer, and from then on sets the wallpaper, or refuses, without a word. So it is the last rung: it applies where `org.freedesktop.portal.Wallpaper` is exported, and declines where the only backend implementing the wallpaper portal is `xdg-desktop-portal-gtk` and no `gnome-shell` runs, since that backend writes GNOME's key and a success there changes nothing on screen. The sink keeps one session bus connection, calls `org.freedesktop.host.portal.Registry.Register("sunlit-earth")` first where the portal has it (1.19.4 and later; Debian 13 ships 1.20.3), so the permission is this app's rather than one every unidentified host app shares, subscribes to the request's `Response`, and calls `SetWallpaperFile`. A stored denial answers with code 2 and the refusal says `flatpak permission-remove wallpaper wallpaper sunlit-earth` resets it. A dialog still open after five seconds is waited on by a thread, and the publish says the portal is asking; a publish that comes while it is open is refused with a sentence saying so rather than raising a second one.

What the GNOME session in the test guest showed on 2026-09-23, with the portal forced: the question is GNOME Shell's own modal, "Allow Sunlit Earth to Set Backgrounds?", which names the app because of the `Register` call, with Deny focused. xdg-desktop-portal gives it 25 seconds, D-Bus's default timeout, and then logs "Failed to show access dialog: Timeout was reached" and answers the request as a failure, storing nothing, so an unanswered question is asked again by the next process that publishes. A question raised while the shell was still in its overview at the first login never became visible. After Allow the permission store held `sunlit-earth` = `yes`, the next publish returned in a fifth of a second with no dialog, and GNOME's backend had copied the image to `~/.config/background` and pointed both keys at that one path, which is why the e2e read-back compares bytes rather than names. Every answer there was a click through `xdotool` from an agent, not a person.

The choice and its evidence go to the info log whenever they differ from the last choice, into every refusal, and onto a `setter:` line of `sunlit-earth displays`.

The list is walked in the order the session wrote it, not in the table's order, which is what makes `Budgie:GNOME` Budgie and `ubuntu:GNOME` GNOME. Every row works identically in that desktop's X11 and Wayland sessions, because neither the shell nor the setting knows which is running, and for KDE and GNOME that is observed: on 2026-09-23 `test_set_wallpaper` passed in Plasma 6.3 and GNOME 48 on Wayland in the test guest, with the app as a native Wayland client and the globe on the desktop in a screendump afterwards. XFCE is the one row that asks a question first: which backdrop properties exist depends on the monitors and workspaces the session has, and their names are inside the property paths, so `xfconf-query -l` runs and every property ending in `last-image` is set. A session with none is a refusal and not a success, because nothing must report a wallpaper it did not set.

Detection and command construction are pure functions tested on every platform against fabricated sessions; only the sink runs anything. `check_supported` makes the whole choice before a frame is rendered. Beyond the table, three rungs have run in the test guest, each with the desktop screendumped afterwards: the root pixmap in i3 (the pixmap id changed between publishes and the previous one was gone), the owned `swaybg` in sway, and the portal in GNOME on X11. awww, wpaperd, and the portal on any other desktop are reviewed, not run. Four of the original seven rows have been run, one boot per desktop in the Linux test guest, with the desktop screenshotted afterwards each time; Cinnamon's globe was visible only after its crashed shell was restarted by hand, since its session falls into a fallback dialog. `docs/roadmap.md` names the three rows that have not run and carries that defect.

Every publish gets a directory of its own, `SunlitEarth/gen-<id>/`, and writes its images into it, one per screen plus a `canvas.png` where the mode spans them. No two publishes share a directory, so no path a desktop was handed is ever rewritten or deleted while that desktop still holds it. This is what a shell that watches its wallpaper file needs, and one does: Plasma's `MediaProxy` keeps a `KDirWatch` on the current image so a changed file reloads. The two-name scheme this replaced reused `wallpaper-1.png` and `wallpaper-2.png` and rewrote whichever the desktop was not showing, which was safe for a desktop that reads the file once and fatal for one that watches it: rewriting a watched path decoded a half-written image, and deleting and recreating the path of a screen a one-screen publish had left alone fired the watch on a source the proxy had moved on from, and on a distro that ships the plugin with assertions live that took plasmashell down. A fresh directory per publish removes both, and it keeps what the two names gave: every one of these desktops keys the wallpaper it shows on the path it was given, so a new image on a path the desktop is not already showing is what makes the setter load a file rather than ignore a write of the value already stored.

Each image is written atomically, encoded into a temporary file in the generation directory and then renamed onto its final name, so a reader watching the destination sees the whole file or none of it, never a truncation. The destination is a name no publish used before, so the rename creates it rather than replacing a file some shell holds open. A publish then sweeps the generations no screen holds any more, keeping the one it just wrote and the one before it: a screen a one-screen publish did not repaint still shows and still watches its file from the previous generation, so that generation stays until a newer one has replaced it too. Which generation is newest carries the alternation across a restart the way the two names' modification times did, so no state file records it. Windows needs none of this in principle, since `SystemParametersInfoW` reads whatever path it is handed, but it writes through the same generations so there is one lifecycle rather than two.

The screenshot is not ceremony. XFCE's setter exited zero, `test_set_wallpaper` passed, and the desktop went on showing xfdesktop's own default: the property xfdesktop reads is named after the connected monitor and does not exist until something creates it, and the ones the channel file ships under `monitor0` are two major versions old. So the XFCE row takes the connected outputs' names and creates that property, and its fill mode, where the session has neither. The general rule the episode leaves behind is that a setter's exit code is not evidence that a wallpaper changed, which is why on Linux `test_set_wallpaper` asks the session what its wallpaper is once the setter says it set one. It derives the read-back from the same table the write came from, and a desktop that names its settings after its own monitors has to hold the image in one of those: reading back only what the write chose is what would have called the XFCE bug a pass. Plasma's tool and `pcmanfm-qt` have nothing to ask, so those two sessions keep the exit code and say so.

`display.rs` is the other half of the same work. It parses `xrandr --query` into the connected outputs that have a mode assigned, which answers both questions Win32 answers: `target_size` takes the primary output's mode, and `is_position_on_screen` tests the title bar against every output. The parser is separate from the process so it is tested everywhere, not only where xrandr exists. Under a Wayland session the answer comes through XWayland, where display scaling can skew it; the native per-desktop D-Bus query is a roadmap item.

Session end on Linux is SIGTERM and nothing else, through `signal-hook` rather than a scoped `unsafe`: a signal handler may call almost nothing and quitting a Slint event loop is not on that list, so the delivery reaches an ordinary thread through a self-pipe first. SIGHUP is deliberately not treated as the session ending, because the e2e suite starts the app from a process whose controlling terminal is not its own. What this does not do is participate in the question: a desktop asks whether an application is *ready* to close over logind's inhibitor protocol, and SIGTERM arrives after that decision. So this uses the grace period, and the inhibitor half is on the roadmap.

The desktop e2e suite is `#[ignore]`d, not `cfg`-gated: it compiles on all three OSes (which is free coverage for the IPC and process plumbing) and never runs in CI, because hosted runners have no interactive desktop. It runs on the developer's desktop with `cargo e2e`, and in a local VM with `cargo xtask e2e --target <windows|linux>`; see `docs/vm-setup.md`.

Three cases inside it are gated at runtime rather than by `cfg`, following the same convention as `software_adapter_produces_correct_results`. The tray-start-hidden lifecycle and single-instance enforcement need a tray icon, and single-instance is additionally tray-mode-only in the product. Whether there is a tray is a property of the session rather than of the platform: Windows always has one, and on Linux Slint registers its icon over D-Bus through `ksni`, so `tray_supported()` asks `gdbus` who owns `org.kde.StatusNotifierWatcher`. Plasma and xfce4-panel answer, GNOME and Cinnamon do not, so those two cases run under the first two desktops and skip under the other two. On macOS every GUI session has a menu bar and Slint compiles its own AppKit status item, so `tray_supported()` answers `true` there without probing: a session with no menu bar is no session at all, which the cases that need a window fail on first. `test_set_wallpaper` sets a real desktop wallpaper, so it is opt-in through `SUNLIT_EARTH_E2E_WALLPAPER`, which both generated guest jobs set and nothing else does. All three print why they skipped. Two further cases pick their startup mode by the tray capability, running windowed where there is no tray, which tests the same thing minus the icon. macOS has no VM story and will not get one: the hosted runner is the only macOS this project can run on, so `cargo xtask e2e --target macos` does not exist and `macos-build.yml` in its `build-and-e2e` mode is what runs the suite there.

What `test_set_wallpaper` can assert about the capability differs by platform, which is why it is three checks rather than one equality. Windows has one setter and every session has it, so a refusal there is a regression, and macOS is on that list too now that it has one. A platform with no setter at all must not claim one. Linux has a setter per desktop, so the answer belongs to the session rather than to the build, and the guarantee is narrower and sharper: a run that opted in to replacing the wallpaper is a run in a guest whose desktop was chosen for having a setter, so on Linux an opted-in run that reports no setter fails rather than skips. Without that clause a backend that went missing would report itself unsupported and the case would quietly pass.

It publishes twice, and the second publish is a case of its own rather than a repetition: the file the app wrote must differ between the two, on every platform, and where the desktop has a store to ask, what that store reports must differ too. One publish cannot tell a working setter apart from one that changes the wallpaper once and then never again, which is the shape the alternation above exists to prevent.

`test_memory_report` is deliberately not gated at all: the report degrades section by section on its own, so a backend with no allocator report produces a shorter line rather than a missing section, and the case asserts the four section names and prints the whole report. Printing is half the point, since the suite runs with `--nocapture` on both paths and that is where a real report from a real GPU or from a guest is captured.

`test_session_end_shuts_down_promptly` is the one exception to "`#[ignore]`d, not `cfg`-gated": it delivers `WM_QUERYENDSESSION` and `WM_ENDSESSION` to the running binary, which are Win32 calls, so the body does not compile elsewhere. It asserts the app exits successfully and in under five seconds, which is the number Windows gives an application before it names it on the shutdown screen.
