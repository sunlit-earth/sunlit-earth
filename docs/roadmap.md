# Roadmap

Features and improvements planned for Sunlit Earth, roughly ordered by priority within each category.

## Wallpaper app

- [x] Wallpaper export and setting: save rendered frame to an image file and set it as the desktop wallpaper via OS APIs. All three platforms implemented: Windows (`SystemParametersInfoW` and `IDesktopWallpaper` via `windows-sys`), Linux (a per-desktop setter, see the entry below) and macOS (`NSWorkspace`, see the entry below). The refusal a platform with no setter would get is still in `wallpaper_sink` and nothing this tree builds for reaches it.
- [ ] Periodic re-rendering: timer-driven scheduler that re-renders every N minutes so the terminator tracks the sun. Update interval should be user-configurable.
- [x] System tray icon: minimize to tray on window close with "Open" / "Exit" context menu, single-instance enforcement, `--windowed` flag for original close-exits behavior (Windows only).
- [x] System tray extended features: "Refresh Now" and a checkable "Auto-refresh" entry are in the tray menu, and the engine runs headlessly with no window at all (the `render` subcommand creates no window and no Slint backend). A long-running daemon mode with no settings window is still open.
- [x] About window: the tray menu and the settings panel share one lazily created window, which sets its own icon from the SVG master and puts a fixed header (the mark, the title, the version, the copyright and the repository link) over three tabs: the attributions, the GPLv3, and the third-party crate list. All three documents are `include_str!`'d, so nothing reads a path at runtime. `assets/ATTRIBUTION.md` is parsed into blocks and laid out one element per block, headings sized and bullets hanging in their own margin, because `StyledText` renders inline markup but cannot lay a document out; `assets/third-party.md` stays one `StyledText`, flattened so its heading parses; `LICENSE` goes in as plain unwrapped text. Links are live in all three. Links open through the platform's own handler with no `unsafe`. The audit behind it closed four real gaps: the mandatory EUMETSAT notice for the cloud layer, HYG's license URI and the statement that the catalog was cut to magnitude 7, the CC BY-SA to GPLv3 compatibility note, and the third-party licenses, whose texts nothing in the tree carried at all before `cargo xtask bake licenses`. Measured headlessly on 2026-09-04: the 557-line third tab parses in 1.5 ms and lays out in 10 to 11 ms; paint and scrolling on a real adapter are unmeasured. Plan: [plans/2026-09-04-about-window-overhaul-plan.md](plans/2026-09-04-about-window-overhaul-plan.md).
- [x] App icon: the mark (night-side globe, bold outline, tilted aurora arcs, the sun rising occluded behind the limb) is an SVG master plus 32/24/16 variants under `assets/icon/`, and `cargo xtask bake icon` turns them into every raster the app shows: the nine-size `.ico` embedded in the exe, the 32 px tray bytes, a 256 px PNG that turned out to be a spare, and the freedesktop hicolor set that goes with `assets/linux/sunlit-earth.desktop`. Both windows take their icon from the SVG master through Slint, and so does the mark in the About window's header. Verified in the Linux guest under KDE and XFCE (the tray and the title bar, and the taskbar entry once `install-user.sh` has run, since a task manager draws the entry its `WM_CLASS` matches) and on Windows (the exe's group icon, and `WM_GETICON` on the running window). One half is not verified: what the KDE launcher search offered was the running window rather than the installed entry, so Kickoff's indexing of a fresh install is unobserved. The 16 and 24 px rasters were judged on real shells on 2026-08-24: good enough to ship, with the 16 px variant a candidate for a later nudge. The macOS `.icns` came with the macOS branch: ten entries, five logical sizes at 1x and 2x, baked by the pure-Rust `icns` crate so no Mac is needed to produce it, and consumed by the `.app` bundle through `CFBundleIconFile`. System packaging (deb, Flatpak, AppImage) stays with the cross-platform release item below, which consumes the same assets. Plan: [plans/2026-08-23-app-icon-integration-plan.md](plans/2026-08-23-app-icon-integration-plan.md).
- [x] Configuration persistence: save and load settings (camera position, update interval, rendering options) between launches.
- [x] Wallpaper setting on Linux: `desktop.rs` is a table of per-desktop setters chosen by `XDG_CURRENT_DESKTOP`, and `display.rs` is the native display query that came with it, which replaced both placeholders Phase 2 left behind: the 2560x1440 default in `wallpaper_sink` and the coordinate-range window-position check in `config`. Phase 5, see [plans/2026-08-21-phase5-linux-vm-and-parity-plan.md](plans/2026-08-21-phase5-linux-vm-and-parity-plan.md).
- [x] Wallpaper setting on macOS: `NSWorkspace.setDesktopImageURL` per screen from the main thread, over the CoreGraphics display query and the ColorSync UUIDs that address a screen across a reboot, with `CGDisplayRegisterReconfigurationCallback` for a layout that moves. Not `osascript`, which needs a TCC grant a bare binary cannot hold. Written blind and compiled and unit-tested on `macos-latest`, which is as far as the evidence goes: nobody working on this project owns a Mac, so [platforms.md](platforms.md) gives every macOS row the tier it is at, and the tester round is the entry below. Plan: [plans/2026-09-06-macos-support-plan.md](plans/2026-09-06-macos-support-plan.md), with the research in [plans/2026-09-06-macos-support-research.md](plans/2026-09-06-macos-support-research.md).

- [ ] A tester on a real Mac: the probe in the runner's own session (`macos-build.yml` in `build-and-e2e` mode), then the same runner held open with that workflow's `interactive` input, which is a desktop somebody here can drive by hand without owning a Mac, and then a person on macOS 15 or 26 with the ad-hoc signed bundle. The first two steps are done as of 2026-09-23, and `platforms.md` has what they moved. The middle step is cheaper than the last and answers less: a paravirtual GPU with one screen, or two with `screens: 2`, both at 1x, so the menu bar, the window, the wallpaper and a two-screen layout are all observable there and the Retina and mixed-scale questions below are not. What only a Mac can answer is in section 4 of the macOS research document: whether the wallpaper actually appears per screen and what a Space that was not active shows afterwards, whether the status item reads against a light and a dark menu bar and brings the window forward, how FemtoVG on OpenGL performs on a real Apple GPU, what `sunlit-earth displays` reports on a Retina laptop with a 1x monitor beside it, and what the Gatekeeper dialogs say word for word. Until then no macOS row goes past the "runner" tier.
- [ ] `test_render_and_exit` fails on Apple Silicon runners: the process holds 1775 to 2075 MB at exit against the case's 1000 MB bound, in three runs on 2026-09-23 with one screen and with two, while the same case passes on the Intel runner. Unified memory may count GPU allocations in RSS there, which would make the bound the wrong measure rather than the app wrong, but nothing has checked that yet.

- [ ] A layout that mixes display scales overlaps on macOS, the way mixed DPI is already open on Windows. A monitor's pixel origin is its point origin times its own scale, so a 2x built-in screen beside a 1x external one puts the second inside the first's pixel rectangle: 1512x982 points at the origin and (1512, 0) give 0..3024 and 1512..3432. `AcrossScreens` then crops the external screen from a region the laptop covers; the per-monitor modes address each screen on its own and are right. The fix is the same one Windows needs, which is to carry points for the layout and pixels for the render size rather than one space for both, so the two are one piece of work. `display::macos`'s fixture is that layout and its test pins the current numbers, which is what a fix would have to change.
- [ ] macOS `LSUIElement`, the ordered teardown, and autostart. All three need Slint's `unstable-winit-030` feature or product surface this project does not have yet. `LSUIElement` would hide the Dock icon, and the key does nothing today because winit forces the regular activation policy at startup; the teardown is winit's `exiting` callback, which `with_custom_application_handler` could hand to the app and which would give macOS back the ordered exit a logout takes away; autostart would be a LaunchAgent, which is also what would make SIGTERM the ordinary way this app is stopped there.
- [ ] Three of the Linux wallpaper backends ship reviewed rather than exercised. The test guest boots KDE, GNOME, XFCE and Cinnamon, and all four were run with the desktop screenshotted afterwards, so those four are observed, Cinnamon's only after restarting its crashed shell by hand, which is the session defect its own item below carries; MATE, LXQt and Budgie are one table row each, written from their documented setters and never run. Adding any of them to the guest image is the cheapest way to close that, at one to two GB of image each, and the desktop-share research that picked the four put all three of these in the noise.
- [x] Wallpaper setting under Wayland, for KDE and GNOME: the Linux guest boots Plasma 6.3 and GNOME 48 on Wayland with `--session-type wayland`, from the same image, and on 2026-09-23 the whole suite passed in both with the app as a native Wayland client, `test_set_wallpaper` included and the globe on the desktop in a screendump afterwards. Nothing in the setter table changed, as expected, since every row is a desktop-shell operation. What the guest contract needed was `WAYLAND_DISPLAY` in `session.env`, written only when the session has one, and a check that the session which came up is the one asked for; what the icon needed was an app id, which the app now sets to `sunlit-earth` on Linux, and KWin matches the window to `sunlit-earth.desktop` by it. XFCE's and Cinnamon's Wayland sessions are experimental in Debian 13 and not offered. Plan: [plans/2026-09-23-wayland-sessions-plan.md](plans/2026-09-23-wayland-sessions-plan.md), research in [plans/2026-09-23-wayland-sessions-research.md](plans/2026-09-23-wayland-sessions-research.md).
- [ ] The Linux display query is `xrandr`, so under a Wayland session it answers through XWayland, where display scaling can skew the reported size. The native answer is a per-desktop D-Bus call, which is a different table from the wallpaper one; the suite now runs in Plasma and GNOME on Wayland, so there is a place to check it. Observed on 2026-09-23 in both, at the guest's scale of 1 with one 1920x1080 output: `test_displays_reports_the_session_layout` and `test_across_screens_writes_what_this_desktop_can_hold` passed, and XWayland reported that output as `0,0,1920,1080`, its true rectangle. That is one output at the origin and scale 1; more than one output, an offset origin and any other scale are all unmeasured.
- [ ] Layout changes and more than one screen under Wayland. `test_a_layout_change_republishes_the_wallpaper` skips in a Wayland session and `--screens` above one is refused with `--session-type wayland`, because the change and the placement are `xrandr` and the pointer mapping is `xinput`, none of which reach a Wayland compositor's outputs. The port is `kscreen-doctor` on Plasma (in `libkscreen-bin`, not in the image) and `org.gnome.Mutter.DisplayConfig.ApplyMonitorsConfig` after `GetCurrentState` on GNOME, and at that point the native per-desktop display query in the entry above is the better foundation for all three, so it is one plan rather than a patch to the harness. Decision 9 of the Wayland sessions plan.
- [ ] Linux session end handles SIGTERM and nothing else, which means it uses the grace period a session gives a process it has already decided to close. The other half of the conversation is logind's inhibitor protocol, over the session bus, which is how an application gets *asked* first, the way `WM_QUERYENDSESSION` asks on Windows. That needs a D-Bus dependency and has no test the suite can run without a session bus, so it is deferred rather than half-built.
- [ ] Cinnamon's session in the Linux test guest starts its shell, loses it a second later, and falls back to `metacity`, which the image does not install, so a login leaves a modal "Cinnamon just crashed" dialog over a black desktop. Nothing the suite does is affected: the cases run over SSH through `DISPLAY` and all ten pass, and `cinnamon --replace` over `vm ssh` restores the shell and the wallpaper with it. Reproduced on two fresh boots, so it is deterministic. What is unknown is why the shell is signalled; its own log says it started cleanly in 799 ms with every applet loaded, and the journal reports no segfault and no out-of-memory kill. Installing `metacity` would make the fallback a working window manager rather than a Python traceback, which is a better symptom and not a fix.
- [ ] The guest's quiet-down turns off Baloo and nothing else that indexes. `localsearch-3`, which is what trixie calls tracker-miners, was seen running in the XFCE session, and the same package answers for GNOME and Cinnamon: the plan wanted file indexing off in every desktop and `desktop.sh` writes `baloofilerc` only, so three of the four still index a test suite's output. Harmless to the results and a waste of a throwaway guest's CPU. The fix is one more config file, or the `localsearch` user units masked, at the cost of an image rebuild.
- [ ] Two of the guest's four sessions have no polkit authentication agent. `polkit-kde-agent-1` is the only agent the image installs and its autostart entry says `OnlyShowIn=KDE;`, so Plasma gets it, GNOME is its own agent inside `gnome-shell`, and XFCE and Cinnamon get none: `polkitd` is running and nothing is listening for it, so an operation needing authorization there fails instead of prompting. Nothing the suite does asks for one, which is why this is a note and not a blocker. The fix is one package plus an autostart override in `desktop.sh`, at the cost of an image rebuild.
- [ ] GNOME's session in the guest opens the Activities overview at login, which is its own default with no window on screen. Harmless to the suite and confusing to a person looking at the console; one Escape closes it, and an autostart entry or a shell setting would close it for good.
- [x] Multi-monitor support: the wallpaper is a plan over the monitors a session has rather than one image at the primary's size. Three modes over a monitor list and an anchor screen, the geometry as pure functions in `display::layout` that need no display to test, and two thin per-OS functions carrying everything platform-specific: enumerate the monitors, and hand the desktop N files instead of one. A single-monitor session on a landscape screen comes out byte-identical in every mode, which is the first thing the tests pin; a lone portrait screen deliberately does not, because the contain rule is what a portrait screen is for and it gives that screen the lens the globe fits inside instead of the one that ran it off both sides. `sunlit-earth displays` prints the layout and the plan without rendering anything, the Displays group in the settings window offers the mode and the anchor with a diagram of the layout, and `desktop.rs` says how far each Linux desktop's setter reaches so a mode it cannot reach degrades to the nearest thing and says so. Verified in a two-head Linux guest: the app reports the rectangles the guest was configured with, and KDE's one-image reach takes the anchor's piece as the model says it should. Geometry in [rendering.md](rendering.md), the sink contract in [architecture.md](architecture.md), the per-platform half in [platforms.md](platforms.md); the plan and its nine departures are in [plans/2026-08-30-multi-monitor-plan.md](plans/2026-08-30-multi-monitor-plan.md).
- [ ] Four Windows questions the Linux guest cannot answer, each cheap once somebody has the hardware. Whether `rcMonitor` is physical pixels under *mixed* scaling: the app declares `PER_MONITOR_AWARE_V2` itself before enumerating, and the development host runs at 100 percent where an unaware process reads the same numbers, so the declaration is verified and its consequence is not. Whether the `HMONITOR` to device-path mapping holds with two monitors, and with two mirrored ones, where `GetMonitorRECT` against `rcMonitor` is ambiguous by construction. Whether Windows persists per-monitor images across an unplug and a replug. And what `DWPOS_SPAN` does under mixed DPI, which decides whether the canvas goes to the shell whole or is cut here; the fallback needs no new code. `sunlit-earth displays` on a two-screen machine answers the first two in thirty seconds. The Hyper-V synthetic adapter has no multi-monitor mode and enhanced-session multi-monitor needs the host to have the monitors, so an automated Windows case needs an indirect display driver in the guest, which is its own piece of work.
- [ ] A fifth Windows question, in the same shape and answered by the same hardware: the display-change hand check. With the settings window open, undock, and within about two seconds the diagram should show one screen and the wallpaper should be rendered for the internal panel; redock, and both should return. Then, with the anchor on automatic, change the main display in Windows' own settings and see the anchor follow, which is what decides whether `WM_DISPLAYCHANGE` arrives for a primary move that shifts no resolution. The log records every hint and every recheck, so it also says how many hints a dock produces and how far apart they are, which is what the settle constant should be tuned from. The guest's video is a single fixed mode, so no automated case can make Windows send the real message; the unit test proves the message reaches the hint and stops there.
- [ ] KDE Plasma's per-screen wallpapers are written and not yet watched. The row is `PerMonitor` now: `dbus-send` runs a plasmashell script that walks `desktops()`, sorts them by `screenGeometry` rather than by index, and writes `Image` into each screen's containment, which is what Plasma's own settings dialog does and what `plasma-apply-wallpaperimage` cannot do, since it writes every containment at once. `dbus-send` comes with `dbus-x11`, already in the guest image, so nothing new is needed on `PATH`. What has not happened is a two-head guest run: the script's ordering assumption, the hole that keeps a screen the publish left alone from shifting the rest, and whether a Plasma screen takes a `file:` URI the way the config stores it are all reasoned from the documented API rather than observed. The read-back to prove it still does not exist: `evaluateScript` can return a value, so `readConfig` per containment is the way to ask Plasma what it is actually holding instead of trusting an exit code.
- [x] A display layout that changes while the app runs is reacted to as it happens. `display::watch` blocks on the platform's own notification (an invisible top-level window for `WM_DISPLAYCHANGE` on Windows, a RandR subscription through `x11rb` on Linux, `CGDisplayRegisterReconfigurationCallback` on the main thread's run loop on macOS) and drops a hint into the engine's command channel; the engine settles the burst for two seconds on its own tick, re-queries once, compares against the last list it saw, announces a list that differs so the settings window's Displays group is rebuilt, and republishes only where the desk holds a picture this process made for a layout that is gone. No timer and no polling anywhere, and a watcher that cannot start leaves the app exactly as it was. Verified in the two-head Linux guest by switching an output off and back on and watching the wallpaper follow (`test_a_layout_change_republishes_the_wallpaper`); the Windows message reaches its callback in a unit test, and what only a real docking station can answer is the hand check in the entry below. The plan is [plans/2026-09-03-multi-monitor-amendment-display-change-events.md](plans/2026-09-03-multi-monitor-amendment-display-change-events.md).

## Rendering

- [x] Blue Marble water brightness: ocean areas are too dark and sometimes contain satellite imagery. Pre-process textures to get a uniform ocean color, preserving different extents of sea ice per season
- [x] Color correction: Rendered textures still look darker than their sources. Investigate if there is a color space issue to resolve and provide in-app texture processing to adjust e.g. gamma and saturation (current image may be oversaturated)
- [x] Water on the day side looks matte and more like a solid surface that happens to be blue. Investigate what kind of effect can be applied to make it look more like actual water. First iteration: specular sun glint (Blinn-Phong). Second iteration: Schlick Fresnel for specular modulation and diffuse color shift toward sky at grazing angles, with UI sliders for mix strength and extent.
- [ ] Seasonal texture switching: auto-select from the 12 monthly NASA Blue Marble variants based on the current month.
- [x] Atmosphere glow / Airglow: three physically-motivated layers (Rayleigh scattering, orange nightglow, green nightglow) with separate controls.
- [x] Cloud overlay: semi-transparent cloud layer from near-real-time satellite data. Requires researching data sources (GOES/Himawari composites, etc.) and building a download + caching pipeline.
- [ ] Make clouds less intense over land, since our cloud data sources have a bias towards creating a haze of clouds over land.
- [x] Clouds on the night side. The night floor in `fs_cloud` was a hardcoded 0.05, which measures darker than the 0.137 the night map's own unlit land sits at, so a cloud over land darkened what it covered and a cloud over a city took it from 1.0 to 0.19. The shell was also shaded with the unit-sphere normal, so cloud tops shared the ground's terminator instead of sitting the 3.14 degrees nightward their 9.6 km buys, and `fs_cloud` read the `terminator_width` uniform that carries the -1.0 sentinel in the three single-texture modes, which reversed its `smoothstep` edges there. See [plans/2026-08-29-night-side-clouds-plan.md](plans/2026-08-29-night-side-clouds-plan.md): `cloud_night` at 0.35, chosen against the night map rather than against a photograph, the shell's own tangent condition, and `CLOUD_TERMINATOR_WIDTH` at 0.18, which is also what takes `fs_cloud` off the sentinel-carrying uniform. Each hemisphere then got its own opacity, because one alpha does not read the same on both: a deck is darker than the city under it, and the source's median texel is 0.79 with half a percent of it over 0.97, so the day side's straight multiply left a third of the ground showing at 100 percent. `cloud_opacity_night`, 0.55 by default, is an optical depth rather than a multiplier, and the top of its range covers the ground completely. Measured on the fixtures: a night-side deck reads 89.0 over ground that reads 42.0, where the old constant gives 13.0, and over the fixture's city the window reads 246.7 with no deck, 164.7 at the default night opacity and 89.0 at the top of it, against the 89.2 the deck alone is worth. The suite gains a fixture cloud source, which is what lets a test measure a cloud pixel rather than only count that one was drawn, with two goldens and four engine cases. A third control was tried and removed: `cloud_city_gain` lit a cloud base from the night map under it, and the night map turned out to carry a blue-tinted terrain layer as well as lights, measured at 0.172 over the Sahara and 0.231 over Antarctica against 0.289 over Tokyo, so it brightened every land mass rather than glowing under cities and the whole term came out again. The document's own finding is why the floor is a control and not a calculation: the day-to-night gap is 18.6 stops by the sun-to-full-moon ratio and 18.53 by the exposure settings of "Hello, World" against those of Blue Marble, which is more than any sensor or eye holds at once, so every image showing both is a tone map and so is this one.
- [x] Texture resolution selection: the Rendering group offers 8192, 4096, and 2048 for the two local surface textures, 4096 is the default, and lower widths are halved from the 8K sources once and cached as PNG beside the cloud cache. Switching purges the textures in memory before the reload allocates, so going down returns the memory: measured 1259.7 MiB of private bytes at 8192 against 616.5 MiB at 2048 on the software adapter, the Moon's 2.7 MiB included in both. `--texture-resolution` overrides for one run without being saved. Phase 4, see [plans/2026-08-21-phase4-texture-resolution-plan.md](plans/2026-08-21-phase4-texture-resolution-plan.md).
- [x] The cloud variant follows the texture resolution: the setting picks which of the three published cloud sizes is downloaded, instead of the quality tier picking it, so lowering the width lowers the biggest texture the app holds along with the two surface ones. A switch retargets the fetcher and asks for a poll rather than purging the slot, so the clouds on screen stay until the new image lands and, offline, until the network comes back. The disk cache is keyed by variant. Phase 4.1, see [plans/2026-08-22-phase4-1-cloud-and-memory-report-plan.md](plans/2026-08-22-phase4-1-cloud-and-memory-report-plan.md).
- [x] A memory report worth reading: the `memory-report` IPC command prints four sections, the process counters, wgpu's internal counters, the backend allocator's live allocations, and the renderer's own expected table, with the last two side by side so a disagreement between them is visible. Top-N discipline throughout: the ten largest allocation groups of at least 1 MiB, everything else in one rollup line. Phase 4.1, same plan.
- [ ] Memory budget management: MSAA 8x at 4K uses 600+ MB in render textures (see [notes.md](notes.md)). Auto-reduce MSAA or cap resolution based on available memory. Partly addressed by the Phase 1 quality tiers, which cap the sample count and the preview width per tier (low, medium, high) and default to low in debug builds, and by the Phase 4 texture resolution setting, which is the same idea for the largest single allocation the app makes. Phase 4.1 made the soft private-bytes budget a function of that setting rather than one constant sized for the widest case; what remains is choosing either setting from the memory actually available rather than from the build profile or a saved preference.
- [x] Star field: 15,597 HYG v4.4 stars baked to a 244 KiB instance buffer, adjusted for proper motion to epoch 2026.0, and drawn as additive analytic sprites through one J2000 to world transform and a separately controlled stereographic sky lens. Horizontal field of view, brightness, crisp core size, glow strength, glow radius, contrast, and faintest magnitude are persisted controls. The blob ships beside its CC BY-SA 4.0 attribution and has no runtime parse. Phase A: [plans/2026-08-23-celestial-a-stars-plan.md](plans/2026-08-23-celestial-a-stars-plan.md).
- [x] Sun: two procedural quads, no assets and no new passes. The clipped white disk at its true 0.267 degree angular radius draws with the sky, where the painted globe covers it; the Spencer glare draws last over everything, faded by the fraction of the disk the globe leaves visible. Bloom, integer-hashed corona needles, a lenticular halo at three degrees, and a warm shift while the disk crosses the atmosphere band, all measured in degrees from the center by inverting the sky lens per fragment, so the composition holds across the 60 to 180 degree slider. Occlusion is measured against the painted silhouette rather than the true limb, which is what makes it agree with the picture rather than with an ephemeris; the cost is that it does not agree with an ephemeris, and the grazing golden is where that would show. Three persisted controls: glare, rays, and a camera mode with aperture spikes and ghosts that shipped off. That is phase B as it landed, and the item below is where the warm shift, the control count and the boost all moved: the disk and the glare are colored by the transmitted light path per fragment rather than by one orange keyed on the transit, there are twelve controls, camera mode ships at 0.15, and the `fs_rayleigh` forward-scatter boost that was tried here and removed at 0.007 of 255 came back as a Henyey-Greenstein lobe in the view ray, which is what the surface normal could not have given it. Phase B: [plans/2026-08-23-celestial-b-sun-plan.md](plans/2026-08-23-celestial-b-sun-plan.md).
- [ ] Bodies at the limb. The review of phase B found that the composite does not read well while the Sun's disk is partly behind the globe or barely clearing the horizon. The Sun's half of that has landed, in [plans/2026-08-29-celestial-b-amendment-sun-at-the-horizon.md](plans/2026-08-29-celestial-b-amendment-sun-at-the-horizon.md): the disk and the glare are colored per fragment by what the light path through the band leaves of the light, the glare's amplitude is the visible flux through a compressive response and an exposure that lags a Sun climbing out of the band, refraction lifts and flattens the disk, the Rayleigh shell carries a forward-scattering band around it, and nine new controls sit behind all of it. What is left is the Moon's half, and it is the harder one: an opaque Moon under the painted globe is a hard cut with no fade at all, and the composite hides it wherever it overlaps the painted silhouette, which is earlier than an ephemeris would. What the Sun's half leaves ready for it is `limb_transmission(position)` in `sphere.wgsl`, which takes a framebuffer position and nothing about the Sun, so `fs_moon` can call it unchanged; the squash would be a non-uniform scale on the model matrix toward the globe's center plus a lift, both cheap and on the CPU, and the fade in the lowest kilometers is what would soften the cut that draw order makes. `moon_crescent` is framed clear of the limb so it does not have to move when that lands. The lobe's own frame was wrong: it was measured in the true scattering angle while everything else about the limb is measured against the painted silhouette, so at the shipped 140 degrees of sky it fired before the Sun's image reached the limb and was gone when the disk appeared. [plans/2026-08-29-celestial-b-amendment-2-sunrise-at-every-zoom.md](plans/2026-08-29-celestial-b-amendment-2-sunrise-at-every-zoom.md) moved it into the sky lens, where the band now peaks under the emerging disk at every zoom, and verified the sunrise at 3.7, 9 and 40 Earth radii; at 2 the painted globe covers a 16:9 frame at the default 20 degree camera lens and there is no limb to judge, which is the one thing that amendment could not show.
- [x] Moon: a textured sphere at its true position, distance and IAU orientation, drawn with the sky through the same stereographic lens the stars use. Position from `Astronomy_GeoMoon` and orientation from `Astronomy_RotationAxis`, so the phase falls out of lighting the sphere with the shared sun direction and the near side faces the Earth to within the libration; the vertices are measured from the eye rather than the geocenter, which makes parallax and apparent size exact at every camera distance for free. Opaque and back-face culled, drawn after the Sun's disk and before the Earth, so a Moon crossing the Sun covers its body and the painted globe covers the Moon; the Moon is also a second occluder in the Sun's visibility arithmetic, so the glare fades behind it rather than burning around it. - [ ] The sky lens inverse costs three transcendentals it does not need. `sky_lens_direction` computes `theta = 2 * atan(t)` and then `sin(theta)` and `cos(theta)`, which are exactly `2t / (1 + t^2)` and `(1 - t^2) / (1 + t^2)`: three transcendentals for two divisions, with no approximation anywhere. The Milky Way's fullscreen draw pays for them on every pixel, which on a software adapter is 133 ms of a 1920 by 1080 frame on `warp` and 555 ms of a 4K one, against the cloud shell's 16; on a real adapter the whole layer is 0.2 ms and 0.9 ms. What it would buy is at best half of that, because the equirectangular map's own `atan2` and `asin` cannot go anywhere, so it would not reach the bound phase D's criterion 6 stated and did not meet. What it costs is a regeneration: the function is the Sun's glare's as well, so substituting it moves every golden reference on every adapter and belongs in a commit that contains nothing else. - [x] The release does not carry the runtime it needs: `sunlit-earth.exe` linked the Visual C++ runtime dynamically, and a clean Windows 11 has only the `_clr0400` copies that belong to .NET, so the app could not start on a machine that had never had a redistributable installed. Found on 2026-08-20 by the first `e2e --target windows`, where every case answered with `0xC0000135` and no output. Closed by linking the runtime in: `.cargo/config.toml` sets `-C target-feature=+crt-static` for `x86_64-pc-windows-msvc`, so every Windows build of this tree agrees, the e2e binaries included, and the `cc` crate follows it with `/MT` for the Astronomy Engine's C. `cargo xtask dist --target windows` is what proves it on the artifact: the builder runs `dumpbin /dependents` on the binary it just made and the host refuses a build whose imports name `vcruntime140.dll` or `msvcp140.dll`, because a guest with the redistributable installed runs a dynamically linked binary perfectly well and could never have shown the difference.
- [x] Release builds in a guest: `cargo xtask dist --target <windows|linux|all>` builds the binary in a pristine overlay of a builder image, from a `git archive` of HEAD, with the toolchain `rust-toolchain.toml` pins, and then runs it in the desktop image of the same target to prove it starts on a machine that did not build it. Nothing of the host reaches the build but the archive and the channel's name. `target/dist/<target>/` holds the binary, `build-info.json`, the builder's own log and the verification render. Phase 6, see [plans/2026-08-28-vm-release-build-plan.md](plans/2026-08-28-vm-release-build-plan.md). Two things were added on top of it, and the amendment that describes them is [plans/2026-08-29-release-build-amendment-cache-and-bundle.md](plans/2026-08-29-release-build-amendment-cache-and-bundle.md). The first is a release bundle beside the loose binary, a zip on Windows and a `.tar.gz` on Linux, carrying the textures, the license and the third-party notices, and on Linux the desktop entry and its installer; the verification boot runs *that*, with no `SUNLIT_EARTH_TEXTURES` set, and compares its render against one made with no textures at all, so a bundle whose lookup failed is refused rather than shipped. The second is a build cache on the host, two zstd archives per builder image, which takes a warm build to 4m 04s from 6m 58s on Windows and to 3m 49s from 5m 28s on Linux and can never decide what the binary is: `-m` on the source extraction with this workspace's own fingerprints dropped out of a restored cache behind it, so those crates are rebuilt whatever the guest's clock says, `--locked` on the registry, and the whole cache discarded when the channel or the image moves. `--no-cache` opts out and the record says per archive what happened.
- [x] Persistent builder guests: a builder guest is a compiler that survives between runs rather than a throwaway. `cargo xtask vm stop <builder>` asks the guest to shut down and keeps its overlay, `vm start` resumes it, and `vm down` is what frees it; a build reuses one it finds and leaves a builder it booted itself stopped rather than destroyed. That takes the Windows suite's staging build on a Linux host from a nine-minute cold compile to a seven-second freshness check, and a whole `vm up windows` from 12m 09s to 61s. Builders are also exempt from the one-guest rule in both directions, so a compiler may run beside the guest it compiles for and the boot says what the two hold together. The desktop guests are unchanged: every boot of one is still a pristine overlay, and `start` and `stop` refuse them for that reason. See [plans/2026-08-31-persistent-builder-guests-plan.md](plans/2026-08-31-persistent-builder-guests-plan.md), whose validation record carries the timings and the measurement that set the Windows builder's memory at 6 GiB.
- [ ] The Linux builder's glibc floor has a date on it: `linux-builder` is Ubuntu 22.04, so a release binary runs on glibc 2.35 and newer, and standard support for 22.04 ends in April 2027. The successor is 24.04 at glibc 2.39, which is one line in `vm/linux-builder/ubuntu-2204.pkr.hcl` and a rebuild; taking it raises the floor and drops 22.04 users, so it is a decision rather than a chore.
- [ ] A kept QEMU guest holds a pipe on the command that started it. `cargo xtask vm smoke linux-builder --keep | tail` never terminates on a Windows host, while the same command redirected to a file exits as it should, so the reader is waiting for a writer that outlives the xtask. Only a kept guest can show it, since every other path ends the guest before the command returns. The cause is unconfirmed and the candidate is handle inheritance rather than the redirection: `Runner::spawn` gives QEMU the `vm.log` file for stdout and stderr, and a Windows `CreateProcess` with inheritance on hands the child every inheritable handle the parent holds, the pipe on the parent's own stdout included. Reported by validator round 3 of the release-build work, out of that round's range and left as it was found.
- [ ] The Windows builder is a Windows 11 layer, which inherits its parent's ninety-day evaluation clock: a Windows desktop image rebuilt for expiry costs the layer's few minutes on top of the hour. A Windows Server Core base would be about 7 GB smaller and its evaluation runs 180 days, at the cost of a second ISO, a second unattend file and an install path nobody has measured. - [x] Hosted CI is manual only: `ci.yml` is `workflow_dispatch` and no longer runs on pushes or pull requests. The reason was that the repository was private and its Actions minutes were billed; it has been public since the 0.1.0 release, so standard runners are free and unmetered and that reason is gone. What is left is that the local VM suite plus `cargo test` on the development host cover what the runners were for, which is an argument about noise rather than about budget, and a weaker one: putting `ci.yml` back on pushes and pull requests is now open, and this entry is where it is carried. What a dispatch still buys is Linux and macOS, so it wants running before anything that has to hold on all three, and the macOS branch is what happens when nobody does: two of the three jobs had gone red on `main` and no document said so, both for the same reason, dead code that is only reached from a `cfg`-gated arm and `RUSTFLAGS: -D warnings`. - [x] The dev target directory grew without a ceiling: 119 GiB on the development host, 101 of it under `target/debug`, where `deps/` held 61 GiB (26 GiB of rlibs, 20 GiB of pdbs, 8 GiB of rmeta) and `incremental/` held 38 GiB across 481 unit directories. Three causes, one fix each. Dependencies were built with the dev profile's full debug info on top of `opt-level = 2`, and the linker copies that into a pdb per binary, so every integration target carried a 300 MB one and the app's own was 344 MB; `[profile.dev.package."*"]` now sets `debug = false`, which leaves symbol names intact and drops only the file and line of a dependency's frames. That takes the app's pdb to 87 MB and a freshly built tree with every target linked to 4.5 GiB. A WSL build with `CARGO_TARGET_DIR` unset had also written a complete Linux artifact set into the Windows directory: 13 ELF executables at 4.5 GiB, 88 `.so` at 897 MB, and a 751 MB `target/debug/sunlit-earth` beside the 47 MB `.exe`. Nothing collides when that happens, because the target triple is part of every artifact hash, so cargo reports nothing unusual and the two sets simply accumulate; `sunlit-app`'s build script now records the triple in `<profile>/.built-for` and fails a build whose own disagrees. That is the earliest hook cargo offers and it is still not early, since a build script runs only once the dependencies are compiled, so it catches the linked binaries rather than every rlib. The third cause is cargo's design: it removes nothing it has stopped using, which is how 507 distinct crates came to stand behind 3871 rlibs, 45 of them copies of `windows_sys`. `cargo xtask sweep` answers that one, and it is deliberately a chore rather than a build step. Not in CI, where the runners are ephemeral and `Swatinem/rust-cache` prunes before saving; not per build either, where it would walk 7450 fingerprint directories every time, and in its `--stamp`/`--file` shape would delete whatever the last build did not touch, which in this workspace means relinking the integration targets on the next `cargo test`. What makes its age pass trustworthy is that cargo-sweep dates an artifact by the access time of its fingerprint files, and cargo reads those for every unit in the graph whether or not it recompiles it, so the question it really asks is "has any build needed this": `cfg-if` here was compiled on 2026-03-21 and reused ever since, and carried an access time from the day of the measurement. That holds only where the volume records access times, so the command reads `fsutil behavior query DisableLastAccess` and skips the age pass instead of trusting it where they are off. Neither pass reaches `incremental/`: of the 21,639 files a `--maxsize 1` dry run named here, none were in one, so the command reports what those hold and leaves deleting them, which costs a cold build of this workspace's own crates, to a person.
