# Roadmap

Features and improvements planned for Sunlit Earth, roughly ordered by priority within each category.

## Wallpaper app

- [x] Wallpaper export and setting: save rendered frame to an image file and set it as the desktop wallpaper via OS APIs. Windows (`SystemParametersInfoW` via `windows-sys`) and Linux (a per-desktop setter, see the entry below) implemented. macOS still returns the plain "not supported on this platform yet" that the status line shows; the headless `render` subcommand is the cross-platform mode there.
- [ ] Periodic re-rendering: timer-driven scheduler that re-renders every N minutes so the terminator tracks the sun. Update interval should be user-configurable.
- [x] System tray icon: minimize to tray on window close with "Open" / "Exit" context menu, single-instance enforcement, `--windowed` flag for original close-exits behavior (Windows only).
- [x] System tray extended features: "Refresh Now" and a checkable "Auto-refresh" entry are in the tray menu, and the engine runs headlessly with no window at all (the `render` subcommand creates no window and no Slint backend). A long-running daemon mode with no settings window is still open.
- [ ] About window: an "About" entry in the tray context menu, plus a control in the settings window since windowed mode has no tray, opening a window with the version and the asset and data attributions. Needed by the star catalog credit (HYG v4.4, CC BY-SA 4.0) and the NASA SVS credit lines; ships with the star plan, [plans/2026-08-23-celestial-a-stars-plan.md](plans/2026-08-23-celestial-a-stars-plan.md).
- [x] App icon: the mark (night-side globe, bold outline, tilted aurora arcs, the sun rising occluded behind the limb) is an SVG master plus 32/24/16 variants under `assets/icon/`, and `cargo xtask bake-icon` turns them into every raster the app shows: the nine-size `.ico` embedded in the exe, the 32 px tray bytes, the About PNG, and the freedesktop hicolor set that goes with `assets/linux/sunlit-earth.desktop`. The settings window takes its own icon from the SVG master through Slint. Verified in the Linux guest under KDE and XFCE (the tray and the title bar, and the taskbar entry once `install-user.sh` has run, since a task manager draws the entry its `WM_CLASS` matches) and on Windows (the exe's group icon, and `WM_GETICON` on the running window). One half is not verified: what the KDE launcher search offered was the running window rather than the installed entry, so Kickoff's indexing of a fresh install is unobserved. The 16 and 24 px rasters were judged on real shells on 2026-08-24: good enough to ship, with the 16 px variant a candidate for a later nudge. System packaging (deb, Flatpak, AppImage) and the macOS `.icns` stay with the cross-platform release item below, which consumes the same assets. Plan: [plans/2026-08-23-app-icon-integration-plan.md](plans/2026-08-23-app-icon-integration-plan.md).
- [x] Configuration persistence: save and load settings (camera position, update interval, rendering options) between launches.
- [x] Wallpaper setting on Linux: `desktop.rs` is a table of per-desktop setters chosen by `XDG_CURRENT_DESKTOP`, and `display.rs` is the native display query that came with it, which replaced both placeholders Phase 2 left behind: the 2560x1440 default in `wallpaper_sink` and the coordinate-range window-position check in `config`. Phase 5, see [plans/2026-08-21-phase5-linux-vm-and-parity-plan.md](plans/2026-08-21-phase5-linux-vm-and-parity-plan.md).
- [ ] Wallpaper setting on macOS: `osascript` or `NSWorkspace`, plus the native display query that goes with it. `wallpaper_sink` still refuses there before rendering anything, which is the honest answer and not a stub.
- [ ] Three of the Linux wallpaper backends ship reviewed rather than exercised. The test guest boots KDE, GNOME, XFCE and Cinnamon, and all four were run with the desktop screenshotted afterwards, so those four are observed, Cinnamon's only after restarting its crashed shell by hand, which is the session defect its own item below carries; MATE, LXQt and Budgie are one table row each, written from their documented setters and never run. Adding any of them to the guest image is the cheapest way to close that, at one to two GB of image each, and the desktop-share research that picked the four put all three of these in the noise.
- [ ] Wallpaper setting under Wayland is untested, though it should need nothing: every backend in the table is a desktop-shell operation, so it is the same command in a desktop's X11 and Wayland sessions. What does differ is the two things the guest contract needs, which is why the guest stayed on X11: `DISPLAY` for a process the orchestrator starts over SSH, and a client's ability to place its own window. The app icon adds a third thing for that session to check: under Wayland a launcher matches a window to its desktop entry by app id rather than by `WM_CLASS`, and winit sets no app id unless asked, so the association that works on X11 today may need one line there.
- [ ] The Linux display query is `xrandr`, so under a Wayland session it answers through XWayland, where display scaling can skew the reported size. The native answer is a per-desktop D-Bus call, which is a different table from the wallpaper one and worth having only once a Wayland session is something the suite runs in.
- [ ] Linux session end handles SIGTERM and nothing else, which means it uses the grace period a session gives a process it has already decided to close. The other half of the conversation is logind's inhibitor protocol, over the session bus, which is how an application gets *asked* first, the way `WM_QUERYENDSESSION` asks on Windows. That needs a D-Bus dependency and has no test the suite can run without a session bus, so it is deferred rather than half-built.
- [ ] Cinnamon's session in the Linux test guest starts its shell, loses it a second later, and falls back to `metacity`, which the image does not install, so a login leaves a modal "Cinnamon just crashed" dialog over a black desktop. Nothing the suite does is affected: the cases run over SSH through `DISPLAY` and all ten pass, and `cinnamon --replace` over `vm ssh` restores the shell and the wallpaper with it. Reproduced on two fresh boots, so it is deterministic. What is unknown is why the shell is signalled; its own log says it started cleanly in 799 ms with every applet loaded, and the journal reports no segfault and no out-of-memory kill. Installing `metacity` would make the fallback a working window manager rather than a Python traceback, which is a better symptom and not a fix.
- [ ] The guest's quiet-down turns off Baloo and nothing else that indexes. `localsearch-3`, which is what trixie calls tracker-miners, was seen running in the XFCE session, and the same package answers for GNOME and Cinnamon: the plan wanted file indexing off in every desktop and `desktop.sh` writes `baloofilerc` only, so three of the four still index a test suite's output. Harmless to the results and a waste of a throwaway guest's CPU. The fix is one more config file, or the `localsearch` user units masked, at the cost of an image rebuild.
- [ ] Two of the guest's four sessions have no polkit authentication agent. `polkit-kde-agent-1` is the only agent the image installs and its autostart entry says `OnlyShowIn=KDE;`, so Plasma gets it, GNOME is its own agent inside `gnome-shell`, and XFCE and Cinnamon get none: `polkitd` is running and nothing is listening for it, so an operation needing authorization there fails instead of prompting. Nothing the suite does asks for one, which is why this is a note and not a blocker. The fix is one package plus an autostart override in `desktop.sh`, at the cost of an image rebuild.
- [ ] GNOME's session in the guest opens the Activities overview at login, which is its own default with no window on screen. Harmless to the suite and confusing to a person looking at the console; one Escape closes it, and an autostart entry or a shell setting would close it for good.
- [ ] Multi-monitor support: detect monitor layout and resolution, render appropriately sized wallpapers for each display.

## Rendering

- [x] Blue Marble water brightness: ocean areas are too dark and sometimes contain satellite imagery. Pre-process textures to get a uniform ocean color, preserving different extents of sea ice per season
- [x] Color correction: Rendered textures still look darker than their sources. Investigate if there is a color space issue to resolve and provide in-app texture processing to adjust e.g. gamma and saturation (current image may be oversaturated)
- [x] Water on the day side looks matte and more like a solid surface that happens to be blue. Investigate what kind of effect can be applied to make it look more like actual water. First iteration: specular sun glint (Blinn-Phong). Second iteration: Schlick Fresnel for specular modulation and diffuse color shift toward sky at grazing angles, with UI sliders for mix strength and extent.
- [ ] Seasonal texture switching: auto-select from the 12 monthly NASA Blue Marble variants based on the current month.
- [x] Atmosphere glow / Airglow: three physically-motivated layers (Rayleigh scattering, orange nightglow, green nightglow) with separate controls.
- [x] Cloud overlay: semi-transparent cloud layer from near-real-time satellite data. Requires researching data sources (GOES/Himawari composites, etc.) and building a download + caching pipeline.
- [ ] Make clouds less intense over land, since our cloud data sources have a bias towards creating a haze of clouds over land.
- [x] Texture resolution selection: the Rendering group offers 8192, 4096, and 2048 for the two local surface textures, 4096 is the default, and lower widths are halved from the 8K sources once and cached as PNG beside the cloud cache. Switching purges the textures in memory before the reload allocates, so going down returns the memory: measured 1251.5 MiB of private bytes at 8192 against 610.9 MiB at 2048 on the software adapter. `--texture-resolution` overrides for one run without being saved. Phase 4, see [plans/2026-08-21-phase4-texture-resolution-plan.md](plans/2026-08-21-phase4-texture-resolution-plan.md).
- [x] The cloud variant follows the texture resolution: the setting picks which of the three published cloud sizes is downloaded, instead of the quality tier picking it, so lowering the width lowers the biggest texture the app holds along with the two surface ones. A switch retargets the fetcher and asks for a poll rather than purging the slot, so the clouds on screen stay until the new image lands and, offline, until the network comes back. The disk cache is keyed by variant. Phase 4.1, see [plans/2026-08-22-phase4-1-cloud-and-memory-report-plan.md](plans/2026-08-22-phase4-1-cloud-and-memory-report-plan.md).
- [x] A memory report worth reading: the `memory-report` IPC command prints four sections, the process counters, wgpu's internal counters, the backend allocator's live allocations, and the renderer's own expected table, with the last two side by side so a disagreement between them is visible. Top-N discipline throughout: the ten largest allocation groups of at least 1 MiB, everything else in one rollup line. Phase 4.1, same plan.
- [ ] Memory budget management: MSAA 8x at 4K uses 600+ MB in render textures (see [notes.md](notes.md)). Auto-reduce MSAA or cap resolution based on available memory. Partly addressed by the Phase 1 quality tiers, which cap the sample count and the preview width per tier (low, medium, high) and default to low in debug builds, and by the Phase 4 texture resolution setting, which is the same idea for the largest single allocation the app makes. Phase 4.1 made the soft private-bytes budget a function of that setting rather than one constant sized for the widest case; what remains is choosing either setting from the memory actually available rather than from the build profile or a saved preference.
- [ ] Star field: astronomically correct background stars. Researched, with a recommended approach (catalog point sprites over one J2000-to-world rotation): [plans/2026-08-23-celestial-bodies-research.md](plans/2026-08-23-celestial-bodies-research.md). Plan: [plans/2026-08-23-celestial-a-stars-plan.md](plans/2026-08-23-celestial-a-stars-plan.md).
- [ ] Sun: a visible disk with perceptual glare (bloom, radial needles, lenticular halo, optional camera-style flare), analytically occluded by the Earth with a sunrise transit at the limb. Same research document, section 5. Plan: [plans/2026-08-23-celestial-b-sun-plan.md](plans/2026-08-23-celestial-b-sun-plan.md).
- [ ] Moon: rendered at correct position and phase. Same research document; the phase falls out of true-scale placement plus the shared sun direction. Plan: [plans/2026-08-23-celestial-c-moon-plan.md](plans/2026-08-23-celestial-c-moon-plan.md).
- [ ] Visible planets: at correct positions. Same research document; five extra sprites through the star pipeline, so they land with the star plan: [plans/2026-08-23-celestial-a-stars-plan.md](plans/2026-08-23-celestial-a-stars-plan.md).
- [ ] Milky Way background: the diffuse sky as a texture layer (NASA SVS Deep Star Maps 2020, Milky-Way-only layer), separate from the point stars. Same research document. Plan: [plans/2026-08-23-celestial-d-milky-way-plan.md](plans/2026-08-23-celestial-d-milky-way-plan.md).
- [ ] Eclipse visualization. Sketched in the same research document (section 6.5), deferred until the Moon exists.
- [x] Specular highlights on oceans.

## Camera and controls

- [x] Offset / pan: shift the camera north/south or east/west so the Earth doesn't have to be centered in the frame.
- [x] Tilt: rotate the camera around its view axis for angled compositions.
- [x] Zoom curve: zoom should be slower when close to the Earth and faster when far away. Extend the zoom range limits.
- [x] Improved Controls: Rotate Earth with mouse drag, Zoom with scroll wheel in addition to existing UI controls.
- [x] Preset camera views: quick-select buttons for common viewpoints (Europe, Americas, Asia, etc.), as well as recreations of iconic photographs (blue marble, earthrise). Implemented as a 3x3 grid of preset buttons with `PRESETS` constant array.
- [x] Change date and time of day: checkbox to enable custom date/time, sliders for hour (UTC) and day of year, year dropdown. Implemented with proper leap year handling and live sun position updates.

## CI and distribution

- [x] CI pipeline: GitHub Actions workflows for building, testing, and linting on Windows. GPU integration tests run on the software adapter. Release workflow builds and publishes Windows binaries on version tags.
- [x] CI lint gates: the codebase-wide reformat and the warning cleanup landed in Phase 2, so `ci.yml` runs a `fmt` job again and sets `RUSTFLAGS: "-D warnings"`. Clippy stays a local command: its artifacts do not share the test cache and running it in CI would force a full recompile.
- [x] Cross-platform build and test: the workspace builds, tests, and renders headlessly on Linux (lavapipe) and macOS (Metal), and CI is a three-OS matrix. Phase 2, see [plans/2026-08-15-phase2-cross-platform-plan.md](plans/2026-08-15-phase2-cross-platform-plan.md).
- [x] Desktop e2e in local VMs: `cargo xtask` orchestrates a Windows guest on Hyper-V and a Linux guest on QEMU, builds the golden images, and runs the suite in the guest's console session. Phase 3, see [plans/2026-08-19-phase3-vm-orchestration-plan.md](plans/2026-08-19-phase3-vm-orchestration-plan.md) and [vm-setup.md](vm-setup.md). Implemented, unit-tested end to end, and proved live on Windows: `vm build-image windows`, `vm smoke windows`, and `e2e --target windows` all pass on the development host, the last of them with all ten cases including the wallpaper one. The Linux guest's own e2e run is still unmade. The builder matrix mirrors the runtime provider matrix: Packer and QEMU everywhere except the Windows image on a Windows host, which the xtask installs natively on Hyper-V because a WHPX guest does not survive the reboot Windows Setup performs after copying its files (deviation 25 in the plan, and [plans/2026-08-20-phase3-amendment-hyperv-windows-build.md](plans/2026-08-20-phase3-amendment-hyperv-windows-build.md) for the design of the native install and the cleanup that went with it).
- [ ] The release does not carry the runtime it needs: `sunlit-earth.exe` links the Visual C++ runtime dynamically, and a clean Windows 11 has only the `_clr0400` copies that belong to .NET, so the app cannot start on a machine that has never had a redistributable installed. Found on 2026-08-20 by the first `e2e --target windows`, where every case answered with `0xC0000135` and no output. The golden image now installs the redistributable so the suite runs; the product side is unaddressed. The options are to ship the redistributable with the release, to link the CRT statically (`-C target-feature=+crt-static`), or to say so in the release notes.
- [x] Hosted CI is manual only: `ci.yml` is `workflow_dispatch` and no longer runs on pushes or pull requests. The repository is private, so its Actions minutes are billed, and the local VM suite plus `cargo test` on the development host cover what the runners were for. What a dispatch still buys is Linux and macOS, so it wants running before anything that has to hold on all three.
- [ ] Cross-platform release builds: `release.yml` still builds Windows only. Produce binaries for Linux and macOS too and publish them as GitHub release artifacts.
- [ ] Golden reference regeneration: `golden.yml` is the intended route, but GitHub only registers a dispatchable workflow once it is on the default branch, so it becomes usable after this branch merges. The `warp`, `lavapipe`, and `metal` sets all exist; until the workflow is dispatchable, regenerate on the adapter in question with `SUNLIT_EARTH_UPDATE_GOLDEN=1`.

## Bugs and polish

- [ ] Memory leak in tray mode: decoded 8K cloud textures (~134 MB each) accumulate in the unbounded texture channel because the only consumer (`process_decoded_textures`) runs in `BeforeRendering`, which stops firing while the window is hidden. Observed: 7.3 GB RSS after 10 days. Analysis in [retrospective-2026-08.md](retrospective-2026-08.md) section 4.1. **Fix landed** (`TextureMailbox` plus a 5-second drain timer, see [plans/2026-08-15-phase0-memory-leak-plan.md](plans/2026-08-15-phase0-memory-leak-plan.md)): the e2e regression test `test_hidden_window_cloud_updates_do_not_grow_memory` went from 120.4 MiB to 1.8 MiB of private-bytes growth across 15 hidden cloud updates. Left unchecked pending the multi-day validation in retrospective section 8.2.
- [x] Non-blocking texture loading: the main window used to be unresponsive while textures loaded, because mipmap generation and GPU upload ran on the UI thread inside `BeforeRendering` and the cached cloud JPEG was decoded synchronously at startup. Resolved by the Phase 1 restructure ([plans/2026-08-15-phase1-restructure-plan.md](plans/2026-08-15-phase1-restructure-plan.md)): decode and mip generation happen on engine-owned threads, and the UI thread only copies finished pixel buffers into a `slint::Image`.
- [x] Diffuse shading banding on JPEG wallpapers: fixed by switching the wallpaper export format from TIFF to PNG. Windows preserves PNG wallpapers losslessly (no JPEG transcode), eliminating the banding artifact.
- [x] Refactor `main()`: extract mouse math into `mouse_math.rs` (with unit tests and proptests), UI callback registration into `ui_callbacks.rs`, and initialization into sub-functions. Removed `clippy::too_many_lines` suppression.
- [x] The app blocked a Windows reboot: Windows names the applications that have not exited after it ends the session, and this was one of them. It asks every top-level window with `WM_QUERYENDSESSION` and then tells it with `WM_ENDSESSION`; winit handles neither, so nothing here ever learned that the machine was going down. `session_end.rs` listens on an invisible top-level window of its own, permits the shutdown, and quits the event loop when the session really ends, with a guard that exits the process if the ordinary teardown has not finished in three seconds. Covered by unit tests for the decision, a Win32 test for the window, and an e2e case that sends the real binary both messages and asserts it exits in under five seconds. Windows' own delivery of those messages to a never-shown window is the one link only a real reboot exercises; the log line to look for is "windows is ending the session".
- [ ] Automated slint UI testing
- [ ] The WSL gate leg still carries one flake: `tests/shading.rs` dies in wgpu-hal's gles/egl layer with a BadAccess on roughly one run in five, and reproduces at commits predating phases 4 and 4.1. It wants a root cause or a documented skip under WSL. The two xtask path-separator failures that used to sit beside it are fixed in Phase 5: the boot-image constants are path components joined with the host's own separator, and the vmconnect settings test compares components rather than a backslash literal.
- [ ] No test in CI decodes a real JXL texture. `textures/**` is Git LFS, `actions/checkout` does not fetch it, and the CI smoke step points at an empty directory on purpose, so every job renders the procedural grid. The 8K decode, the mipmap upload for a real texture, and the blend-mode composite are therefore covered nowhere automated, which is the same region the `textures_ready` defect below lives in. The e2e render case does cover them wherever the assets are on disk: on a developer's desktop, and in a VM guest since `e2e --target <guest>` stages them (departure 38 of the Hyper-V amendment), which is a local run and not a gate. Turning on `lfs: true` would close it at the cost of pulling the assets on every run on every OS against a shared bandwidth quota; a small committed JXL fixture that exercises the decode path without the 8K assets is the cheaper shape, and belongs with the asset-pipeline work.
- [ ] `Renderer::textures_ready` never becomes true when a texture is missing or fails to decode, so `TexturesReady` is an event that cannot arrive and every client waiting on it waits forever. A failed decode clears `source_path` so it is not retried, which leaves the slot in exactly the state an unconfigured slot is in: no bind group, no path, not loading. Both are terminal and both should read as ready. Blend mode additionally requires `composite_bind_group`, which can never be built if either texture is absent, so that condition needs the same treatment. Surfaced in Phase 2 by CI, where `textures/**` is Git LFS and `actions/checkout` leaves pointer files that fail to decode as JXL; `run_render` has a local guard for the missing-file half, and the smoke step points at an empty textures directory to keep CI deterministic. The general fix belongs with the asset-pipeline work.
