# Testing

The test layers, the conventions every layer follows, and the hosted CI that runs them. What each platform can and cannot assert, and how the desktop e2e cases gate themselves, is in [platforms.md](platforms.md); running the e2e suite in a local VM is in [vm-setup.md](vm-setup.md).

## Running checks

From the repository root:

```bash
cargo test --workspace
cargo unit
cargo clippy --workspace --all-targets
cargo fmt --check
```

`cargo unit` runs unit tests without the integration targets. Clippy includes the workspace's pedantic lint configuration. For an HTML coverage report, install `cargo-llvm-cov` and run:

```bash
cargo llvm-cov --html
```

The report is written under `target/llvm-cov/html/`. GPU and desktop requirements still apply to the tests being measured. See [building.md](building.md) for native dependencies, including lavapipe and the optional virtual display used by CI. The soak suite simulates 14 days with a mock clock; the old README recorded a runtime of about 13 seconds, which is a measurement rather than a timing guarantee.

## Layers

| Layer | Where | What | Runs on |
|---|---|---|---|
| Unit + property | both crates | pure functions, `proptest` invariants | all three |
| Engine integration | `sunlit-core/tests/engine/` | real engine, real GPU, headless | all three |
| Soak | `sunlit-core/tests/soak.rs` | mock clock, fixture cloud, 14 simulated days | all three |
| Golden images | `sunlit-core/tests/golden.rs` | fixed scenes, software adapter, perceptual tolerance | all three, per-adapter references |
| GPU shader | `sunlit-core/tests/{shading,render_pipeline}.rs` | real WGSL on the GPU | all three |
| UI logic | `sunlit-app/tests/slint_ui.rs` | `i-slint-backend-testing` | all three |
| Desktop e2e | `sunlit-app/tests/e2e.rs`, harness in `tests/common/` | the real binary over IPC, `#[ignore]`d | built everywhere; `cargo e2e` on the desktop, `cargo xtask e2e --target <windows\|linux> [--desktop <d>] [--session-type <x11\|wayland>] [--screens <n>]` in a VM |
| VM orchestration | `crates/xtask/src/**` | pure decision logic against fabricated hosts, no VM | all three |

## What a display-less machine can prove about several displays

Almost all of the multi-monitor work is decided on a machine with one screen, and that is a property of how the code is split rather than a happy accident. `display::layout` is a pure function from a list of rectangles to a canvas size, a modified framing and a set of crops, so every layout question is answered against fabricated monitor lists: side by side, stacked, unequal heights, a portrait secondary, negative origins, a gap, two identical rectangles, one monitor, no monitors, a monitor with a zero dimension. `tests/engine/`'s `RecordingSink` reports a fabricated layout to a real engine and keeps what it was handed, which is what proves the engine asks for the right images in each mode with no display anywhere; `desktop.rs`'s table is asserted per row against fabricated two-monitor sessions; and the two GPU cases render a real canvas and compare the anchor's crop against its standalone render. All of that runs in CI on all three operating systems.

What is left is exactly three things, and each has one place it can be checked. That a real session's monitors come back with the rectangles it actually has is answered by `test_displays_reports_the_session_layout` in the guest, which compares what the running app reports over IPC against what the test process gets from the same platform query. That a real desktop holds what the mode said it should is answered by `test_set_wallpaper` and `test_across_screens_writes_what_this_desktop_can_hold`, which read the setting back out of the desktop rather than trusting an exit code. That a layout which really changes reaches the app is answered by `test_a_layout_change_republishes_the_wallpaper`, which switches an output off with `xrandr` from the test process and waits for the app's own account of what happened.

The display-change path is the same split. The settle, the comparison and the two edges of the republish rule are five cases in `tests/engine/` on a `MockClock`, with a `RecordingSink` whose monitor list moves under the running engine and whose query count is what says a settled burst was one query. `display::watch` itself is start-and-stop on each platform: on Linux, against whatever X server the run has, which proves the connection, the extension check, the `select_input` and the wake, and skips with a printed reason where `DISPLAY` is unset; on Windows, by sending `WM_DISPLAYCHANGE` to the listener's own window the way `session_end`'s test does, which is the only way to produce it in a guest whose video is a single fixed mode. `tests/slint_ui.rs` takes the window from two screens to one and back and asserts the combo rows, the tile count, the hidden group and the anchor returning to its own row.

`test_a_layout_change_republishes_the_wallpaper` is what none of that reaches: a real RandR change waking a real watcher, the settle collapsing a real burst, and a real desktop being handed images for the layout it has now. It asks the session which change it can make. With two outputs it switches the non-primary one off, which is the case the feature was written for and the only one that moves the screen count. With one it switches that output to another of its modes, which is the same event and the same comparison, and is what runs on a host whose QEMU cannot give the guest two heads. Either way it waits for `SIGNAL:displays_changed` and then for the publish, checks that every path changed and that the sizes match the layout the session now has, and puts the layout back from a guard so a failing assertion cannot leave the guest one-screened, or at the wrong mode, for the cases after it. It checks that its own change took before waiting on anything, and skips with a printed reason where the session put its layout straight back. What is left after that is a Windows-only hand check on real hardware, because no guest can undock a notebook; `docs/roadmap.md` carries it beside the other Windows questions.

The Linux guest runs the suite in eight sessions: KDE, GNOME, XFCE, Cinnamon and i3 on X11, and KDE, GNOME and sway on Wayland (`--session-type wayland` for the first two). Under Wayland the app is a Wayland client, and `test_the_window_is_a_client_of_the_sessions_display_server` is what says so: it reads the app's `SIGNAL:windowing` line, taken from the window's own raw handle, and requires it to match `XDG_SESSION_TYPE`, so a Wayland run whose app came up through Xwayland fails rather than passing every other case as an X11 client. `test_a_layout_change_republishes_the_wallpaper` skips under Wayland before its own gate, which would find the outputs through Xwayland and then change nothing; the other two layout cases run and read the layout through Xwayland. The earlier measurement, on 2026-09-23 on the image rebuilt for Wayland and before sway, i3 and the sixteenth case were added: the six sessions of that image passed all fifteen cases, with the skips each session's tray and desktop account for, and the desktop screendumped after each run showed the app's globe as its wallpaper.

The setter fallbacks added a sixteenth case off Windows, `test_displays_names_the_wallpaper_setter`, which prints the `setter:` line of `sunlit-earth displays` and requires it, and three read-backs in `tests/common/desktop_linux.rs` for setters whose writes the command-derived read-back cannot follow: under the root pixmap `_XROOTPMAP_ID` must name a new pixmap after each publish and the previous one must be gone, which is the leak check; under the owned `swaybg` exactly one `swaybg` may name a file under the wallpaper directory, the newest; under the portal GNOME's key must name a file whose bytes are the published image, since GNOME's backend copies it to `~/.config/background`. The cases that compare published files skip under the root pixmap, which writes none. `SUNLIT_EARTH_WALLPAPER_SETTER` on the host is passed into the guest's suite, which is how the rungs a session would not reach by itself are run. On 2026-09-23, on the image rebuilt for the fallbacks, KDE and GNOME on both session types, XFCE, sway and i3 passed all sixteen, each printing its setter and each with the globe in the screendump; Cinnamon passed fifteen, because its shell had crashed, the Cinnamon row's process gate declined, and the desktop-window probe, which then read only `_NET_CLIENT_LIST`, missed nemo-desktop's window and painted the root under it. With the probe reading the root's children where that list is missing, Cinnamon passed all sixteen on the next boot with the globe on screen; its shell was up that time, so the row was chosen by its gate, and in the same guest with `cinnamon` killed and `_NET_CLIENT_LIST` removed from the root, `sunlit-earth displays` chose the Cinnamon row through nemo-desktop's desktop window. Forced, the owned `swaybg` in sway passed all sixteen, and the portal in GNOME passed fifteen: its permission question needs an answer, which a watcher on the host gave by matching the dialog in a screendump and clicking through `xdotool`, and the layout change case, whose publish raised the question before the watcher saw it, had its republish refused while it was open.

The two-head guest is `cargo xtask e2e --target linux --screens 2`, and what it costs the image is two packages: `xinput`, without which QEMU's single absolute pointer covers the whole desktop and clicks at twice the x it was aimed at, and `arandr`, a display settings UI that works in every session where the minimal Plasma install has none. Measured in the Debian guest on 2026-08-31: both connectors come up connected at the rectangles the boot placed them at, `display::monitors()` reports exactly those, and the pointer maps to the primary output. What the guest cannot show is Windows' own behavior with more than one monitor: the Hyper-V synthetic adapter has no multi-monitor mode, so the Windows guest exercises the whole new path, COM plumbing and id mapping and read-back included, at one monitor only. Mixed DPI is a Windows question that no guest of either kind answers today; see [platforms.md](platforms.md).

## Conventions

- **Test behavior, not constants.** Changing a preset or a default must not break a test.
- **Float comparisons**: `approx::assert_relative_eq!`. `tests/shading.rs` predates this and keeps its own GPU tolerance pattern.
- **GPU tests assert invariants** (monotonicity, bounds, visibility), not exact pixels, because of cross-adapter float variance.
- **A test that changes one thing and diffs two frames owns the whole frame, not the thing it changed.** Adding a draw to a pass can move pixels that draw cannot reach, by a step, on an adapter that rounds in tile memory; the measurement is under "Measurements behind the thresholds". Read a diff as evidence only where the thing under test could have reached.
- **One GPU device at a time.** Per-test device creation crashes on Windows. Shader tests share a device through `LazyLock<Mutex<GpuContext>>`; the engine and soak targets each hold a `GPU_SERIAL` mutex for the lifetime of their engine, and the golden target serializes on the `LazyLock<Mutex<EngineHandle>>` it shares one engine through.
- **One wgpu instance per process, ever.** `wgpu_init::instance()` holds it in a `OnceLock` and nothing else may call `wgpu::Instance::new`; `clippy.toml` enforces that through `disallowed-methods`, so a second call site has to allow the lint by name. An instance owns the loaded driver libraries, and dropping the last one `dlclose`s the Vulkan loader while Mesa's pthread TLS destructors still point into it, so the next thread to exit dies in `__nptl_deallocate_tsd`. That is not theoretical: it killed all 14 engine tests on lavapipe.
- **Golden images** force the software adapter where the platform has one, so a developer machine and a CI runner compare against the same references. References are per adapter (`tests/golden/warp/`, `lavapipe/`, `metal/`), keyed by `wgpu_init::adapter_key`, which carries the rule; the measured cross-adapter deltas that justify the split are under "Measurements behind the thresholds" below. Which adapters have a set is listed in the test's `GENERATED_ADAPTERS`, not inferred from the filesystem: an adapter on the list whose directory is missing fails, and only an adapter that has genuinely never been generated skips. A missing single case fails every run, with its render written under `CARGO_TARGET_TMPDIR` for review rather than into the tracked tree. Tolerance: mean channel difference under 2/255 and at most 1% of pixels differing by more than 24. A companion test asserts every pair of references is distinguishable, which is what stops the others from becoming vacuous.
- **Every committed bake is compared against a fresh one.** `the_committed_bake_matches_a_fresh_one` in `bake_icon` and `bake_licenses`, and `the_committed_fixture_matches_a_fresh_bake` in `bake_stars`: the outputs of `cargo xtask bake ...` are data in the tree rather than something a build produces, so a source edited without rerunning the bake has to fail the suite. The licence one is the only bake test that can skip: it needs `cargo metadata`, `cargo tree` and the unpacked registry sources the manifests point at, so on a checkout that cannot resolve the tree it prints why and returns, the way the tests that need the real 8K assets do.
- **Scratch directories come from `ScratchDir`** in `crates/sunlit-core/src/test_support.rs`: the name carries the process id and a counter, and `Drop` removes the tree, so two `cargo test` runs over one checkout never share a directory and a test that panics leaves nothing behind. The library reaches it as a `cfg(test)` module; the integration targets take the same file by `#[path]`, which keeps `tests/common`'s GPU context out of a binary that must not create a second device. It roots under `CARGO_TARGET_TMPDIR` where cargo sets one, which is every integration target, and under the system temporary directory for a library's own unit tests. Note that it creates its directory, so a test asserting that production code creates a parent must name a path below the scratch root that does not exist yet, or the assertion is vacuous.
- **`cargo doc --no-deps` does not see inside private items.** A doc link in a private or `pub(super)` item is
  unchecked by the plain form, so it can rot invisibly, and every module split manufactures more such items: an item
  that moves behind a private module keeps a link that pointed at a sibling in its old file.
  `cargo doc --no-deps -p sunlit-core --document-private-items` is the form that sees them. Run 4 found three that way,
  one of them written during the run itself.
- **Soak measurements** take their baseline after warm-up (the first cloud texture and wgpu's allocator pools are a one-off ~85 MiB); the assertion is on the remaining simulated days. Both ends are floors, the lowest of one reading per step over seven publications, never a single reading: on `macos-latest` about one reading in twenty is 8 to 11 MiB above a level that does not otherwise move, and a single reading passes or fails by whether it lands on one. The roadmap has the measurements.
- **A test that needs the real 8K assets skips with a printed reason without them**, rather than failing or passing vacuously: `textures/**` is Git LFS, and a checkout without the objects holds pointer files that exist as far as anything that only asks about existence is concerned, so the check is on size. `lowering_the_resolution_lowers_the_process_footprint` in `tests/engine/` is the one such case, and it costs about 25 seconds where the assets are present. Everything else that needs a texture, including every Moon case, the golden suite's Moon and every panorama case but the two that are about the real asset, uses a generated fixture instead.

## Measurements behind the thresholds

Numbers that justify a tolerance or a budget live here rather than in the source, so that they can be compared and so
that the code says what it does instead of how it was tuned. Each one names the test or the constant it stands behind.

**What a draw added to the pass costs the rest of the frame.** Measured on the paravirtual Metal device of a `macos-latest` runner on 2026-09-06 and again on 2026-09-07, against `zero_star_intensity_leaves_catalog_pixels_at_the_clear_color`, which renders one scene twice and differs only in `star_intensity`. Seven pixels of the 131072, all on the globe near the limb where the grid minifies hardest, come back up to two of 255 away when the star draw's ten thousand sprites are in the pass. The star sprites are additive and drawn before an opaque globe, and `test_params` sets `sample_count` to 1 so there is no silhouette to blend through, yet three of the seven come back *darker* and one neighbouring pair, (284, 48) and (285, 48), exchanges values. Nothing additive does that: it is the sampled texel moving under extreme minification, and the size of it is bounded by the local texture contrast rather than by a step. WARP, lavapipe and this machine's dx12 adapter are bit-identical across the same pair. The case therefore holds a covered pixel to the outlier threshold the golden suite already uses for a difference worth seeing, and keeps the exact assertion on the background pixels, which is where the property it names lives.

**The cross-adapter deltas behind the per-adapter golden sets.** Measured on the four reference scenes, each against
WARP, at the tolerance above: lavapipe agrees to a mean channel difference of 0.19 to 0.86 with 0.001% to 0.42%
outliers, and the paravirtual Metal device on a `macos-latest` runner to 0.008 to 0.18 with at most 0.008% outliers. One
shared reference set would therefore pass on all three today, but it would spend up to 43% of the mean budget on the
difference between two correct implementations, leaving a regression that size able to hide on one platform while
failing on another. The ordering in those numbers is not the expected one: the two CPU rasterizers are the pair that
disagree most, and Metal, which is both a different shader translation target and an actual GPU, lands about five times
closer to WARP than lavapipe does.

**The memory budget's cold-start figure.** `MEASURED_COLD_START_PEAK` in `memory.rs`'s test module is 2488 MiB, the one
cold-cache startup peak anyone has measured: private bytes, at 8192, in a release build. Every resolution is held to
that one figure rather than to a smaller one derived from it, and that is the point. The peak is dominated by the two 8K
JXL decodes, which a cold downscale cache performs whatever width it was asked for; how much of the resident saving at a
lower width also shows up in the peak is exactly what nobody has measured. Deriving a per-resolution peak from the
budget's own decomposition would make the two move together and assert nothing, and it would let the budget rest on a
saving that may not be there.

The two bounding tests clear it from both sides, and by these margins: 2048 clears the measurement by 121 MiB where 8192
clears it by 633, so a cold-start figure set too low fails at the two lower widths while the widest, which is where the
3 GiB total is anchored, still passes. The narrow end is the binding case rather than a restatement of the wide one: it
gets the smallest resident allowance and has the same decode to pay for.

**The e2e suite's harness is `tests/common/`.** `tests/e2e.rs` is the seventeen cases, sixteen of them off Windows; the harness under them is one
module per layer: `process.rs` starts and watches the binary, `pixels.rs` says what a frame should look like,
`cloud_stub.rs` is the loopback cloud server, and `desktop_linux.rs` asks a Linux desktop what it did with the
wallpaper.

**The e2e render case's thresholds and its budget.** `test_render_and_exit` gives itself an empty cache directory so
that it pays the surface texture decode instead of inheriting a warm cache from whichever case ran first. Measured in
the Linux guest on 2026-09-01, the same 800x800 render peaked at 2088 MB and settled to 444 MB with a cold cache, and
sat flat at 381 MB with a warm one, where the peak is the last sample and "settled" means nothing. Its one-minute budget
comes from the same date on the development host, debug build, empty cache: 5.9 s on the GPU and 8.0 s on the software
adapter, against 2.5 s warm. A guest is a software rasterizer on a slower CPU and has never been timed, which is what
the margin is for.

**The e2e suite's own budget**, defined as every wait consuming its full timeout and then succeeding, is about 67
minutes on Linux and 45 on Windows, dominated by the two cases that publish a wallpaper five and six times. A real
Windows guest run is about 97 seconds. `xtask`'s `job_timeout` sits above the budget rather than near the real runtime,
so that a stuck case reports the signal it was waiting for instead of the job reporting that it ran out of time.

**Why three golden cases compare a window, and why two turn a parameter up.** The suite's tolerance is a mean channel
difference under 2.00 with at most 1 percent of pixels off by more than 24, measured over whatever region the case
compares. A feature a few dozen pixels across cannot move a 512 by 256 frame past that, so three cases compare a window
instead, and two more raise a parameter until the effect is larger than the tolerance. Each row below compares a
reference against the same scene with the named feature deleted.

| Case | Feature deleted | Over the whole frame | Over the case's own window |
|---|---|---|---|
| `moon_crescent` | the Moon | mean 0.22, passes | mean 3.12, 1.71 percent outliers |
| `sun_rising_through_the_band` | the refraction tint | mean 10.04, 16.80 percent | mean 55.33, 83.09 percent |
| `sun_rising_through_the_band` | the exposure gain | mean 7.27, 11.00 percent | mean 56.03, 98.58 percent |
| `sun_rising_through_the_band` | the lift and the squash | mean 0.91, 0.22 percent, passes | mean 6.19, 4.58 percent |
| `sunrise_band` | the forward lobe | mean 0.21, 0.40 percent, passes | mean 1.52, 2.83 percent |

The two turned-up parameters are the same argument without a window. `sun_grazing_the_limb` runs `sun_glow` at 1.6
because at the default strength losing the warm shift entirely comes to a mean of 2.33 against a tolerance of 2.00 and
1.04 percent outliers against a limit of 1.00, which is a test that passes or fails on rounding. `sunrise_band` runs
`atmo_sunrise_glow` at 3.0 for the same reason. Both sun cases also run at a 60 degree sky rather than the 140 degree
default, for the reason `docs/rendering.md` gives beside the four goldens.

## CI/CD

Five GitHub Actions workflows in `.github/workflows/`:

- **`ci.yml`**: `workflow_dispatch` only. It ran on every push and PR until the hosted minutes ran out, back when this repository was private and they were billed; it has been public since the 0.1.0 release, so standard runners are free and unmetered here and cost is no longer what keeps it manual. What does is that the local VM suite covers what the runners were for, and that a run nobody asked for is a result nobody reads. What a manual run still buys is the other two operating systems, so dispatch it before anything that has to hold on all three. A `fmt` job runs `cargo fmt --check` once on Ubuntu, and a `test` matrix runs `cargo test --locked --no-fail-fast -- --show-output` plus a headless `render` smoke test on `ubuntu-latest`, `windows-latest`, and `macos-latest`, uploading the contact sheet and the smoke render per OS. An `os` input narrows the run to one runner, which is what makes a macOS check worth dispatching on its own: a question about macOS is answered by one macOS job rather than by waiting on three. It was a cost argument while the repository was private and macOS minutes billed at ten times Linux; it is a round-trip argument now. The matrix comes from a `plan` job that emits the chosen entries as JSON rather than from a job-level `if`, because `matrix` is not a context a job-level `if` can read; `fmt` runs with the Linux entry and not beside every dispatch.
- **`golden.yml`**: `workflow_dispatch` only. Pick an OS, run it, download the `golden-<adapter>` artifact, review the images, commit them. It regenerates, reads the adapter key from the test's marker line, runs the suite again without `SUNLIT_EARTH_UPDATE_GOLDEN` so the job verifies what it produced, and uploads only that adapter's directory. GitHub only registers dispatchable workflows from the default branch, so it is usable once merged; before that, regenerate locally on the adapter in question.
- **`release.yml`**: runs on a push of a version tag, `vX.Y.Z` or a prerelease such as `vX.Y.Z-beta.1`, and on `workflow_dispatch`. The trigger was off from the 0.1.0 release until 0.2.0-beta.1, while release artifacts were built by `cargo xtask dist` in clean VMs alone. A dispatch takes a `publish` input that defaults to false, so the pipeline can still be exercised without a tag or a release. One job per platform and architecture: Windows on x86_64 (`windows-latest`), Linux on x86_64 (`ubuntu-22.04`) and aarch64 (`ubuntu-22.04-arm`), macOS on x86_64 (`macos-26-intel`) and aarch64 (`macos-latest`). Each builds natively on a runner of its own architecture, refused by the toolchain step if the runner's host triple is not the one the job names, because `cargo xtask bundle --verify` executes the binary it bundles and nothing here emulates another architecture. Each job builds `cargo build --release --locked -p sunlit-earth --bin sunlit-earth --target <triple>`, checks the binary's linkage (on Windows it fails if the binary names `vcruntime140` or `msvcp140`; on Linux and macOS it prints the needed libraries, the glibc floor and the deployment target), and then runs `cargo xtask bundle --verify`, which reads the platform and architecture out of the binary's header, names the archives `sunlit-earth-<version>-<platform>-<arch>`, assembles the archive its platform's users open, reads it back, unpacks it and renders from it twice. The job then checks that `build-info.json` records the architecture the job was meant to build. A last job downloads the artifacts and creates the release as a draft, with the records merged into one `build-info.json` keyed by `<platform>-<arch>`; it never goes public on its own, and publishing the draft on GitHub is the manual step that does. A tag run stops before it builds unless the tag names the workspace version, because an archive must never be named after a version other than the tag's, and it saves no cache, because a cache keyed on a tag is one no later ref can reach. `MACOSX_DEPLOYMENT_TARGET` is 11.0 on both Mac jobs, matching `LSMinimumSystemVersion` in `Info.plist`. A `publish`-false dispatch is also what keeps the `release-<platform>-<arch>` caches on the default branch warm, since a tag run restores from them and saves nothing back.

- **`package-managers.yml`**: runs when a release is published (`release: types: [published]`), not on the tag, because `release.yml` only creates a draft and a draft's assets are not at the public download URL; it also runs on `workflow_dispatch` with a `tag` input and a `push` input that defaults to false. It never waits on `release.yml` and `release.yml` never calls it. GitHub raises no workflow events for release actions taken with `GITHUB_TOKEN`, so this runs only because a person publishes the release; if publishing is ever automated with that token, nothing runs, and a dispatch with the tag is the way to catch up. The same dispatch is how a release whose push failed is repaired and how the repositories are bootstrapped, and since a `release` event runs the workflow file at the tagged commit, the first release the event handles on its own is the first one tagged after the file was merged. A `manifests` job refuses a tag that is not a published release, and refuses a prerelease, by the release's flag or by a `-` in its tag, whenever the run would push, which is every `release` event and a dispatch with `push` on. It then downloads the release's own archives with `gh release download`, so what it hashes and installs is what users download, and runs `cargo xtask manifests`. Five `verify` jobs install the result the way a user would: Scoop from the manifest's path on `windows-latest`, and Homebrew from a local tap made with `brew tap-new --no-git` on `ubuntu-24.04`, `ubuntu-24.04-arm`, `macos-latest` and `macos-26-intel`, each Homebrew updated first so the check is against the Homebrew users have. Each runs `brew style` and `brew audit --strict` on its manifest (the formula with `FormulaAudit/ComponentsOrder` excluded, departure 2 of the plan), checks that `sunlit-earth --version` through `PATH` names the release, and runs `cargo xtask verify-install` on the command `PATH` resolves to: the two renders `bundle --verify` makes, from a working directory outside the install. Windows also requires that the installed exe has no `Zone.Identifier` stream and that the Start Menu shortcut points at the `current` junction's exe; macOS requires that `com.apple.quarantine` is gone from `/Applications/Sunlit Earth.app` and that `open -a` starts it; Linux runs the caveat's `install-user.sh` with `--exec` and then `--uninstall`. Every job ends with an uninstall and fails on anything it leaves behind. Only then does the `push` job run, in the `package-managers` environment, with a token for the `sunlit-earth-packaging` GitHub App minted by `actions/create-github-app-token` for `scoop-bucket` and `homebrew-tap` alone. It commits as the app's bot and only what changed, so a rerun is a no-op. What the verify jobs do not prove: that a real Mac shows no Gatekeeper dialog (the runner has no user to see one), that SmartScreen stays quiet on a machine with reputation checks on, and anything about upgrades, since each job installs one version into a clean prefix. The runners have no GPU; the renders are on lavapipe, Metal's paravirtual device and WARP. For `v0.2.0-beta.1`, which predates the texture lookup through a symlink, the macOS jobs verify the app's own binary rather than the command on `PATH` (departure 3). Before the merge it carried a temporary trigger on pushes to its feature branch, which ran the dry run for `v0.2.0-beta.1`, green on all five verify jobs in <https://github.com/sunlit-earth/sunlit-earth/actions/runs/36051180250>; like every workflow here, a dispatch of it needs the file on the default branch.
- **`macos-build.yml`**: `workflow_dispatch` only, and the only compiler this project has for macOS, since nobody here owns a Mac and the C build script in Astronomy Engine fails a cross `cargo check` from Windows. Three modes. **`check`** runs `cargo check --all-targets` and the unit tests, which is the cheap loop while macOS code is being written. **`build`** builds the release binary for the runner's own architecture, `aarch64-apple-darwin` on `macos-latest` and `x86_64-apple-darwin` on `macos-26-intel`, so every mode runs on either image and the bundle and e2e steps execute what was built natively; it then runs `cargo xtask bundle --platform macos --verify`, and uploads the `.app` zip, the tarball and the record. **`build-and-e2e`** does that and then runs the desktop suite in the runner's own session with `SUNLIT_EARTH_E2E_WALLPAPER=1`, uploading the log, `sunlit-earth displays`, `system_profiler SPDisplaysDataType` and a screenshot from before and after. That last mode is the only route this project has to the "runner" tier of evidence for the wallpaper setter, since there is no macOS guest. An `interactive` input composes with all three rather than being a fourth mode, and holds the runner open for `interactive_minutes` afterwards so the desktop can be looked at while it is still there: the runner joins a tailnet as an ephemeral node and answers a VNC client at a `100.x` address, which is the only address it has, since a hosted runner takes no inbound connection and a public tunnel would both publish a reachable address in this repository's logs and meter a stream that a rendering desktop is the worst case for. The server is macVNC, built from source in the job and started from the hold step, not Apple's Screen Sharing: the runner image grants screen capture to the runner's own process tree (`/bin/bash`, the provisioner, `hosted-compute-agent`) and not to `screensharingd`'s agent, which therefore authenticates and streams a black frame, while anything the job starts inherits the grant. It needs `TS_OAUTH_CLIENT_ID`, `TS_OAUTH_SECRET` and an eight-character `VNC_PASSWORD` as repository secrets, and it runs under `!cancelled()`, because a failed build is when looking is worth most. A `screens` input of 2 gives the runner a second screen before anything is built, so `displays`, the e2e suite and the session all see two: `.github/macos/virtual-display.m`, compiled in the job, creates a 1600x900 screen through CoreGraphics' private `CGVirtualDisplay`, the API DeskPad uses, and moves it flush to the right of the main one, since macOS placed it on the left in one run and the right in another. The screen lasts as long as that process does. Adding it switches the Apple Silicon runner's own screen from 1024x768 to 1920x1080, and the session serves the second screen with a second macVNC on port 5901. `touch /tmp/release-the-runner` inside the session ends the job early; the free tailnet allowance is a monthly pool of node minutes rather than a per-session limit. The build steps are release.yml's own, verbatim where they apply, so the file that has never run shares as much as possible with the one that has. A `ci.yml` dispatch with `os: macos-latest` is the whole suite at the end of a step. Like `golden.yml`, all of it is dispatchable only once it is on the default branch.

Key details:

- `fail-fast: false` on both matrices. All the results, every time: cancelling macOS because Linux failed costs a round trip to learn something the same run already knew.
- Per-OS setup, all of it explicit rather than relied on from the runner image: LLVM 19 pinned on Windows via `KyleMayes/install-llvm-action@v2` with `LIBCLANG_PATH`; Slint's build dependencies plus `mesa-vulkan-drivers` and `xvfb` via apt on Ubuntu; Xcode's `libclang.dylib` located defensively on macOS.
- Linux tests run under `xvfb-run -a`. Nothing opens a window today, so this is for the first windowed test to arrive. It does propagate the exit status, so a failing suite still fails the job.
- The render smoke test is deliberately **not** wrapped in xvfb: `run_render` claims to need no window, and running it with no `DISPLAY` is what makes that a tested claim. It asserts the output is a 640x360 PNG by reading the IHDR header, not that the file is merely non-trivial in size.
- `--show-output` on the test step, because the numbers worth having from a CI run come from tests that pass: the golden suite's adapter key and the soak test's per-OS memory profile. libtest discards those otherwise.
- `--no-fail-fast` on the test step, and the render smoke test runs whatever the suite made of itself. Cargo stops at the first target that fails, so the targets after it report nothing: one failing engine case cost a whole macOS round trip to learn that the golden, soak and shading targets had never run. A dispatch is a manual act with a person waiting on it, so a run that reports everything it knows is worth the extra minutes.
- The release checkout is `lfs: true`. The four JXL textures go inside the bundle, and `cargo xtask bundle` refuses rather than shipping a procedural grid under a name that promises a release. 4.7 MB per run.
- The Linux release job runs on `ubuntu-22.04` rather than `ubuntu-latest`, which is 24.04. glibc 2.35 is the floor the `linux-builder` image gives and the one `cargo xtask dist` checks a binary against; a binary linked on 24.04 needs 2.39 and will not start on the distributions that floor exists to cover.
- The release jobs install the channel `rust-toolchain.toml` pins with `rustup toolchain install`, rather than adding `dtolnay/rust-toolchain@stable` beside it, which would be a second toolchain downloaded on every cold runner to build nothing.
- The bundle verification runs the real binary twice, so `SUNLIT_EARTH_CONFIG`, `SUNLIT_EARTH_METRICS_DIR` and `SUNLIT_EARTH_CACHE_DIR` point into the workspace rather than the runner's app data, and `SUNLIT_EARTH_NO_CLOUDS` is set: neither render waits for a cloud fetch and nothing asserts on one. The step also compiles the xtask in the dev profile, which is a second dependency tree on the runner, and prints its own wall time so that cost stays visible.
- The publish job merges the records into one `build-info.json`, an object keyed by `<platform>-<arch>`, because files of the same name cannot be separate release assets and one per build crowded the release page, and marks the release a prerelease when the tag carries a hyphen, which all three tags this repository has do.
- `ci.yml`, `golden.yml` and `package-managers.yml` declare `permissions: contents: read` at the top level. `release.yml` needs write and says so itself; `package-managers.yml` writes to the two package manager repositories only through the app token, never through its own.
- `package-managers.yml` keys its `concurrency` group on the release's tag rather than the ref, and never cancels: two runs for one release would race to push, and a run for another release has nothing to do with it. The other four workflows declare a `concurrency` group keyed on the workflow and the ref, so a second dispatch on one ref replaces the first rather than queueing behind it. `release.yml` is the exception to `cancel-in-progress`: it is false on a tag ref, because a run that is publishing a release is not one to cancel, and the per-ref key already keeps a branch dispatch away from it.
- Publishing needs a tag *and* an intention. A tag push would publish, and that is the path the 0.1.0 release made unreachable; the live one is a dispatch, which publishes only on a tag ref with `publish=true`, so a dispatch on a tag with `publish=false` builds and verifies without touching the release that tag already has; and a dispatch from a branch that asks for `publish=true` fails at the first step with the reason rather than handing the release action a branch name to tag. A branch dispatch with `publish=false` is the dry run and runs to the end.
- Cache keys are `ci-linux` / `ci-windows` / `ci-macos` for the test profile and `release-<platform>-<arch>` for the release one. The split is not tidiness: cargo fingerprints the two profiles separately, so nothing compiled for one is reusable by the other, and a merged key would make every job restore a cache half of which it cannot use. What the split costs is the one part they do share, the registry index and crate cache under `~/.cargo`, which is stored once per key and measured 194 MB on the development host in September 2026. Against a 10 GiB repository budget that is worth paying twice.
- Every `RUSTFLAGS` in this repository is `-D warnings`, `release.yml` included, and the cache is half of why. rust-cache folds the `RUST*` environment into its key and cargo's own fingerprint includes `RUSTFLAGS`, so a job that omits it neither restores from nor is restorable by a job that has it, whatever `shared-key` says. `release.yml` omitted it until 2026-09-22, which silently cost `macos-build.yml`'s `build` mode the warm cache this document claimed it had. The other half is that a release build should not be laxer about lints than the CI that gates it. Setting `RUSTFLAGS` has a cost on Windows: cargo takes extra flags from exactly one source, and the environment variable wins over `[target.<triple>] rustflags` in `.cargo/config.toml`, so any job that sets it drops the config's `+crt-static` and links the dynamic C runtime. `release.yml` therefore spells out `-D warnings -C target-feature=+crt-static` on its Windows job, and its linkage check is what catches a regression. The `ci.yml` Windows jobs still build without it; their test binaries run on a runner that has the redistributable, so nothing there notices.
- `cache-on-failure: true` on every one of them. It defaults to false, and every workflow here is dispatch-only, so a run exists because somebody wanted an answer and the answer is often a failure; without it the run that finds the failure saves nothing and the run that goes back to look recompiles from cold. `macos-build.yml`'s `interactive` input sharpens that: the session steps run under `!cancelled()` so the desktop is there whatever the suite did, but the job still concludes as failed, so a debugging session could otherwise never warm anything.
- `macos-build.yml` takes whichever key its mode is in: `check` deliberately shares `ci-macos`, since it compiles the same tree in the same profile as the macOS test job; `build` takes `release-macos-x86_64` or `release-macos-aarch64` by runner, since it compiles the release profile the matching `release.yml` job warms, which holds now that both set the same `RUSTFLAGS`; and `build-and-e2e`, which compiles both profiles, takes a key of its own, `macos-build-e2e`, so its rare runs start cold rather than mixing test artifacts into either shared cache. The key is a function of `mode` and, in `build`, the runner, which is what lets `interactive` be a separate input rather than a fourth mode: a screen sharing session compiles nothing, so it has nothing to cache and nothing to keep out of a cache. The Windows test key is spelled out rather than derived from the runner label so it kept the key it had before the matrix.
- The first run on a new PR builds cold (roughly 45 minutes on Windows) because Actions caches are scoped per merge ref. Later runs on the same PR restore it. That is expected, not a regression.
- All `cargo` commands use `--locked`. `Cargo.lock` lives at the workspace root.
- GPU tests run on the software adapter where the platform has one: WARP on Windows, lavapipe on Linux. macOS has no CPU adapter, so it falls back to the runner's paravirtual Metal GPU, which is a real one.
- **The macOS job.** On 2026-09-07 `stars::zero_star_intensity_leaves_catalog_pixels_at_the_clear_color` failed on one covered pixel moving two of 255; the revision that holds a covered pixel to the golden suite's outlier bound passed on `macos-latest` in all three runs of 2026-09-23. The soak case failed there by where a single memory reading landed, not on a leak, and now compares floors; the roadmap has the measurements.
- A dispatch-only workflow is one nobody runs unless they mean to, and that has a cost the macOS branch paid: the Linux and macOS jobs had both been red on `main` for weeks, each because of dead code reachable only from a `cfg`-gated arm, and `RUSTFLAGS: -D warnings` makes that an error. Nothing says CI is green except the last dispatch, so a claim about CI wants a run behind it.
- Clippy runs locally only (its artifacts are incompatible with the test cache and force full recompilation). `-D warnings` in CI covers rustc's own lints.
